# S2 화면 캡처·DPI

결론 → [ADR-0021](../../docs/decisions/0021-worker-dpi-capture.md) (제안)

## 확인하려 한 것

배율 125%·150%에서 **UIA가 준 좌표 = 캡처 이미지의 좌표 = 클릭 좌표**인가. 어떤 조건에서 어긋나는가. Worker 프로세스의 DPI 인식 모드와 캡처 라이브러리를 무엇으로 정할 것인가.

## 환경

| 항목 | 값 |
| --- | --- |
| OS | Windows 11 Education 10.0.26200 |
| 화면 | 1920×1080 **한 대**. 배율 100% → 125% → 150% → 100% (사용자가 설정에서 바꿈, 로그아웃 없이) |
| Python | 3.12 (uv 관리), PEP 723 인라인 의존 |
| 라이브러리 | `uiautomation` 2.0.29, `mss` (최신), `pillow` (최신) |

## 파일

| 파일 | 하는 일 |
| --- | --- |
| `target_window.py` | 시험 창(표준 라이브러리만). 색 칸 다섯 개, 칸마다 UIA 이름 `S2-<색>`, 받은 클릭을 jsonl로 기록. DPI 인식 모드를 인자로 정한다 |
| `probe_capture.py` | Worker 역할. DPI 모드를 정하고 시험 창을 모드별로 띄워 판정 → `outputs/result-<배율>pct-w<모드>.json`, `outputs/summary.txt` |

```bash
uv run spikes/S2-capture-dpi/probe_capture.py all       # Worker 모드 4가지 × 시험 창 모드 3가지
uv run spikes/S2-capture-dpi/probe_capture.py summary   # 지금까지 결과 표
```

판정 방법 (칸마다):
1. UIA `BoundingRectangle` — Worker가 받는 좌표.
2. 가상 화면 전체를 캡처(mss, Pillow `ImageGrab`)해서 그 색의 실제 테두리 상자를 찾고 UIA 사각형과의 차이를 잰다. `[0,0,0,0]`이면 일치.
3. UIA 사각형 가운데를 클릭하고, 시험 창이 받은 칸 이름과 칸 안 위치(비율)를 본다. `(0.5, 0.5)`면 정확.

**안전장치:** 시험 창은 맨 위 고정. 클릭 전에 그 점의 최상위 창이 시험 창 프로세스인지 확인하고 아니면 누르지 않는다. 끝나면 커서를 제자리로 돌린다.

모드 이름: Worker `default`(아무것도 정하지 않음) · `unaware` · `system` · `pmv2`(Per-Monitor v2). 시험 창 `unaware`(Windows가 비트맵 확대) · `system` · `pmv2`.

## 본 것

### 결과 (클릭은 모든 조합 5/5 맞는 칸)

| 배율 | Worker | 시험 창 DPI 인식 | 시험 창 DPI 비인식 |
| --- | --- | --- | --- |
| 100% | 모두 | 캡처 일치, 클릭 정중앙 | 캡처 일치, 클릭 정중앙 |
| 125% | default·system·pmv2 | 캡처 일치, 클릭 정중앙 | **±1px** (예 `[0,1,-1,0]`), 클릭 (0.5, 0.48) |
| 125% | **unaware** | **캡처 어긋남 44~120px** | **캡처 어긋남 55~149px** |
| 150% | default·system·pmv2 | 캡처 일치, 클릭 정중앙 | **±1px** (`[1,1,-1,-1]`), 클릭 정중앙 |
| 150% | **unaware** | **캡처 어긋남 118~151px**, 클릭 (0.49, 0.52) | **캡처 어긋남 110~150px** |

캡처 한 장(1920×1080 가상 화면 전체): mss 36~53ms, Pillow 34~50ms. 둘 사이에 좌표 차이는 한 번도 없었다.

### 발견

1. **DPI 비인식 Worker는 캡처와 UIA 좌표가 배율만큼 어긋난다.** Windows가 이 프로세스에 UIA 좌표·`GetSystemMetrics`·클릭을 모두 축소 좌표(150%면 1280×720)로 가상화해서 **UIA로 찾고 클릭하는 것은 맞는다.** 그런데 캡처 이미지는 실제 픽셀(1920×1080)이다. 화면 이미지에서 위치를 찾아 클릭하는 AI 태스크, 캡처를 잘라 실행 기록에 넣는 일이 모두 틀린 곳을 가리킨다. 오류가 나지 않고 조용히 틀린다.
2. **DPI 인식 Worker(system·pmv2)는 세 좌표가 일치한다.** 대상 앱이 DPI 비인식이어서 Windows가 비트맵으로 확대한 경우에만 반올림으로 ±1px 차이가 난다 — 가운데 클릭에는 영향이 없다.
3. **라이브러리가 프로세스 DPI 모드를 몰래 바꾼다.** 아무것도 정하지 않은 프로세스(기본 = 비인식)에서
   - `import uiautomation` 하는 순간 per-monitor로 바뀐다.
   - `mss.MSS()` 객체를 만들 때 per-monitor로 바뀐다.
   - Pillow `ImageGrab.grab()`은 프로세스 설정을 바꾸지 않는다 (캡처할 때만 스레드 단위로 바꾸는 것으로 보인다 — 그래서 비인식 프로세스에서도 실제 픽셀로 찍힌다).
   DPI 모드는 **처음 정한 것만 먹고** 나중 호출은 실패한다. 즉 import 순서에 따라 Worker의 좌표계가 달라진다. 이번 `default` 결과가 맞은 것은 우연(uiautomation을 먼저 import)이다.
4. **비인식 프로세스는 배율을 알 수 없다.** `GetDpiForSystem()`이 96, 화면 크기가 축소값으로 보인다. 실제 배율은 `GetDeviceCaps(DESKTOPHORZRES)`(가상화되지 않는 해상도)로만 알 수 있었다 — 처음엔 이걸 몰라 결과 파일 이름이 `100pct`로 붙어 100% 결과를 덮어썼다 (다시 만들었다).
5. 배율을 바꾼 뒤 로그아웃 없이 새로 띄운 프로세스는 새 배율을 바로 받았다.
6. 함정 두 개 (스파이크 코드에서 겪음):
   - uv 가상환경의 `python.exe`는 진짜 인터프리터를 자식으로 띄우는 런처다. `Popen().pid`는 창 주인이 아니다 → 창의 pid는 UIA(`ProcessId`)로 얻는다.
   - ctypes 기본 반환형은 32비트 int라 HWND·HDC가 잘린다. 125%에선 우연히 통과하고 150%에서 `OverflowError`가 났다 → `restype`/`argtypes`를 항상 적는다.

### 하지 않은 것 (다음에)

- **다중 모니터, 모니터마다 배율이 다른 경우** — 모니터가 한 대뿐이다. 이론상 system 인식 Worker는 주 모니터와 배율이 다른 모니터에서 어긋나고 pmv2만 맞는다. 이 결정의 가장 큰 남은 위험이라 모니터 두 대 PC에서 `probe_capture.py all`을 다시 돌려야 한다 (시험 창을 두 번째 모니터로 옮기는 인자 추가 필요).
- 배율 175%·200%, 원격 데스크톱(RDP) 세션.
- 실제 앱(Win32 DPI 비인식 사내 앱) — 시험 창으로 대신했다.
- DXGI 캡처(`dxcam` 등). 전체 화면 40ms 수준이라 지금은 필요 없어 보인다.
