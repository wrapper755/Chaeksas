# ADR-0054. 서버 실행기는 기다리는 실행을 **JSON 한 덩이로** 담고, 실행마다 **스레드 하나**로 돈다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-10-13 |
| 관련 | 스파이크 `spikes/s10-server-runner-state/`, [C12](../03-contracts/C12-server-runner-center.md), [C3](../03-contracts/C3-run-events.md), [C6](../03-contracts/C6-approvals.md), [C11](../03-contracts/C11-service-app-common.md), [ADR-0007](0007-client-initiated-communication.md), [ADR-0014](0014-one-bot-per-pc.md), [ADR-0015](0015-run-location.md), [ADR-0016](0016-server-first.md), [ADR-0038](0038-approval-request-channel.md) |

## 배경

업무 대부분은 서버 Bot으로 돈다 (ADR-0016). 서버 실행기는 PC와 **두 가지가 다르다**: 여러
건을 동시에 돌리고, 결재·메시지를 기다리는 실행은 **일꾼을 놓고 상태만 남긴다** (ADR-0015,
C12). PC는 거꾸로 — 실행기 프로세스가 살아 있으면서 끝까지 자리를 쥔다 (ADR-0014).

그런데 엔진의 실행은 **메모리 안의 `Run` 객체**다 (`core.run_state`). 토큰·변수·기다림·사람
요청·안쪽 실행을 들고 있고, 바깥 세계(`RunEnv`)에는 파일·보내기·서비스 앱·모델·확장 어댑터가
꽂혀 있다. 이것을 **글로 담아 되살릴 수 있는지**가 M7 기준 셋째(「서버 실행기를 재시작해도
이어 간다」)를 떠받친다. C12가 스스로 「서버 실행 세부 구현은 **M7 스파이크 뒤 ADR로
확정**」이라고 적어 둔 것이 이 자리다.

스파이크 `s10`이 BX-03(실행 위치 `server`, 결재 `location: center`, 경계 타이머 둘)과
서버 예제 **42개**로 확인했다. 결론은 **된다**이고, 되는 모양을 여기 적는다.

## 선택지

### 상태를 어떻게 남기나

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. `Run`을 **JSON 한 덩이**로 담아 저장소에 넣는다 | 엔진을 고치지 않는다. 사람이 읽을 수 있다. 되살린 실행이 **같은 답을 낸다**(측정함) | 엔진에 칸이 늘면 조용히 빠질 수 있다 → 시험으로 막는다 |
| B. `pickle` | 아무것도 안 적어도 된다 | 판이 바뀌면 못 읽는다. 예외·어댑터까지 끌려 들어간다. 저장소를 사람이 못 본다 |
| C. 실행 기록(C3)을 되밟아 상태를 짓는다 | 저장소가 따로 없다 | 기록에 **업무 값이 없다**(원칙 6). 되밟을 수 없다 |
| D. 기다리지 않는다 — 결재를 기다리는 동안 프로세스를 띄워 둔다 | 아무것도 안 만든다 | 며칠 기다리는 실행이 자리를 쥔다. 상한 10이 금세 찬다 (BX-03은 P7D다) |

### 동시 실행의 모양

| 선택지 | CPU만(8건) | 막힐 때(8건) | 비고 |
| --- | --- | --- | --- |
| E. 협력 루프 (한 스레드가 `step()`을 번갈아) | **9~13ms** | **1,610ms** | 엔진의 본래 모양. 막히는 걸음이 루프 전체를 세운다 |
| F. 한 프로세스·실행마다 스레드 하나 | 13~18ms | **215ms** | `Run` 하나는 스레드 하나만 만진다 |
| G. 실행마다 OS 프로세스 하나 | 64~76ms | 256ms | 확장을 N번 싣고 메모리도 N배 |

「막힐 때」는 보내기 한 번이 0.2초 걸리는 경우다 (서비스 앱·모델 왕복 자리).

## 결정

**기다리는 실행은 `Run`을 JSON 한 덩이로 담아 SQLite에 넣고(A), 도는 실행은 한 프로세스
안에서 실행마다 스레드 하나로 돈다(F).**

### 1. `Run`의 칸을 셋으로 가른다

| 갈래 | 칸 |
| --- | --- |
| **담는다** | `variables`·`state`·`tokens`(`loop` 포함)·`last_token_id`·`pendings`·`arrivals`·`expected`·`waits`·`children`(재귀)·`nested`·`mode`·`executor`·`version`·`started`·`instances`·`call_seqs`·`learned` |
| **다시 꽂는다** | `process`·`log`·`env`·`helpers` |
| **버린다** | `error` — 예외 객체다. **실패한 실행은 되살리지 않는다** |

**`Run`의 칸이 셋 중 하나에 반드시 들어가야 하고, 그것을 시험이 센다.** 엔진에 칸을 더하면
시험이 깨져 「담아야 하나」를 묻게 한다 — 조용히 빠지면 되살린 실행이 다른 답을 낸다.

담을 때 **모양을 바꾸는 것이 셋**이고 되살릴 때 **파이썬 타입으로 되돌린다**.

| 칸 | 담을 때 | 안 되돌리면 |
| --- | --- | --- |
| `waits[].due_at` | 시각 → ISO 글 | 타이머가 안 울린다 |
| `arrivals`의 값 | **집합** → 목록 | 합류가 **도착한 토큰을 두 번 센다** |
| `pendings[].form` | 계약 모델 → `model_dump` | 답 검증이 폼을 못 읽는다 |

### 2. 다시 꽂는 넷은 **어디서 오는지**까지 정한다

| 칸 | 어디서 |
| --- | --- |
| `process` | **설치된 패키지에서 다시 읽는다.** 그림은 담지 않는다. 담은 `bpm_process_id`·`version`과 **다르면 되살리지 않고** `runner_version_changed`로 닫는다 — 다른 판으로 이어 가면 없는 노드를 밟는다 |
| `log` | `runs/<run_id>.jsonl`을 **다시 읽어** `seq`를 잇고, 보낸 자리는 `runs/<run_id>.sent`에서 읽는다 (`core.run_shipping.read_sent`) |
| `env` | 실행하는 쪽이 새로 만든다 — 출력 폴더·보내기·서비스 앱·모델·도구·확장·DMN·호출 대상·시계. 기본값은 **아무것도 못 한다** |
| `helpers` | `core.helpers.bind(now=run.started)` — **실행 시작 시각**이다. 「지금」으로 묶으면 `오늘()`·`지난달()`이 다른 답을 낸다 |

**`log`를 빈 `RunLog`로 되살리면 실행은 멀쩡히 끝나고 Center 쪽만 조용히 깨진다** (스파이크
장면 E). `seq`가 1부터 다시 시작해 C3 멱등 `(run_id, seq)`이 겹치므로 Center는 이어 돈 줄을
**지나간 것으로 보고 버리고**, `run_finished`의 셈이 **0으로** 올라가 CON-01·CON-02가
「사람 개입 0」이라고 말한다. Center는 줄을 다시 읽어 세지 않아 고칠 길이 없다.

### 3. 적는 때는 둘, 지우는 때는 하나

| 때 | 저장소의 상태 |
| --- | --- |
| 실행을 시작할 때 | `running` |
| 실행이 **멈출 때** (`blocked()`이고 `WAITING`) | `waiting` + 스냅샷 |
| 끝났을 때 (성공·실패·취소) | **지운다** (실행 기록 파일은 남는다) |

**걸음마다 적지 않는다.** 실행 기록 파일에 이미 걸음이 다 있고, 되살릴 자리는 **기다림**뿐이다.

**시작할 때 적는 것을 빠뜨리면** 다시 뜬 실행기가 죽은 실행을 알지 못해 Center의 작업이
`accepted`로 영원히 남는다. 그래서 스냅샷 없이도 행은 먼저 들어간다.

### 4. 되살리면 **마지막 기다림 이후를 다시 한다**

C12가 적은 「실행 중이던 태스크는 처음부터 다시 한다」보다 넓다 — 마지막 기다림 뒤에 밟은
노드를 **전부** 다시 밟는다.

**C11 멱등 키를 따로 적어 둘 필요가 없다.** `instances`·`call_seqs`가 스냅샷과 함께 되돌아가
키(`run_id`·`node_id`·`node_instance`·`call_seq`)가 **같은 값으로 다시 만들어지므로** 서비스
앱이 두 번째 호출을 걸러 준다. C12의 「`node_instance`와 `attempt`는 호출 전에 저장해 둔다」는
이 결정으로 필요 없어진다.

**요구 사항은 그대로이고 방법만 바뀐 것이다.** 계약 README 원칙 9가 말하는 것은 「재시작 뒤에도
같은 키로 다시 부를 수 있어야 한다」이고, C11이 적어 두었던 「호출 전에 저장한다」는 그것을
이루는 한 가지 방법이었다. 스냅샷이 같은 일을 하므로 C11의 그 줄(문서와 `idempotency_key()`의
docstring)을 **요구 사항을 말하는 쪽으로** 고쳤다. `attempt`는 재시도 안에서만 올라가는
지역 값이라 스냅샷에 담지 않는다 — 되살리면 1부터 다시 세고, 처음 시도의 키가 처음 시도와
같으므로 어긋나지 않는다.

**기다림이 없던 실행(쭉 도는 BPM 프로세스)은 되살리지 않는다** — `runner_restarted`로 닫고
C5 `run_status`에 `failed`로 적는다. 보내기(메일·웹훅)는 멱등이 아니라 처음부터 다시 돌리면
**두 번 보낸다**. 다시 돌릴지는 **운영자가** 작업을 다시 내 정한다.

### 5. 동시 실행 — 한 프로세스, 실행마다 스레드 하나

- **협력 루프를 쓰지 않는다.** 엔진의 본래 모양이고 CPU만 쓰면 가장 빠르지만, 막히는 걸음
  하나가 루프 전체를 세워 **상한 10이 사실상 1이 된다**(1,610ms ↔ 215ms).
- **프로세스를 실행마다 띄우지 않는다.** 60~70ms와 N배 메모리를 더 쓰고 얻는 것이 없다.
  확장·모델 클라이언트를 N번 싣는 것도 값이다.
- `Run` 하나는 **스레드 하나만** 만진다. 스레드가 함께 보는 것은 `Engine.handlers`(읽기
  전용)와 저장소·전송 큐뿐이고 **그 둘만 잠근다**.
- **기다리는 실행은 스레드를 놓는다.** `capacity.running`은 스레드를 쥔 수이고
  `waiting[]`은 세지 않는다 (C12 — 상한 3에 기다리는 3건을 들고도 새 작업 3건을 더 받는다).

### 6. Center가 꺼져 있어도 **기한은 간다**

실행기가 들고 버티는 것은 저장소의 스냅샷, 실행 기록 파일, 올리지 못한 결재 요청(ADR-0038),
`restored[]`다. **부르는 쪽이 다시 온다** (ADR-0007).

**경계 타이머는 로컬 시계로 잰다.** 그래서 Center가 며칠 꺼져 있어도 마감이 지난 실행은
실행기가 혼자 닫는다 — 스파이크에서 결재가 Center 결재함에 `open`으로 떠 있는 동안 실행이
`기한초과반려`로 끝났다. **기한은 업무 규칙이지 전송 규칙이 아니다**(결재자가 못 봤다고
마감을 늘려 주면 그림이 적은 뜻이 깨진다). 갈 곳 없이 남은 결재는 C6의 `run_ended` 자동
회수가 받는다.

## 결과

- 쉬워지는 것:
  - M7 기준 셋째가 **엔진을 고치지 않고** 선다. `core.engine`·`core.run_state`에 손대지
    않는다 — 담고 되살리는 것은 서버 실행기 쪽 일이다.
  - 저장소를 사람이 읽을 수 있다(JSON). CON-12가 「기다리는 실행」을 보일 때 쓸 거리가 그대로 있다.
  - 전송은 새로 만들 것이 없다 — `core.run_shipping`이 `.sent`를 파일로 두므로 다시 떠도 이어진다.
  - BX-03(며칠 대기)의 인수 시험에 **재시작을 끼워 넣을 수 있다** (M7 기준 여섯째).
- 어려워지거나 포기하는 것:
  - **엔진에 칸을 더할 때마다 담는 길도 고쳐야 한다.** 시험이 막지만 일은 는다.
  - **쭉 도는 실행은 재시작을 못 넘는다.** `runner_restarted`로 닫고 운영자가 다시 낸다.
  - 스냅샷은 **기다림마다 한 번**이라, 멈춘 뒤 밟은 걸음은 되살릴 때 다시 밟는다. 서비스
    앱은 멱등 키가 걸러 주지만 **보내기는 아니다** — 기다림 바로 뒤에 보내기를 두면 두 번
    보낼 수 있다. C14에 규칙을 더할지는 인수 시험에서 실제로 걸리면 본다.
  - 스레드라서 `Run` 하나를 두 곳에서 밀면 깨진다. 지금은 그럴 길이 없지만 **CON-12의
    「유실 처리」가 도는 실행을 건드리지 않게** 해야 한다 (오프라인인 실행기만 — C12).
- 다시 볼 조건:
  - 스냅샷이 **수백 KB**가 되면 (업무 변수에 큰 목록이 들어가면) JSON 한 덩이를 다시 본다.
    지금 재 본 것은 BX-03 2KB, 서버 예제 42개가 모두 0.5~2KB다.
  - 상한을 **수십**으로 올려야 하면 스레드 모양을 다시 본다 (그때는 `asyncio`나 프로세스
    묶음이다). 지금 기본은 10이다.
  - **PostgreSQL로 옮길 때** (「나중에」 목록) 스냅샷 칸이 그대로 가는지 본다.
  - PC 위임(M7 기준 넷째)을 붙일 때 — 서버 실행의 `callActivity`가 Bot UI를 부르면
    `children`이 **다른 PC에 있다**. 이 결정은 그 경우를 다루지 않는다.
