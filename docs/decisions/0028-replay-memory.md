# ADR-0028. 재생 명세는 패키지 안에 넣고, 도구 인자는 `{변수}` 템플릿으로 적는다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-10-04 |
| 관련 | [C14](../03-contracts/C14-bpmn-extensions.md) §재생, [C1](../03-contracts/C1-package-manifest.md) 패키지 구성(`memory/specs.json`), [ADR-0010](0010-service-apps.md) §2(수행 모드), [ADR-0027](0027-llm-connection.md), 스파이크 [`spikes/s7-llm/`](../../spikes/s7-llm/NOTES.md), M3 조각 3c |

## 배경

ADR-0010은 수행 모드를 둘로 갈랐다 — 자율 수행(Studio, LLM을 쓴다)과 **결정 수행**(Bot UI 운영 실행, 「학습·등록된 대로. LLM 쓰지 않거나 최소」). C1의 패키지 구성에는 `memory/specs.json`(재생 명세) 자리가 있지만 **무엇을 어떤 모양으로 적는지는 비어 있었다**. `docs/01-architecture.md` §7도 「저장 방식은 새로 정한다」로 두었다.

세 가지 근거가 모였다.

- **프로토타입**은 성공 궤적을 벡터 DB에 쌓아 LLM 없이 재실행하고, 실패하면 자율로 돌아가 덮어썼다. 시나리오 3에서 **자율 388초 → 재생 56초**.
- **예제의 교훈**이 두 번 같은 말을 한다. BX-37: 「재생 명세는 태스크마다 하나라서, 종류에 따라 달라지는 값은 목표 문장이 아니라 **입력으로 받아야** 세 조항에 맞게 재생된다.」 BX-02: 「주소를 목표 문장에 쓰면 재생이 그 문장에 묶인다 — 업무 파라미터로.」 BX-36: 「재생 명세가 맞지 않을 수 있다. 그때 **운영에서 몰래 자율 수행으로 넘어가지 않는다** — 오류 경계로 받아 사람에게.」
- **스파이크 S7**: 예제의 AI 태스크 31곳 중 **18곳은 도구가 없다**. 되밟을 「도구 차례」가 아예 없는 태스크가 절반을 넘는다.

## 선택지

### 무엇을 재사용하나

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 계획만 (도구 차례는 기억, 마지막 추출은 모델 1회) | 입력이 달라져도 맞다. ADR-0010의 「최소(값 추출)」 그대로 | 운영에서도 늘 모델을 부른다. **도구 없는 18곳은 이득이 0** |
| B. 완전 (답까지 기억에서, 모델 0회) | 프로토타입의 388→56초 | 도구 없는 태스크에서는 **그냥 캐시**다 — 입력이 달라도 같은 답을 낸다 |
| **C. 태스크마다 정책** | 도구가 **일을 하는** 태스크는 B, 도구가 **읽어 오고 모델이 판단하는** 태스크는 A, 매번 다른 것은 끄기. 그림 쓴 사람이 안다 | C14에 필드 하나, 검사 하나가 는다 |

### 어디에 두나

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **D. 패키지 안 (`memory/specs.json`)** | 배포된 Bot은 **읽기만** 한다 — PC마다 다르게 학습되지 않고, C2 서명으로 무결성이 보장되며, 「어느 판이 무엇을 재생하는가」가 분명하다. C1에 이미 자리가 있다 | 현장에서 스스로 고쳐지지 않는다 (Studio에서 다시 학습해 다시 배포해야 한다) |
| E. 현장 PC 로컬에 쌓기 (프로토타입) | 현장 변화에 스스로 적응한다 | PC마다 달라지고, **운영에서 LLM이 돌아야** 하며(ADR-0010과 충돌), 무엇이 저장됐는지 추적이 어렵다 |

## 결정

**C + D.**

1. **`chk:aiTask.replay`** = `plan`(기본) / `full` / `none` (C14 §재생의 표).
   - `plan` — 도구 차례를 되밟고 **마지막 값 추출만 모델에게 한 번**.
   - `full` — 도구 차례를 밟고 **마지막 답도 기억에서** 쓴다. 모델을 한 번도 부르지 않는다.
   - `none` — 기억을 쓰지 않는다.
2. **도구가 없는 AI 태스크에 `full`은 쓸 수 없다** (검사 오류 B12). 아무것도 확인하지 않고 답만 복사하는 꼴이다. 캐시가 필요하면 그것은 재생이 아니라 다른 기능이다.
3. **재생 명세는 패키지 안 `memory/specs.json`**이고 배포된 Bot은 **읽기만** 한다. 열쇠는 `(BPM 프로세스 정의 id, 노드 id)` — 노드마다 하나다. 같은 노드가 한 실행에서 여러 번 돌아도 같은 명세를 쓴다 (BX-37).
4. **도구 인자는 값이 아니라 `{변수}` 템플릿으로 적는다.** 기록할 때 인자 값이 그 시점 프로세스 변수의 값과 **그대로 같으면** 이름으로 바꿔 둔다. 그래야 입력이 달라져도 같은 명세가 맞고, 「달라지는 값은 입력으로 받아라」는 예제의 교훈이 실제로 지켜진다. 템플릿 모양은 C14 기본 규칙 7과 같다.
5. **명세가 없으면 그냥 돈다** (모델을 부른다). 없다고 실패시키지 않는다 — 처음 배포한 Bot이 멈추면 안 된다.
6. **재생이 깨지면 몰래 자율로 넘어가지 않는다** (ADR-0010). 기억에 적힌 도구가 이 PC에 없거나 도구가 실패하면 `TaskFailed`로 올려 **오류 경계가 받게** 한다 (BX-36이 바라는 그대로).
7. 재생한 노드는 C3 `node_state: replayed`로 남는다 (`run_finished.replayed_tasks`가 센다).

## 결과

- **쉬워지는 것:** 운영 실행이 **싸고 같은 결과**가 된다 (`full`은 모델 0회). 「이 Bot이 무엇을 재생하는가」를 배포 전에 파일 하나로 볼 수 있고 서명에 들어간다. 재생이 맞지 않는 상황이 **흐름으로** 드러난다 (오류 경계 → 사람).
- **포기하는 것:** 현장에서 스스로 학습해 고쳐지지 않는다. 화면·서식이 바뀌면 Studio에서 다시 자율 수행으로 돌려 명세를 새로 만들고 다시 배포해야 한다. 이것은 의도한 번거로움이다 (운영에서 LLM이 몰래 끼어들지 않는 값).
- **우리가 지는 것:** 인자 템플릿화는 **어림**이다 — 인자 값이 어쩌다 어떤 변수 값과 같으면 잘못 묶일 수 있다. 그래서 문자열이 **그대로 같을 때만** 바꾸고, 짧은 값(2자 이하)·참거짓·수는 바꾸지 않는다.
- **다시 볼 조건:** ① 현장 적응이 꼭 필요해지면 (그때는 「현장에서 모은 후보를 Studio로 올려 사람이 승인」이지, 운영 PC가 스스로 덮어쓰는 것이 아니다), ② 같은 노드가 입력 종류에 따라 **다른 도구 차례**를 써야 하면 (명세를 노드마다 하나에서 `(노드, 갈래)`로 늘린다), ③ UI 태스크(M4)의 재생과 모양이 갈라지면 둘을 맞춘다.
