# ADR-0012. 현장 PC의 프로그램은 Bot UI 하나: Bot 실행, Worker 실행 관리, UI 셀렉터 등록

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-01) · 실행기 제안(여러 Bot 동시 실행)은 대체됨(ADR-0014) · ③ UI 셀렉터 등록과 ② Worker 관리는 UI 자동화 확장의 기여로 바뀜(ADR-0018) |
| 날짜 | 2026-10-01 |
| 대체 | ADR-0009 전체, ADR-0008의 역할 이름(실행·손) |
| 관련 | `docs/02-glossary.md`, `docs/01-architecture.md`, 계약 C4·C10, 스파이크 S4, 화면 `docs/06-screens/bot-ui.md` |

## 배경

ADR-0008·0009에서는 "Bot = BPM 프로세스를 실행하는 프로그램", "Worker = 미리 떠 있는 별도 트레이 앱"으로 정했다. 검토에서 두 가지 문제가 드러났다.

1. **"프로세스"와 "화면(프로그램)"이 섞였다.** "Bot"이 실행되는 업무(BPM 프로세스)인지, 그것을 돌리는 프로그램인지 헷갈린다. "Worker"도 트레이 앱(화면)인지 서버(프로세스)인지 모호하다.
2. 현장 PC 사용자에게 **트레이 앱이 둘**(Bot, Worker)이면 운영이 번거롭다.

## 결정

현장 PC(그리고 설계자 PC)에는 **화면 있는 프로그램이 Bot UI 하나**뿐이다. 나머지는 화면 없는 프로세스다.

| 이름 | 종류 | 뜻 |
| --- | --- | --- |
| **Bot UI** | 화면 (트레이 기반 GUI 프로그램) | 항상 떠 있다. PC 한 대에 하나. Center에 등록되는 단위 |
| **Bot** | 업무 (= BPM 프로세스) | Center에서 Bot UI로 전달되어 실행되는 BPM 프로세스. 운영 화면(Center 콘솔, Bot UI)에서는 "Bot", 설계 화면(Studio)에서는 "BPM 프로세스"라 부른다. 같은 것이다 |
| **Worker** | 프로세스 (화면 없음, 서버) | 127.0.0.1의 REST API 서버. Bot UI가 시작·감시·재시작·종료한다. 실행 중인 Bot이 UI 자동화를 REST로 요청한다 |

### Bot UI가 하는 일

1. **Bot 다운로드 및 실행** — Center에서 배포된 Bot(BPM 프로세스)을 받아 설치하고, 작업 지시·감시 모드·수동 실행으로 실행한다.
2. **Worker 실행 관리** — Worker 서버 프로세스를 띄우고, 상태를 확인하고, 죽으면 다시 띄운다. 포트·로그를 관리한다.
3. **유틸리티: UI 셀렉터 등록 관리** — 자동화할 화면의 요소를 등록·검증·삭제한다 (예전 Worker 화면 등록 GUI). 브라우저 조작은 Worker API를 통해 한다 (브라우저를 다루는 주체는 Worker 하나).

### 호출 관계

```
Bot UI (화면, 트레이)
 ├─ 실행 ─▶ Bot = BPM 프로세스 (실행 중)
 │            ├─ AI 태스크        → AI
 │            ├─ UI 태스크        → Worker (REST, 127.0.0.1)
 │            ├─ 서비스 앱 태스크  → 서비스 앱 (REST, API 키)
 │            └─ 결재              → Center
 ├─ 시작·감시 ─▶ Worker (서버 프로세스)
 └─ 유틸리티: UI 셀렉터 등록 ─▶ Worker API + UI 자동화 앱
Center ─(하트비트 응답으로 배포·작업)─▶ Bot UI
```

- Bot(BPM 프로세스)은 Worker를 띄우지 않는다. Worker의 기동·종료는 Bot UI의 일이다.
- Studio의 개발 실행(자율 수행)도 같은 PC의 Bot UI가 관리하는 Worker에 요청한다. 그래서 설계자 PC에도 Bot UI를 설치한다.
- > 제안: Bot 실행은 실행마다 Bot UI의 **자식 프로세스(실행기)** 로 돌린다. Bot 하나가 멈추거나 죽어도 Bot UI와 다른 Bot은 산다. S4 스파이크에서 확정한다.

### 역할 경계 (ADR-0008 갱신)

| 역할 | 담당 |
| --- | --- |
| 지도 | BPMN (BPM 프로세스 정의) |
| 운전사 | AI |
| 실행 | Bot UI가 Bot(BPM 프로세스)을 실행한다 (개발 중에는 Studio) |
| 손 | Worker (실행 중인 Bot이 REST로 요청) |

### 용어 규칙: 프로세스와 화면을 구별한다

- 업무 흐름은 항상 **"BPM 프로세스"** (또는 운영 화면에서 "Bot"). "프로세스"를 단독으로 쓰지 않는다.
- 프로그램이 도는 단위(OS 프로세스)는 **"<이름> 프로세스"** 로 쓴다: Worker 프로세스, 실행기 프로세스.
- 사람이 보는 프로그램은 **"UI"** 를 붙이거나 앱 이름으로 쓴다: Bot UI, Studio, Center 콘솔.

## 결과

- 쉬워지는 것: 현장 PC 사용자는 트레이 하나만 본다. Worker 상태가 Bot UI에서 관리된다. "Bot"이 무엇인지(업무)와 "Bot UI"가 무엇인지(프로그램)가 분명하다.
- 어려워지는 것: Bot UI가 자식 프로세스(Worker, 실행기)의 수명 관리를 Windows·Linux 양쪽에서 해야 한다. 셀렉터 등록 중 Bot 실행과 브라우저가 겹치지 않게 Worker가 세션을 나눠야 한다.
- 다시 볼 조건: S4에서 Windows 잠금 화면·로그오프 환경의 자식 프로세스 관리가 과하게 복잡하면, Bot 실행을 Bot UI 프로세스 안으로 넣는 방안을 다시 본다.
