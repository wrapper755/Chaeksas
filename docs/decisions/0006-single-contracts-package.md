# ADR-0006. 계약은 패키지 하나, 스키마 버전 정수

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-01) |
| 날짜 | 2026-10-01 |
| 관련 | `docs/03-contracts/README.md` |

## 배경

프로토타입의 계약 관리는 두 방식이었다.
- 프로토타입 Studio·Bot ↔ Center: 계약 패키지를 git 태그로 공유했다. 패키지 버전(1.2.0)과 태그(v1.3)와 코드 내용(v1.4 `llm_usage`)이 서로 어긋났다.
- 프로토타입 UI 자동화 서버 ↔ Worker: 서버가 Worker 계약을 손으로 복사하고 AST 드리프트 테스트로 맞췄다. 버전 필드가 없었고, 문서마다 어느 쪽이 원본인지 다르게 적혀 있었다.

## 결정

- `packages/contracts/` 하나가 모든 구성요소 간 모델의 원본이다. 서버·클라이언트 모두 import한다.
- 계약(메시지 종류)마다 `schema: int`를 둔다. 필드 추가는 같은 번호, 변경·삭제는 번호 증가.
- 받는 쪽은 모르는 이벤트 종류·선택 필드를 거부하지 않는다 (프로토타입 계약 v1.3의 교훈).
- 모델에서 JSON Schema를 생성해 문서에 링크한다.
- 계약 문서(`docs/03-contracts/C*.md`)의 예시 요청·응답은 테스트로 검증한다. 문서와 코드가 어긋나지 않게 하려는 것이다.

## 결과

- 쉬워지는 것: 복사본·태그·드리프트 테스트가 필요 없음.
- 어려워지는 것: 현장 PC에 옛 버전 Bot이 남아 있을 때의 호환은 여전히 `schema` 규칙으로 지켜야 함.
- 다시 볼 조건: Python 외 언어 클라이언트가 생기면 JSON Schema를 원본으로 올리는 것을 검토.
