# ADR-0010. BPM 프로세스가 호출하는 서버 앱은 "서비스 앱"으로 통일한다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-01) · §3 인증과 §4-7의 키 목록 동기화는 대체됨([ADR-0013](0013-api-keys.md)) · 서비스 앱은 확장의 서버 부분으로 넓혀짐([ADR-0018](0018-extensions.md)) |
| 날짜 | 2026-10-01 |
| 관련 | `docs/02-glossary.md` §1·§2, `docs/01-architecture.md`, 계약 C7·C11, 화면 CON-07·CON-11 |

## 배경

BPM 프로세스의 ServiceTask는 서버의 API를 호출해 일을 맡긴다. 첫 번째 대상은 UI 자동화(화면·로케이터 레지스트리, 계획, 치유)다. 앞으로 업무용(문서 이해, 사내 시스템 조회 등)과 시스템용 서버가 계속 늘어난다. 이 서버들은 대부분 LLM 앱 형태로 동작한다.

하나씩 따로 만들면 프로토타입에서 겪은 문제가 반복된다: 서버마다 다른 인증, 다른 포트 관리, 다른 상태 확인 방식, Center가 그 존재를 모름.

또 같은 서비스 앱이라도 **누가 어떤 목적으로 부르는가**에 따라 동작이 다르다. UI 자동화만 해도:
- Studio에서 개발 목적으로 프로세스를 실행할 때는 LLM이 방법을 찾는다 (계획 세우기, 탐색, 치유 제안).
- Bot에서 운영 실행할 때는 정해진 대로 결정적으로 수행한다 (등록된 스텝, 캐시된 계획).

## 선택지 (분류 이름)

| 이름 | 장점 | 단점 |
| --- | --- | --- |
| **서비스 앱** (Service App) | "앱"이 계속 늘어나는 느낌과 맞음. LLM 여부와 무관 | "서비스"가 흔한 말 |
| LLM 앱 | 지금의 첫 사례와 맞음 | LLM을 안 쓰는 앱이 생기면 틀린 이름 |
| 스킬 서버 | 짧음 | 에이전트의 도구(스킬)와 헷갈림 |

## 결정

**분류 이름은 "서비스 앱"**, 코드는 `service_app`. 첫 번째 앱은 **"UI 자동화 앱"**, id `ui-automation`.

### 1. 이름 규칙

| 항목 | 규칙 | 예 |
| --- | --- | --- |
| 앱 id | 소문자 kebab, 하는 일을 이름으로 | `ui-automation`, `doc-reader`, `erp-lookup` |
| 화면 표기 | "<하는 일> 앱" | UI 자동화 앱, 문서 판독 앱 |
| 저장소 위치 | `services/<id의 밑줄 형태>/` | `services/ui_automation/` |
| 파이썬 패키지 | `chaeksas_svc_<id 밑줄>` | `chaeksas_svc_ui_automation` |
| 구분 | `business`(업무) / `system`(시스템) | UI 자동화 앱 = `system` |

### 2. 수행 모드: 자율 수행 / 결정 수행

모든 서비스 앱 호출은 **수행 모드**를 가진다.

| 모드 | 코드 | 언제 | 하는 일 | LLM |
| --- | --- | --- | --- | --- |
| 자율 수행 | `autonomous` | Studio에서 개발 목적으로 프로세스 실행 | 방법을 찾고, 결과를 학습 자료로 남긴다 (예: UI 자동화 → 계획 세우기·치유 제안·인텐트 저장) | 씀 |
| 결정 수행 | `deterministic` | Bot에서 운영 실행 (Studio의 재생 실행 포함) | 학습·등록된 대로 수행한다 (예: UI 자동화 → 등록 스텝·캐시 계획만) | 쓰지 않거나 최소 (값 추출 등) |

- 작업마다 manifest에 지원하는 모드를 적는다. 지원하지 않는 모드로 부르면 422와 이유를 돌려준다.
- 결정 수행이 실패했을 때 자율 수행으로 넘어갈지(폴백)는 앱·작업별 정책으로 manifest에 둔다. 기본값은 **넘어가지 않고 실패** — 운영에서 LLM이 몰래 개입하지 않게 한다.
- 수행 모드는 AI 태스크·UI 태스크에도 같은 뜻으로 쓴다 (`docs/02-glossary.md`).

### 3. 인증: API 키

서비스 앱은 LLM 앱 API처럼 **API 키**로 인증한다.

- 호출자마다 키 하나: Studio 사용자, 각 Bot, 각 Worker. 키에는 이름·허용 앱·허용 모드(자율/결정)·만료가 붙는다.
- 전송: `Authorization: Bearer <API 키>`.
- 발급·폐기는 Center 콘솔(CON-11)에서 한다. 키 원문은 발급할 때 한 번만 보인다.
- 서비스 앱은 Center에서 키 목록(해시와 권한)을 주기적으로 받아 **로컬에서 검증**한다. 호출할 때마다 Center를 거치지 않는다 (Center가 잠시 꺼져도 서비스 앱은 동작).
- 키는 호출자 PC의 OS 비밀 저장소에 둔다. 설정 파일·실행 기록에 넣지 않는다.
- > 제안: Bot의 키는 Center 등록 때 자동 발급해 하트비트로 전달한다 (사람이 키를 옮기지 않게). Studio·Worker는 사용자가 콘솔에서 발급받아 설정에 넣는다.
- 기본 정책: Bot 키는 결정 수행만, Studio 키는 두 모드 모두.

### 4. 모든 서비스 앱이 지키는 공통 규칙 (계약 C11)

1. `GET /healthz` — 살아 있는지 (인증 없음).
2. `GET /manifest` — 앱 id, 버전, 구분, 제공하는 **작업(operation)** 목록과 각 작업의 입력·출력 JSON Schema, 지원 수행 모드, 폴백 정책.
3. `POST /v1/ops/{operation}` — 작업 호출. 본문에 `mode`(자율/결정), `run_id`, `node_id`, 입력. 입력·출력은 manifest 스키마를 따른다.
4. 인증은 위 API 키 하나. 앱마다 새로 발명하지 않는다.
5. 기본 포트를 갖고, 설정으로 바꿀 수 있다 ([ADR-0011](0011-config-ports-env.md)).
6. Center의 리소스 목록에 등록된다. Studio는 이 목록에서 앱과 작업을 골라 서비스 앱 태스크를 만든다.
7. 공통 뼈대(API 키 검증·healthz·manifest·로깅·설정)는 `packages/service_kit/`로 제공한다. 새 앱은 작업 구현만 쓴다.

### 5. UI 자동화 앱의 특수성

UI 자동화 앱의 작업(계획·치유·보고·화면 등록)은 프로세스가 직접 부르지 않고 **Worker가 Bot·Studio를 대신해** 부른다. 화면 조작이 현장 PC에서 일어나야 하기 때문이다. Worker는 요청받은 수행 모드를 그대로 전달한다. 그 밖의 서비스 앱은 Bot·Studio가 서비스 앱 태스크에서 직접 부른다.

## 결과

- 쉬워지는 것: 새 서비스 앱을 추가할 때 인증·포트·상태 확인·Center 등록·Studio 편집 화면이 이미 있다. 운영 실행에서 LLM 사용이 모드로 통제된다.
- 어려워지는 것: 공통 계약(C11), `service_kit`, Center의 API 키 관리(CON-11)를 먼저 만들어야 한다. 키 목록 동기화 주기만큼 폐기가 늦게 반영된다.
- 다시 볼 조건: 서비스 앱 중 일부가 Python이 아닌 언어로 만들어지면, C11을 HTTP 명세(OpenAPI)로만 강제하고 `service_kit`은 선택으로 둔다. 키 폐기의 즉시 반영이 필요해지면 동기화 대신 Center 조회(캐시 포함)로 바꾼다.
