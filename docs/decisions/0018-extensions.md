# ADR-0018. 확장(Extension): BPM 프로세스의 공통 기능은 확장으로 붙인다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-01, 독립 검토 반영). §5 사내 확장의 코드 배포(서명된 확장 패키지)는 **제안** |
| 날짜 | 2026-10-01 |
| 대체 | ADR-0010의 "서비스 앱 = 플랫폼의 한 구성요소" 관점을 넓힌다 (서비스 앱 = 확장의 서버 부분). ADR-0012의 Bot UI ③ "UI 셀렉터 등록"은 Bot UI 고유 기능이 아니라 **UI 자동화 확장이 기여하는 유틸리티**가 된다. 저장소 구성(ADR-0004·0017)의 `services/`, `apps/worker/` 위치 |
| 관련 | 계약 [C13](../03-contracts/C13-extension-manifest.md), C1·C7·C8·C9·C10·C11, 화면 BUI-01·02·06~11, STU-03·13·15, CON-07 |

## 배경

UI 자동화 앱은 BPM 프로세스가 쓰는 **공통 기능 하나**다. 지금까지는 이 앱이 플랫폼 안에 박힌 구성요소처럼 그려졌다. 예를 들면 다음과 같다.

- Worker는 `apps/worker`에, UI 자동화 앱은 `services/ui_automation`에 있었다.
- 셀렉터 등록은 Bot UI 고유 기능이었다.
- UI 태스크는 핵심 엔진이 직접 알았다.

실제로는 다음과 같다.

1. **같은 저장소에 없는 LLM 앱을 써야 하는 경우가 많다.** 사외 서비스나 다른 팀이 만든 앱처럼 우리 계약(C11)을 따르지 않는 앱도 있다.
2. **사내에서도 UI 자동화 같은 공통 기능이 계속 늘어난다.** 문서 인식, 메일 분류 같은 것들이다.
3. 그래서 플랫폼은 **확장을 받아들이는 틀**이어야 한다. VS Code가 확장으로 언어·명령·화면을 더하듯이, 확장이 BPM 프로세스에 태스크 종류·작업·화면·도구를 더한다.

## 결정

### 1. 확장이란

**확장 = BPM 프로세스에 공통 기능을 더하는 묶음.** 확장 정의(C13 `extension.json`) 하나가 무엇을 더하는지(**기여**)를 선언한다. 플랫폼(Studio, Bot UI, 실행기, 서버 실행기, Center, 콘솔)은 **특정 확장을 모른다.** 확장 정의를 읽어 기여 지점에 끼워 넣을 뿐이다.

- **서비스 앱은 확장의 서버 부분이다.** BPM 프로세스가 API로 부르는 서버 앱이라는 뜻은 그대로다 (ADR-0010).
- 확장은 서버 부분 없이 클라이언트 기여만 가질 수도 있고 (예: 사내 장비 연동 도구), 서버 부분만 가질 수도 있다 (외부 앱).
- 확장마다 상태와 버전을 Center 리소스 목록에서 본다.

### 2. 기여 지점 (contribution points)

| 기여 지점 | 붙는 곳 | 형태 | UI 자동화 확장의 예 |
| --- | --- | --- | --- |
| `operations` | 서비스 앱 작업 (서비스 앱 태스크 STU-14) | C11 manifest, 또는 HTTP 어댑터(§4) | `plan`, `heal`, `report`, `registry_*` |
| `task_types` | Studio 팔레트·속성 편집기, 실행기의 태스크 수행 | 선언 + 수행 코드 | `ui_task` (UI 태스크) |
| `studio.editors` | Studio 속성 패널의 태스크 편집기 | 코드, 또는 JSON Schema 자동 폼 | STU-13 UI 태스크 편집기 |
| `studio.resource_views` | Studio 리소스 탐색기(STU-03)의 한 갈래 | 선언 (Center 리소스 종류를 가리킴) | 「UI 화면」 |
| `bot_ui.utilities` | Bot UI 「도구」 메뉴·탭 | 코드 | 「UI 셀렉터 등록」 (BUI-06~08) |
| `bot_ui.local_runtimes` | Bot UI가 띄우고 감시하는 로컬 프로세스 | 선언 (실행 명령·포트 설정·상태 확인) | Worker 프로세스 |
| `preflight` | 사전 점검 | 코드 | 「쓰는 화면이 레지스트리에 있나」 |
| `console.pages` | 그 서비스 앱의 관리 콘솔 고유 화면 | 웹 모듈 | UIA-01~03 |
| `resources` | Center 리소스 목록(C7)에 올릴 것 | 선언 (공개 카탈로그 주소) | 「UI 화면」 카탈로그 (C9 `/v1/catalog`) |

- **활성화:** 기여는 필요할 때만 켠다 (VS Code의 활성화 이벤트와 같다).
  - Worker(로컬 런타임)는 설치된 Bot 중 UI 자동화 확장을 요구하는 것이 있거나, 「UI 셀렉터 등록」을 열었을 때 띄운다.
  - 「항상 실행」 설정도 둔다 (BUI-11).

### 3. 확장 등급 셋

| 등급 | 코드 위치 | 클라이언트 코드 기여 | 서버 부분 | 예 |
| --- | --- | --- | --- | --- |
| **내장 확장** | 이 저장소 `extensions/<id>/` | 가능. 설치 파일에 함께 들어간다 | C11 서비스 앱 (`service_kit`) | UI 자동화 |
| **사내 확장** | 다른 저장소 | 처음에는 **설치 파일 빌드에 포함할 때만** 가능 (§5) | C11 서비스 앱 | 문서 인식, 메일 분류 |
| **외부 확장** | 없음 (확장 정의 파일만) | **불가.** 선언만 (자동 폼, 리소스 보기) | 외부 앱 + **HTTP 어댑터** | 사외 OCR API, 다른 팀의 LLM 앱 |

- 클라이언트 코드(Studio·Bot UI·실행기 안에서 도는 코드)는 현장 PC에서 업무 화면과 비밀에 닿는다. 그래서 **우리가 빌드·서명한 설치 파일에 든 것만** 돌린다. 실행 중에 내려받은 코드는 돌리지 않는다.
- 외부 확장은 코드 없이 선언만으로 쓴다.
  - 작업은 서비스 앱 태스크(STU-14)로 부른다. 입력·출력 칸은 JSON Schema 자동 폼이다.
  - 키는 다른 서비스 앱과 똑같이 BPM 프로세스의 키 참조로 지정한다 (ADR-0013). 값은 그 앱의 콘솔에서 발급받아 Bot UI·Studio·서버 실행기에 둔다.

### 4. 외부 앱 연결: HTTP 어댑터 (선언형)

C11을 따르지 않는 외부 앱은 확장 정의 안의 **HTTP 어댑터**로 붙인다 (C13 §4).

- **외부 확장 정의는 Admin 서명(C2 `extension`)을 받아야 쓰인다.** 정의가 서비스 앱 키와 업무 값을 어느 주소로 보낼지 정하므로, 배포와 같은 관문을 둔다. 실행하는 쪽은 서명을 다시 검증하고, BPM 프로세스 매니페스트는 정의 해시를 고정한다.

- 어댑터는 작업마다 다음을 **템플릿으로만** 적는다.
  - 요청: 메서드, 경로, 헤더, 본문
  - 인증: 어느 헤더에 키 참조의 값을 넣나
  - 응답: 어디서 출력 필드를 꺼내나
- 코드는 쓰지 않는다. 실행하는 쪽(실행기·서버 실행기·Studio)의 공통 호출기(`core`)가 해석한다.
- **안전장치** (자세히는 C13 §4):
  - https만 쓰고, 리다이렉트를 따라가지 않는다.
  - 허용 호스트 목록에 있는 주소만 부르고, 사설망·루프백은 막는다 (DNS를 한 번 풀고 그 IP로 접속).
  - 입력값은 위치별로 인코딩하고, 템플릿에서는 입력·실행 id만 쓸 수 있다. 키는 템플릿에 넣을 수 없다.
  - 응답은 읽는 동안 크기 상한을 넘으면 끊는다.
- 외부 앱이 멱등(같은 호출을 두 번 해도 한 번만 처리)을 보장하지 못하면 `idempotent: false`로 선언한다. 그러면 시간 초과 같은 "결과를 모르는" 실패 때 자동으로 다시 부르지 않는다.
  - PC는 확인(`confirmation`)으로 넘긴다.
  - 서버는 실행 실패나 오류 경계 이벤트로 보낸다.
- 수행 모드: 외부 앱에는 모드 개념이 없다. 확장 정의가 작업마다 허용 모드를 선언하고, **기본값은 자율 수행만**이다. 결정 수행에서 부르려면 정의에 명시하고 서명받아야 한다.
  - 결정 수행은 **우리 쪽에서 LLM이 계획·판단하지 않는다**는 뜻이다. 작업 자체가 LLM 호출인 것은 manifest에 드러나 있으므로 결정 수행에서도 부를 수 있다.
- 네트워크: 외부 앱은 현장 PC에서 닿지 않을 수 있다.
  - Studio 사전 점검이 「이 작업은 PC에서 닿지 못할 수 있습니다 — 실행 위치를 서버로 두세요」를 경고한다.
  - 서버 우선 원칙(ADR-0016)과도 맞다.
- 더 복잡한 연동(여러 번 호출, 상태 유지)은 어댑터로 하지 않는다. C11을 따르는 **사내 확장 서비스 앱(감싸는 앱)** 을 만든다.

### 5. 사내 확장의 클라이언트 코드 배포 (제안)

- **첫 릴리스:** 사내 확장의 클라이언트 코드는 Studio·Bot UI 설치 파일을 빌드할 때 포함 목록(`installer/extensions.toml`)으로 넣는다. 사내 확장의 서버 부분은 독립 배포한다.
- **나중 (별도 ADR):** Admin 서명(C2에 `extension` claim 추가)된 확장 패키지를 Center에서 배포해, 설치 파일을 다시 만들지 않고 붙인다.

### 6. 코드 구조 (확장이 코드에 드러나게)

```
Chaeksas/
├─ packages/
│  ├─ contracts/          # 플랫폼 계약 (C1~C7, C11~C13)
│  ├─ extension_api/      # 확장이 구현하는 안정 인터페이스 (신규)
│  │                      #   TaskType, TaskExecutor, StudioEditor, BotUiUtility,
│  │                      #   LocalRuntime, PreflightCheck, HttpAdapter 해석기 규격
│  ├─ core/               # 실행 엔진 + 확장 호스트 (확장을 찾아 기여를 등록)
│  ├─ qt/                 # 공용 위젯 (확장의 화면도 이것으로)
│  └─ service_kit/        # C11 서비스 앱 뼈대 (내장·사내 확장의 서버 부분)
├─ extensions/            # 내장 확장 (신규, 확장 하나 = 폴더 하나)
│  └─ ui_automation/
│     ├─ extension.json   # 확장 정의 (C13)
│     ├─ contracts/       # 이 확장의 계약 모델 (C8·C9·C10)
│     ├─ service/         # 서버 부분 = UI 자동화 앱 (service_kit)
│     ├─ worker/          # 로컬 런타임 = Worker 프로세스
│     ├─ client/          # ui_task 수행, Studio 편집기(STU-13), Bot UI 유틸리티(BUI-06~08), 사전 점검
│     └─ console/         # 관리 콘솔 고유 화면 (UIA-01~03, web/apps/svc-console이 불러 씀)
├─ apps/                  # studio, bot_ui, server_runner, center, admin (worker는 확장으로 이동)
└─ web/                   # center-console, svc-console, packages/ui …
```

- **찾기:** 확장은 Python 패키지 엔트리 포인트 그룹 `chaeksas.extensions`로 등록한다. Studio·Bot UI·실행기는 시작할 때 이 그룹을 읽는다. 외부 확장은 Center 리소스 목록(C7)에서 확장 정의만 받는다.
- **의존 방향:**
  - `extension_api`는 `contracts`에만 의존한다.
  - `core`와 `apps/*`는 `extension_api`를 통해서만 확장을 부르고, **특정 확장을 import하지 않는다.**
  - 확장끼리도 import하지 않는다.
  - 이 규칙은 import 검사 테스트로 강제한다.
- **확장 하나의 계약은 그 확장 폴더에 둔다** (C8·C9·C10 → `extensions/ui_automation/contracts/`). 계약 문서는 계속 `docs/03-contracts/`에 둔다 (찾기 쉽게).
- 웹: `svc-console`은 확장의 `console.pages`를 확장 id별 모듈로 불러 쓴다 (`web/apps/svc-console/extensions/<id>` → 빌드 때 `extensions/<id>/console`을 연결).

## 결과

- **쉬워지는 것:**
  - 새 공통 기능을 플랫폼 코드 수정 없이 확장으로 더한다.
  - 외부 앱을 코드 없이 정의 파일로 붙인다.
  - UI 자동화가 "특별한 구성요소"가 아니라 첫 번째 내장 확장이 되어, 같은 틀을 다른 확장이 따라 쓴다.
- **어려워지는 것:**
  - `extension_api`를 안정적으로 유지해야 한다 (버전 범위 `api`를 확장 정의에 적는다).
  - 설치 파일(PyInstaller 등)에 엔트리 포인트 기반 확장이 제대로 들어가는지 확인해야 한다 → **스파이크 S5** 추가.
  - HTTP 어댑터 해석기는 보안 검토가 필요하다.
- **다시 볼 조건:**
  - 사내 확장이 늘어 설치 파일 재빌드가 병목이 되면 §5 "나중"을 ADR로 연다.
  - 외부 앱 연동이 어댑터로 감당되지 않는 경우가 많아지면, 감싸는 앱을 만드는 템플릿을 `service_kit`에 더한다.
