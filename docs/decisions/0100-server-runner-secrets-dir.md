# ADR-0100. 컨테이너의 서버 실행기는 **비밀 폴더**에 받은 키를 둔다 — 운영자가 자리를 적을 때만

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-10-26 |
| 관련 | 계약 C12 §등록 요청과 승인(이 ADR이 「미정: 컨테이너에서도 승인으로 들이려면…」을 닫는다), [ADR-0092](0092-keys-are-issued-and-delivered-by-center.md), [ADR-0094](0094-service-app-keys-ride-the-deployment.md), [ADR-0054](0054-server-run-state-and-concurrency.md), `deploy/compose.yaml` |

## 배경

`deploy/compose.yaml`은 Center만 띄우고 서버 실행기를 띄우지 않았다. 그래서 「Center를 띄웠는데 서버 Bot이 돌지 않는」 상태가 기본이었고, 바깥(NowView) 시연에서는 실행기를 손으로 띄워야 했다.

compose에 넣으려니 키가 걸린다. 실행기는 받은 Center API 키와 등록 키 쌍의 비밀 반쪽을 **OS 비밀 저장소**에 두는데(ADR-0092), 컨테이너에는 그것이 없다. 그러면 남는 길은 환경변수 키(`CHK_SERVER_RUNNER__CENTER_API_KEY`)뿐이고, 그 길에는 공개키가 없어 **Center가 서비스 앱 키를 봉해 내려 줄 수 없다**(ADR-0094 — 「공개키 없는 곳은 환경변수로만 받는다」). 앱 키마다 `CHK_SERVER_RUNNER__SVC__<참조>`를 손으로 넣어야 하고, 빠뜨리면 사전 점검이 Bot을 `not_ready`로 막는다 — 시연에서 실제로 그렇게 막혔다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 환경변수 키만, 문서로 적는다 | 코드가 그대로다 | 관리자 토큰으로 키를 따로 발급해야 하고 서비스 앱 키를 모두 손으로 넣는다. 키 회전·배포가 데려가는 키(ADR-0094)가 컨테이너에서만 돌지 않는다 |
| B. 실행기가 키 쌍을 메모리에만 두고 뜰 때마다 새로 등록 | 디스크에 비밀이 없다 | 다시 뜰 때마다 승인을 새로 받아야 한다. Center는 앱 키 원문을 봉하고 버리므로 새 공개키로 다시 봉할 수 없다 |
| C. **운영자가 적은 비밀 폴더**(볼륨)에 파일 하나로 둔다 | 승인·회전·서비스 앱 키 받기가 PC·개발 서버와 **같은 코드로** 돈다. 부르는 쪽이 바뀌지 않는다 | 비밀이 디스크의 파일이다 — 지키는 것은 파일 권한과 볼륨이다 |

## 결정

**C.** 환경변수 `CHK_SERVER_RUNNER__SECRETS_DIR`가 있으면 실행기의 비밀 창고(`credentials.Credentials`)가 OS 비밀 저장소 대신 그 폴더의 `secrets.json`을 쓴다 (`server_runner/secret_file.py`).

1. **적을 때만 켜진다.** 없으면 지금과 같다 — OS 비밀 저장소, 그것도 없으면 등록 요청을 보내지 않고 끝 코드 2. 「몰래 평문으로 흘리지 않는다」(CLAUDE.md §5)는 그대로이고 이것은 **사람이 자리를 정해 준 경우**다. 적었으면 OS 저장소가 있어도 그 폴더가 이긴다(적었는데 볼륨 밖에 남으면 다시 만든 컨테이너가 잃는다).
2. 폴더 0700·파일 0600, 쓰기는 0600 임시 파일을 바꿔 끼운다. **깨진 파일은 덮지 않고 멈춘다** — 받은 키를 조용히 잃으면 다시 승인해야 한다.
3. 들어가는 것은 OS 저장소에 들어가던 것 그대로다 — Center API 키, 등록 키 쌍의 비밀 반쪽, 배포가 데려온 서비스 앱 키(`svc:<Bot>:<참조>`). 환경변수 키·앱 키는 여전히 이긴다(CI·자동화).
4. **compose는 데이터와 비밀을 볼륨 둘로 가른다** (`server-runner-data` → `/data`, `server-runner-secrets` → `/secrets`) — 데이터(배포·실행 기록·기다리는 실행 `state.sqlite3`)를 백업·복사해도 키가 따라 나가지 않는다. 이미지(`deploy/Dockerfile.server-runner`)가 두 자리를 환경변수로 정해 두므로 compose에 따로 적지 않는다.
5. 기계 id는 데이터 볼륨에 둔다 — 이미지가 `/etc/machine-id`를 지운다. 그래야 같은 이미지로 뜬 실행기 둘이 같은 id로 409를 받지 않고, 컨테이너를 다시 만들어도 같은 실행기로 이어진다.

Bot UI·Studio는 바꾸지 않는다 — 둘은 PC에서 돌고 OS 비밀 저장소가 있다.

## 결과

- 쉬워지는 것: `docker compose up` 한 번 뒤 콘솔 CON-12 「승인 대기」에서 승인하면 끝이다. 서비스 앱 키는 배포가 데려온다(ADR-0094). 다시 띄워도 키·기다리는 실행이 볼륨에서 이어진다.
- 포기하는 것: 컨테이너의 키는 OS가 지켜 주지 않는다 — 호스트에서 볼륨을 읽을 수 있는 사람은 키를 읽는다. Docker secrets·외부 비밀 관리(Vault 같은 것)는 들이지 않았다.
- 다시 볼 조건: 실행기를 여러 호스트·오케스트레이터(Kubernetes)에 올리게 되면 비밀 관리 쪽 백엔드를 다시 고른다. Center·UI 자동화 앱처럼 다른 서버 구성요소가 같은 자리를 필요로 하면 공유 모듈로 옮긴다.
