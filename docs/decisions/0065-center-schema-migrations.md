# ADR-0065. Center 저장소는 판 번호와 앞으로만 가는 단계로 옮긴다 — 기준선은 얼린다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-17) |
| 날짜 | 2026-10-17 |
| 관련 | 로드맵 M8-B, 계약 C7(「SQLite로 시작, PostgreSQL 호환」), `apps/center/.../storage.py`, ADR-0058(서버 실행기 저장소도 같은 꼴) |

## 배경

Center 저장소는 `CREATE TABLE IF NOT EXISTS` 한 덩이(`SCHEMA`)로 선다. 그 문은 **없는 표를 만들
뿐 이미 만들어진 표를 고치지 않는다** — 그래서 돌던 Center에 열을 더하거나 이름을 바꾸거나
제약을 걸 길이 없다. 그 탓에 빚이 다섯 자리에 쌓였다 (코드 주석이 모두 「옮기기 수단이 없다」고
적어 두었다):

- `deployment_results.bot_ui_id` — 실제로는 PC(`bui_…`)와 서버 실행기(`srv_…`)를 함께 담는데
  **이름을 고치지 못해** 부르는 쪽이 `host_id`라고 바꿔 부른다.
- `bot_uis`·`server_runners`의 `key_id`·`machine_id` — 하나씩이어야 하는데(C4 「키 묶기」)
  **UNIQUE를 걸지 못해** 코드(`host_keys.py`)만 지킨다.
- `extension_health`·`delegations` — 기존 표에 열을 더하지 못해 **표를 따로** 팠다.
- CON-06 「다운로드 수」 — 셀 열을 더하지 못해 **화면에서 뺐다**.

빚은 조각마다 늘어 왔고(셋은 2026-10-14~15에 생겼다) 다음 계약 확장도 같은 벽에 닿는다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. **판 번호 표 + 순서 있는 단계 목록**을 직접 짠다 (표준 라이브러리만) | Center가 이미 `sqlite3`만 쓴다 — 의존이 늘지 않는다. 단계가 **SQL 문 목록**이라 읽기 쉽고 PostgreSQL로도 옮겨진다 | 판 기록·동시 기동·실패 처리를 우리가 지켜야 한다 (시험으로 묶는다) |
| B. Alembic | 널리 쓰인다. 자동 생성 | **SQLAlchemy를 들여야 한다** — Center는 ORM을 쓰지 않고 SQL을 직접 적는다. 자동 생성은 모델이 있어야 뜻이 있다 |
| C. yoyo-migrations 같은 가벼운 도구 | SQL 파일 단위, 의존이 작다 | 우리 SQL은 파이썬 문자열에 있다. 바깥 도구가 판 표 모양·잠금을 정한다 — 서버 실행기·서비스 앱으로 넓힐 때 그 도구의 결을 따라야 한다 |
| D. 지금처럼 **표를 따로 판다** | 아무것도 안 해도 된다 | 이름을 고치거나 제약을 걸 수는 끝내 없다. 빚이 계속 는다 |

## 결정

**A를 쓴다.** `apps/center/.../migrations.py`가 판 번호 표(`schema_migrations`)와 단계 목록
(`MIGRATIONS`)을 쥐고, 저장소가 뜰 때 모자란 단계만 차례로 돌린다.

### 1. 기준선은 얼린다

**오늘의 `SCHEMA`가 1판이다.** 더는 고치지 않는다 — 표를 더하는 것도 단계로 한다. 고치면
「새로 만든 DB」와 「옮겨 온 DB」가 다른 모양이 된다. 그래서 **기준선의 글을 시험이 지킨다**
(바뀌면 「단계로 더하라」고 말하고 깨진다).

판 표가 없는 DB(이 결정 전에 만들어진 것)는 **기준선을 그대로 다시 돌려**(`IF NOT EXISTS` —
오늘 하던 일 그대로다. 그 사이 늘어난 표가 채워진다) 1판으로 적는다. 새 DB도 같은 길이다 —
두 길이 갈라지지 않는다.

### 2. 단계는 앞으로만 간다

- 단계는 `(판, 설명, [SQL 문…])`이고 판은 **2부터 빈틈 없이** 오른다 (시험이 본다).
- **되돌리는 단계는 두지 않는다.** 되돌리기가 필요하면 새 단계로 앞으로 간다.
- **DB 판이 코드가 아는 판보다 높으면 뜨지 않는다** — 옛 Center가 새 DB를 열면 모르는 열·표를
  조용히 깨뜨린다. 사유를 말하고 멈춘다.

### 3. 단계 하나는 트랜잭션 하나다

- 단계의 문들과 **그 판의 기록이 한 트랜잭션**이다 — 중간에 죽으면 둘 다 없던 일이 되고 다음에
  뜰 때 그 단계부터 다시 돈다. SQLite의 DDL은 트랜잭션 안에서 되돌려진다.
- 단계마다 **`BEGIN IMMEDIATE`로 쓰기 잠금을 먼저 잡고 판을 다시 읽는다** — Center 둘이 같은
  DB로 동시에 떠도 한 쪽만 옮기고 다른 쪽은 이미 적힌 판을 보고 지나간다.
- 단계는 **`executescript`로 돌리지 않는다** — 파이썬 `sqlite3`의 `executescript`는 먼저 커밋해
  버려 트랜잭션이 깨진다. 문을 하나씩 `execute`한다. 그래서 단계가 **문 목록**이다.
- **WAL로 바꾸는 것도 동시 기동을 견딘다** — 짜는 중 넷을 동시에 띄우는 시험이 잡았다: WAL로
  바꾸려면 배타 잠금이 필요한데 둘이 같은 순간 바꾸려 들면 SQLite가 **기다리지 않고**
  `database is locked`를 돌려준다(연결의 대기 시간이 듣지 않는다). **이 결정 전의 코드에서도
  같았다.** 이미 WAL이면 바꾸지 않고(읽기는 잠금이 필요 없다) 잠겼으면 잠깐 쉬고 다시 한다.

### 4. PostgreSQL은 막지 않는다 — 옮길지는 아직이다

판 표와 SQL 문 목록은 그대로 옮겨진다. SQLite에만 있는 것은 `BEGIN IMMEDIATE`(PostgreSQL은
`BEGIN` + 잠금)와 기준선의 `executescript` 둘이고 모두 이 모듈 안이다. **전환 여부는 따로
정한다** — 이 결정은 그 길을 닫지 않는 것까지다.

### 5. 첫 단계 — 열 이름을 고친다

2판은 `deployment_results.bot_ui_id` → **`host_id`**다 (`ALTER TABLE … RENAME COLUMN` — SQLite
3.25 이상, PostgreSQL 모두 받는다). 데이터가 든 기존 표를 고치는 일이라 수단을 증명하기 좋고,
부르는 쪽이 이미 `host_id`라고 쓰고 있어 바뀌는 것은 SQL 세 줄이다.

나머지 빚(UNIQUE 둘·「다운로드 수」)은 **이 수단 위에서 따로** 한다 — UNIQUE는 **이미 겹친 행이
있으면 단계가 실패해 Center가 뜨지 않으므로** 겹친 것을 어떻게 다룰지를 먼저 정해야 하고,
「다운로드 수」는 계약(C5)과 화면(CON-06)을 먼저 고치는 일이다.

## 결과

- 쉬워지는 것: 돌던 Center에 열을 더하고, 이름을 고치고, 제약을 걸 수 있다. 「표를 따로 판다」를
  더는 하지 않아도 된다.
- 어려워지는 것: **기준선을 고칠 수 없다** — 모든 바뀜이 단계로 간다. 단계를 지울 수도 없다
  (이미 돈 DB가 있다).
- 포기하는 것: 되돌리는 단계. 잘못 간 단계는 새 단계로 바로잡는다.
- **같은 꼴이 Center 밖에도 있다** — 서버 실행기의 `state.sqlite3`(ADR-0058이 그래서 표를 따로
  팠다)·UI 자동화 앱의 레지스트리. 지금은 **Center만** 옮긴다: 서버 실행기는 `core`를, Center는
  `contracts`만 쓸 수 있어 공유 모듈 자리가 마땅치 않고, 둘 다 아직 고칠 빚이 없다.
- 다시 볼 조건: 다른 저장소에 빚이 생겨 같은 수단이 필요해질 때(그때 **두 벌을 만들지 않고**
  공유 자리를 정한다), PostgreSQL로 옮기기로 할 때, 데이터를 계산해 옮기는 단계가 필요해질 때
  (그때 SQL 말고 함수 단계를 더한다).
