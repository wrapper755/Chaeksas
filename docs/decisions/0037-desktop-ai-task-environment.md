# ADR-0037. 데스크톱 AI 태스크의 눈과 손 — 확장이 「AI 환경」을 기여하고, 도구는 Worker 세션 위에서 돈다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-10-05 |
| 관련 | [ADR-0008](0008-map-driver-hands-boundary.md)(지도·운전사·손), [ADR-0018](0018-extensions.md)(확장), [ADR-0027](0027-llm-connection.md)(도구 루프), [ADR-0028](0028-replay-memory.md)(재생), [ADR-0033](0033-desktop-app-and-window.md)(창 조건), 계약 C10·C13·C14, 예제 FX-05 |

## 배경

`domain: desktop` AI 태스크(FX-05 「계산기를 AI가 보고 조작한다」)는 엔진이 「아직 수행하지 않는다」로 막고 있다. 모델에게 **데스크톱을 보고 조작할 도구**가 없다.

- 화면을 보고 만지는 손은 UI 자동화 확장의 Worker(UIA)에 있다. 엔진(`core`)은 확장을 import할 수 없다 (ADR-0018).
- 이 앱은 **등록되지 않은 화면**이다. 시맨틱 키도 사다리도 없다. UI 태스크(결정적 스텝)와 다른 점이다.
- AI 태스크의 도구는 `chk:aiTask.tools`의 허용 목록이 정한다 (ADR-0027). 그런데 데스크톱의 눈과 손은 그 환경 자체라, 태스크마다 적는 도구가 아니다.
- Bot(결정 수행)은 자율 수행이 남긴 도구 호출을 **되밟는다** (ADR-0028). 그래서 도구 인자는 실행마다 같은 것을 가리켜야 한다.

## 선택지

도구를 누가 주나.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. `core`에 데스크톱 도구를 둔다 | 엔진 혼자 된다 | `core`가 UIA·Worker를 알게 된다 (ADR-0018 위반). 세션 하나 규칙(ADR-0014)을 두 군데서 지킨다 |
| B. **확장이 「AI 환경」을 기여한다** — 그 domain의 도구와 세션 | 손은 지금처럼 Worker 하나다. 엔진은 domain 이름으로 묻기만 한다 (태스크 수행기와 같은 모양) | 기여 지점이 하나 는다 |

도구 인자가 요소를 어떻게 가리키나.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| C. 스냅샷의 일련번호(`e12`) | 모델이 쓰기 쉽다 | 실행마다 바뀐다 — 재생이 깨진다 |
| D. **로케이터 조건**(`automation_id`·`name`·`class_name` + `control_type`) | 실행마다 같다 — 재생된다. 사다리의 데스크톱 전략과 같은 말이다 | 모델이 조건을 골라야 한다 (스냅샷에 조건을 그대로 보인다) |

## 결정

**B + D.**

1. **C13 `agent_environments`:** `[{domain, entry}]`. `entry`는 `extension_api.AgentEnvironment`를 가리킨다. 내장 UI 자동화 확장이 `desktop`을 기여한다 (`web`은 뒤에).
2. **엔진:** `domain`이 `web`·`desktop`인 AI 태스크는 실행하는 쪽(`RunEnv.extensions.environment(domain)`)에게 환경을 묻는다.
   - 없으면 그림·설치 오류다 (`node_kind_unsupported` — 확장 태스크 수행기가 없을 때와 같다).
   - 있으면 **태스크 동안 세션을 하나** 열고, 그 도구를 **허용 목록에 저절로 더해** 모델에게 준다. 도구 루프·결과 검증·재생은 그대로다.
   - 끝나면 성공이든 실패든 세션을 닫는다.
3. **데스크톱 도구 둘** (이름은 예약이다):
   - `desktop_look`: 붙은 창의 UIA 트리를 줄글로 본다 (컨트롤 종류·이름·`aid`·`class`). 입력한 값·표 칸·창 제목은 가린다 (원칙 6, C8과 같은 가리기).
   - `desktop_act`: `target`(로케이터 조건)·`action`(C10 동작)·`value?`로 요소 **하나**를 조작하거나 읽는다.
     - 맞는 것이 하나가 아니면 도구 결과로 「N개가 맞습니다 — 더 좁히세요」를 돌려준다. 모델이 고칠 수 있게 예외로 끝내지 않는다.
     - 고르기·입력 확인 규칙은 UI 태스크와 같다 (ADR-0033).
4. **Worker (C10):**
   - **계획 없는 데스크톱 세션:** `page_id` 없이 `app`만으로 연다. 창 조건은 `desktop-apps.json`의 그 앱 항목 `window`에서 온다. 창이 없으면 그 항목의 `command`로 띄운다.
   - **스텝의 `target`:** 계획 없는 세션에서만 받는다. 그 조건으로 찾아 **정확히 하나**일 때만 조작한다. 사다리·치유·보고는 없다 (등록된 화면이 아니다).
   - **`GET /v1/sessions/{id}/view`:** 가린 트리.
5. **단계 한도:** 화면을 다루는 AI 태스크는 UI 동작 하나가 한 단계라 기본 `max_steps`를 **30**으로 한다 (다른 domain은 8).
   - 정하는 순서는 태스크의 `limits` → `chk:defaults.limits` → 이 기본값이다.
   - `chk:defaults.limits`가 AI 태스크에 가지 않고 있었다 (C14는 「모든 AI·UI 태스크의 기본값」이라고 적었다). 함께 고친다.
   - FX-05(`12*34`)만 해도 보기 1 + 단추 6 + 읽기 1 + 답 1로 9단계다.
6. **수행 모드:** 자율 수행(Studio)은 모델이 도구를 부른다. 결정 수행(Bot)은 남은 도구 호출을 되밟는다 (ADR-0028 — 인자가 로케이터 조건이라 같은 것을 가리킨다). 모델을 몰래 부르지 않는 규칙은 그대로다.

## 결과

- 쉬워지는 것: 엔진은 여전히 확장을 모른다. 데스크톱의 손은 Worker 하나라 세션 하나 규칙·창 안에서만 찾기·잠금 처리·입력 확인이 그대로 적용된다. 웹 AI 태스크도 같은 자리(`agent_environments`의 `web`)에 붙는다.
- 어려워지는 것: 등록되지 않은 앱은 `desktop-apps.json`에 창 조건(`window`)이 있어야 붙는다. 모델이 고른 로케이터 조건이 실행마다 하나에 맞는다는 보장은 없다 — 재생이 깨지면 `TaskFailed`로 올라간다 (ADR-0028, 몰래 자율로 넘어가지 않는다).
- 다시 볼 조건: UIA 트리로는 보이지 않는 앱(그림으로만 그리는 앱) — 화면 캡처를 눈으로 더할지 본다 (ADR-0021).
- 실제 Studio·Bot UI 실행기는 `core.extensions.HostTasks`로 확장 호스트를 꽂는다.
  - Bot UI는 Bot의 `requires.domains`(`desktop`)로 그 환경의 확장을 찾아 Worker를 먼저 띄운다 (그림에 확장을 적지 않아도 된다).
  - Studio는 Bot UI가 띄운 Worker를 `runtime.json`으로 찾는다.
