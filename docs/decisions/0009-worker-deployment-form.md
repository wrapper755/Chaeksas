# ADR-0009. Worker는 미리 떠 있는 트레이 앱이고, Bot의 요청을 받아 수행한다

| 항목 | 값 |
| --- | --- |
| 상태 | 대체됨([ADR-0012](0012-bot-ui.md)) — Worker는 화면 없는 서버 프로세스, Bot UI가 실행 관리 |
| 날짜 | 2026-10-01 |
| 관련 | `docs/02-glossary.md` (Bot과 Worker의 관계), ADR-0007, ADR-0008, 계약 C10, 스파이크 S4, 화면 `docs/06-screens/worker.md` |

## 배경

용어는 확정되었다 (2026-10-01).
- **Bot** = BPM 프로세스를 실행하는 프로그램.
- **Worker** = Bot이 UI 자동화를 위해 사용하는 손. Bot의 요청을 받아 수행한다.

남은 질문은 Worker를 **어떤 형태로 배치하는가**였다. 처음 제안은 "Bot이 필요할 때 Worker를 띄우고 감시"였다. 검토에서 **Worker는 요청을 받는 쪽이므로, 프로토타입처럼 트레이 앱으로 미리 떠 있어야 한다**로 정리했다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 별도 트레이 앱, 미리 실행 (로컬 HTTP로 요청 받음) | 요청을 받는 서버 역할과 맞음. 화면 등록 GUI와 같은 앱. Bot·Studio 어느 쪽 요청도 받음. 프로토타입 Worker에서 검증된 구조 | 사용자가(또는 자동 시작이) Worker를 따로 켜 두어야 함 |
| B. Bot이 자식 프로세스로 띄우고 감시 | 사용자에게 하나로 보임 | Worker GUI(화면 등록)와 실행 Worker가 따로 놀게 됨. Studio 개발 실행 때 누가 띄우는지 모호 |
| C. Bot 안의 라이브러리 | 설치·기동이 하나 | Playwright·Qt 루프가 Bot과 얽힘. Worker 장애가 곧 Bot 장애 |

## 결정

**A. Worker는 독립 트레이 앱으로 미리 실행되어 있고, 요청을 받아 수행한다.**

- Worker는 로그인할 때 자동 시작한다 (Worker 설정). 창을 닫아도 트레이에 남는다.
- 요청은 계약 C10(로컬 HTTP, 127.0.0.1 전용, 로컬 토큰)으로만 받는다. 요청하는 쪽은 **Bot**(결정 수행)과 **Studio**(개발 목적의 자율 수행)다.
- Bot·Studio는 Worker를 띄우거나 끄지 않는다. 요청 전에 Worker 상태(`/health`)를 확인하고, 응답이 없으면:
  - Bot: UI 태스크를 **확인(실행 개입)**으로 넘긴다 — 「Worker가 실행되고 있지 않습니다. Worker를 켠 뒤 계속을 누르세요」. 무인 상황에서는 시한 뒤 실패.
  - Studio: 실행 대화상자에서 미리 알린다 — 「Worker에 연결할 수 없습니다 — Worker를 먼저 실행하세요」.
- Worker 앱 하나에 두 가지가 있다: 요청을 처리하는 **로컬 API**(항상), 사람이 쓰는 **화면 등록·시험 창**(트레이에서 열기).
- `worker` 패키지는 테스트에서 라이브러리처럼 직접 불러 쓸 수 있게 만든다 (HTTP 층은 얇게).

## 결과

- 쉬워지는 것: 역할이 분명하다 (Bot은 요청, Worker는 수행). 화면 등록 담당자와 Bot이 같은 Worker를 쓴다. 장애 격리.
- 어려워지는 것: 현장 PC 설치 시 Bot과 Worker 둘 다 자동 시작을 켜야 한다 → 설치 안내와 Bot 트레이의 Worker 상태 표시로 보완. 같은 Worker에 Bot 요청과 사람의 화면 등록이 겹칠 때의 규칙이 필요하다 (제안: 실행 중에는 화면 등록 창에서 브라우저 조작을 막고 「Bot 요청 처리 중」 표시).
- 다시 볼 조건: 스파이크 S4(Windows 상주·자동 시작·잠금 화면) 결과, 두 트레이 앱 운영이 현장에서 과하게 번거로우면 설치 관리자에서 함께 설치·자동 시작하는 방안을 추가한다.
