# ADR-0015. BPM 프로세스의 실행 위치: PC(Bot UI) 또는 서버(Center)

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-01) — 이름·기본값 숫자·일정은 ADR-0016에서 확정. §1의 기본값(`pc`)은 대체됨(ADR-0016: 기본값 `server`) |
| 날짜 | 2026-10-01 |
| 대체 | 없음 (ADR-0014의 범위를 "실행 위치 = PC"로 좁힌다) |
| 관련 | ADR-0007, ADR-0012, ADR-0013, ADR-0014, 계약 C1·C3·C5·C6·C12, 화면 STU-06·STU-08, CON-02·CON-05·CON-11·CON-12 |

## 배경

지금까지의 설계는 BPM 프로세스가 모두 현장 PC의 Bot UI에서 돈다고 가정했다. 그런데 화면을 쓰지 않는 업무(문서 처리, 서비스 앱 호출, AI 판단, 결재 흐름)는 PC가 필요 없고, 서버에서 **여러 건을 동시에** 돌리는 편이 맞다. 두 종류는 동작 방식이 다르므로 BPM 프로세스마다 실행 위치를 정해 구분한다.

## 결정

### 1. BPM 프로세스 속성 「실행 위치」

BPM 프로세스(패키지 매니페스트 C1)에 `run_location` 속성을 둔다. 값은 둘이다.

| | **PC** (`pc`, 기본값) | **서버** (`server`) |
| --- | --- | --- |
| 실행하는 곳 | 현장 PC의 Bot UI (실행기 하나) | 서버의 **서버 실행기** (Center가 관리) |
| 운영 화면 이름 | Bot | 서버 Bot (가안) |
| 동시 실행 | **PC 한 대에 하나.** 나머지는 Bot UI 대기열 ([ADR-0014](0014-one-bot-per-pc.md)) | **여러 건 동시에.** 같은 BPM 프로세스의 중복 실행도 허용 (상한은 §4) |
| 결재·확인을 기다릴 때 | **끝날 때까지 실행 자리를 쥐고 기다린다** (실제 업무와 같다) | 기다리는 동안 실행 상태를 저장하고 일꾼을 놓는다. 답이 오면 이어서 실행 |
| 결재 창구 | 현장 PC 창 또는 Center 결재함 | Center 결재함만 (화면 앞 사람이 없다) |
| 쓸 수 있는 태스크 | 모두 | UI 태스크·웹/데스크톱 환경 AI 태스크·현장 확인 **불가** (아래 §3) |
| 배포 대상 | Bot UI (PC) | 서버 실행기 |
| 실행·배포·관리 | Center가 지시, Bot UI가 실행 | **Center가 지시·관리, 서버 실행기가 실행** |
| 수행 모드 | 결정 수행 | 결정 수행 (Studio 개발 실행은 둘 다 자율 수행) |

### 2. 서버 실행기

- 서버에서 도는 화면 없는 프로세스다. `core`(BPMN 실행 엔진)를 쓴다. 코드 위치 `apps/server_runner`.
- Center API(`apps/center`)와 **별도 프로세스**로 둔다. Center는 BPMN을 해석하지 않는다는 원칙을 지키고, 실행이 몰려도 Center API가 느려지지 않게 하기 위해서다. 같은 서버에 함께 설치하고, `docker compose`에 함께 넣는다.
- Bot UI처럼 **Center API 키(서버 실행기용)** 로 Center에 접속해 등록·하트비트하고, 배포·작업을 하트비트 응답으로 받는다 ([ADR-0007](0007-client-initiated-communication.md)의 "연결은 실행하는 쪽 → Center"를 그대로 따른다).
- 서버 실행기는 여러 대 둘 수 있다 (규모가 커지면). 처음에는 한 대.
- 서비스 앱 키 값은 서버 실행기가 가진다: 서버의 OS 비밀 저장소 또는 환경변수. 관리는 명령 `chk-runner keys set <참조>` (가안). Center DB에는 두지 않는다 ([ADR-0013](0013-api-keys.md)).

### 3. 서버에서 쓸 수 있는 태스크

| 태스크 | 서버 | 이유 |
| --- | --- | --- |
| AI 태스크 — LLM·API·문서 환경 | 가능 | 화면이 필요 없음 |
| AI 태스크 — 웹·데스크톱 환경 | **불가** | 화면·로그인 세션 필요 (나중에 헤드리스 웹을 따로 검토) |
| UI 태스크 | **불가** | Worker는 PC에만 있다 |
| 서비스 앱 태스크 | 가능 | |
| 결재 (UserTask) | 가능 — Center 결재함만 | |
| 확인 (실행 중 막힘) | **불가** → 그 태스크는 실패로 끝내거나 오류 경계 이벤트로 | 화면 앞 사람이 없다 |
| 타이머·메시지 이벤트, Call Activity | 가능 (호출되는 BPM 프로세스도 서버 실행 가능해야 함) | |

Studio는 실행 위치가 「서버」인 BPM 프로세스에서 불가한 태스크를 「실행 전 검사」 오류로 보이고, 팔레트에서 UI 태스크를 끈다. Center도 업로드·배포 때 다시 검사한다.

### 4. 서버 실행 규칙

| 규칙 | 내용 |
| --- | --- |
| 동시 실행 상한 | 서버 실행기 전체 상한(기본 10, `CHK_SERVER_RUNNER__MAX_CONCURRENCY`) + BPM 프로세스별 상한(배포 때 지정, 기본 5) |
| 상한 초과 | Center 작업 대기열에서 기다린다 (작업 상태 「대기열」). 순서는 들어온 순서 |
| 기다림(결재·메시지·타이머) | 실행 상태를 서버 실행기의 저장소에 저장하고 일꾼을 놓는다 (상한에 세지 않음). 답·메시지·시각이 오면 다시 대기열에 들어가 이어서 실행 |
| 재시작 | 서버 실행기가 다시 뜨면 저장된 실행을 이어 간다. 실행 중이던 태스크는 처음부터 다시 하므로, 서비스 앱 작업은 같은 `run_id`·`node_id`로 다시 불러도 안전해야 한다 (C11 원칙에 추가) |
| 시작 방법 | Center 작업 지시(콘솔·API), 일정, 메시지(외부 시스템 → Center API) |
| 기록 | PC와 같은 실행 이벤트(C3)를 Center로 보낸다. 콘솔 실행 로그(CON-01)에서 실행 위치로 걸러 본다 |

### 5. PC 실행은 ADR-0014 그대로, 결재 대기도 끝까지

PC에서 도는 Bot은 한 번에 하나이고, 결재·확인을 기다리는 동안에도 실행 자리를 쥔 채 **완료될 때까지 기다린다.** 실제 업무에서 담당자가 일을 하다 결재를 기다리는 것과 같다. 실행 상태 저장·재개는 PC에서는 만들지 않는다 (ADR-0014 §5 결정).

## 결과

- 쉬워지는 것: 화면이 필요 없는 업무를 PC 없이 여러 건 동시에 돌린다. PC 실행은 단순한 규칙(하나씩, 끝까지)을 유지한다.
- 어려워지는 것: 서버 실행기라는 구성요소가 늘고, 실행 상태 저장·재개(서버 쪽만), 재실행 안전성(멱등)이 필요하다. 계약 C12(Center ↔ 서버 실행기)가 생긴다.
- 일정 (제안): 첫 릴리스(M6)는 PC 실행만. 다만 `run_location` 속성과 Studio 검사는 처음부터 넣어 패키지 형식이 나중에 바뀌지 않게 한다. 서버 실행은 M7.
- 다시 볼 조건: 서버에서 웹 화면 조작(헤드리스 브라우저)이 필요해지면 §3을 다시 연다.
