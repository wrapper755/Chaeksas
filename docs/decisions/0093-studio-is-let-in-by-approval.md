# ADR-0093. Studio도 Bot UI처럼 요청 코드를 관리자가 승인해 들인다 — 계정 로그인은 쓰지 않는다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-25) |
| 날짜 | 2026-10-25 |
| 관련 | [ADR-0092](0092-keys-are-issued-and-delivered-by-center.md) §2를 대체한다, [ADR-0090](0090-center-admin-accounts.md)(계정은 콘솔 관리자용으로만 남는다), [ADR-0077](0077-tool-ui.md), 계약 C4(§등록 요청과 승인)·C5·C7, 화면 STU-10·CON-11·CON-14 |

## 배경

ADR-0092는 사람을 두 갈래로 들였다. Bot UI·서버 실행기는 **PC를 승인**하고(요청 코드), Studio·Tool UI는 **사람이 Center 계정으로 로그인**한다. Studio에서 올린 것의 「누가」를 사람으로 남기려는 뜻이었고, 그 갈래는 코드까지 갔다(계정 권한 「설계」, `POST /auth/studio-login`, STU-10 아이디·비밀번호 칸).

써 보니 이것은 ADR-0092가 없애려던 심부름을 다른 모양으로 되살린다. 관리자는 설계자마다 계정을 만들고 처음 비밀번호를 정해 건네야 하고, 설계자는 비밀번호를 외워 Studio에 쳐야 한다. 그리고 들이는 방식이 둘이라 관리자가 「Bot UI는 승인, Studio는 계정」을 따로 익혀야 한다. 「관리자는 승인만 한다」는 원칙에 맞는 것은 Bot UI 쪽 길이다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 계정 로그인을 그대로 둔다 (ADR-0092 §2) | 「누가 올렸나」가 사람 계정이다. 이미 코드가 있다 | 계정 만들기·비밀번호 건네기가 남는다. 들이는 방식이 둘이다 |
| B. **Studio도 등록 요청 → 관리자 승인** (Bot UI와 같은 길) | 아이디·비밀번호가 없다. 관리자 일은 「승인」 하나다. 등록 요청·요청 코드·봉함을 그대로 쓴다 | 「누가」가 사람이 아니라 **승인할 때 붙인 이름**(PC 단위)이다 |

## 결정

**B로 한다.** Studio에도 Center 주소만 넣는다. Studio가 등록 요청을 보내 요청 코드를 띄우면, 관리자가 콘솔에서 같은 코드를 보고 승인하고, Center가 Studio용 키를 만들어 그 요청의 공개키로 봉해 내려 준다. **아이디·비밀번호로 Studio에 들어오는 길은 없앤다.**

### 1. Studio 등록 요청 — C4 §등록 요청과 승인과 같은 길

- 요청 코드·봉함·24시간 대기·막기·같은 PC의 옛 요청 닫기는 **Bot UI와 같은 규칙, 같은 코드**다 (`contracts.enrollment`, Center `center/enrollments.py`). 종류만 `studio`다.
- 경로는 `POST /api/v1/studio/enroll`·`GET /api/v1/studio/enroll/{id}`(인증 없음)이다. 본문은 `{schema, machine_id, name, os, versions{studio, core}, public_key}`이다.
- 승인하면 Center는 종류 `studio`의 키를 만든다. 이름은 승인할 때 관리자가 정하고(기본은 요청의 PC 이름), **그 PC(`machine_id`)에 묶어 둔다**. 같은 PC를 다시 승인하면 옛 Studio 키를 폐기한다.
- Studio는 받은 키를 OS 비밀 저장소(`chaeksas-studio`)에 둔다. 그다음은 지금처럼 그 키로 올리고 읽는다.
- **「누가 올렸나」는 그 키의 이름**이다 — 승인할 때 사람이 알아볼 이름(「김OO 설계 PC」)을 붙인다.

### 2. 키 수명 — 회전 대신 다시 요청

- Studio는 하트비트가 없어서 Bot UI처럼 하트비트로 키를 갈아 줄 수 없다. 그래서 키는 **1년**이고, 만료 14일 전부터 STU-10 상태 줄이 알린다. 만료되거나 폐기되면 Studio가 「다시 요청」을 보이고, 새 요청을 승인하면 된다.

### 3. 걷어 내는 것

- 계정 권한(`permissions`, 「설계」)과 Studio 로그인(`POST /auth/studio-login`·`studio-logout`, 키의 `account`·`machine_name` 칸), CON-14의 「권한」·「Studio 로그인」 열과 그 동작, STU-10의 아이디·비밀번호 칸.
- **계정은 콘솔 관리자용으로만 남는다** (ADR-0090 그대로 — 관리자·보기 전용).
- 저장소에 이미 생긴 11판 열(`accounts.permissions_json`, `center_keys.account`·`machine_name`)은 **지우지 않는다** — 옮기기 단계는 지우거나 고치지 않는다(ADR-0065). 쓰지 않는 열로 남는다.

### 4. 승인하는 자리

- Studio 요청은 **CON-11 「Center API 키」** 위의 「승인 대기」에 보인다 — Studio용 키가 사는 화면이고, Bot UI·서버 실행기의 승인 대기(CON-03·CON-12)와 **같은 표·같은 창**이다. 승인된 Studio는 CON-11 목록에 「승인으로 발급」으로 보이고, 끊을 때는 그 키를 폐기한다.

### 5. Tool UI

- ADR-0092 §2의 「Tool UI는 Center에 계정으로 로그인한다」도 이 결정이 대체한다. Tool UI의 셀렉터 등록 권한을 어떻게 받을지는 **서비스 앱 키 조각(ADR-0092 §3)과 함께** 정한다.

> 미정: Tool UI가 그 PC의 Bot UI 승인을 빌려 쓸지, 제 요청을 따로 보낼지.

## 결과

- 쉬워지는 것: 들이는 방식이 하나다(요청 코드 → 승인). 관리자가 계정을 만들어 건넬 일이 없고, 설계자는 비밀번호를 외우지 않는다. 등록 요청 코드를 그대로 쓰므로 새로 짤 것이 적다.
- 어려워지거나 포기하는 것: 「누가 올렸나」가 사람 계정이 아니라 **승인할 때 붙인 이름**이다 — 한 PC를 여럿이 쓰면 가를 수 없다. Studio 키는 회전하지 않아 1년마다 다시 승인한다.
- 다시 볼 조건: 한 PC를 여러 설계자가 나눠 쓰고 「누가」를 사람으로 가려야 하면 계정 로그인(A)을 다시 연다.
