# ADR-0038. 결재 요청은 **요청 파일**로 올라오고, Bot UI가 Center로 올린다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-10-07 |
| 관련 | [ADR-0031](0031-runner-control-file.md)(파일 한 벌 — 이 ADR이 「올라오는 길은 하나」에 예외를 둔다), [ADR-0007](0007-client-initiated-communication.md)(연결은 늘 현장 → Center), [ADR-0013](0013-api-keys.md)(키는 Bot UI가 쥔다), [ADR-0014](0014-one-bot-per-pc.md), [C3](../03-contracts/C3-run-events.md), [C6](../03-contracts/C6-approvals.md), [C14](../03-contracts/C14-bpmn-extensions.md) `chk:approval`, 화면 CON-04·CMN-01·BUI-03 |

## 배경

C6의 서버 쪽과 결재함(CON-04)은 돈다 (M5 조각 5). 그런데 **현장에서 올라오는 길이 없다.**

- 엔진의 `handle_approval`은 `where="field"`로 박혀 있다 — 「설정을 보는 것은 뒤 조각」이라 주석에 적어 두었다.
- 더 큰 문제는 **무엇을 올리느냐**다. C6 `ApprovalCreateRequest`에는 `review`(결재자가 판단할 업무 값)가 들어간다. 이 값은 실행 중에만 생기고 실행기 자식 프로세스 안에만 있다.
- ADR-0031은 「**올라오는 길은 C3 실행 기록 하나뿐**」이라고 정했다. 그런데 C3에는 **값이 담기지 않는다** (원칙 6 — `human_requested`에는 `request_id`·`layer`·`where`뿐이고 `sanitize()`가 값을 거른다). 실행 기록을 그대로 Center로 보내는 구조라, 거기에 값을 넣는 순간 모든 실행 기록이 업무 값을 나르게 된다.

즉 **올라오는 길 하나로는 결재를 올릴 수 없다.** 지금 정해야 하는 것은 그 예외를 어디에 둘 것인가다.

폼은 문제가 아니다 — 설치된 패키지의 BPMN에 있어서 Bot UI가 다시 읽으면 된다 (CMN-01이 이미 그렇게 한다). 오직 `review`가 걸린다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 요청 파일** — 실행기가 `runs/<run_id>.requests.jsonl`에 **C6 본문 그대로** 쓰고, Bot UI가 읽어 `POST /approvals` | 제어 파일의 **거울**이라 구조가 하나 더 늘지 않는다. 값이 C3에 섞이지 않는다. Bot UI는 **내용을 짓지 않고 나르기만** 한다. 닿지 못해도 남는다. 시험이 쉽다 | 파일이 셋이 된다 (기록·제어·요청) |
| B. 실행 기록에 넣고 보낼 때 거른다 | 올라오는 길이 그대로 하나 | **한 번만 실수하면 값이 샌다.** C3는 Center·콘솔·보관까지 가는 넓은 길인데 거기에 값을 실어 놓고 길목마다 거르는 꼴이다. 원칙 6을 뒤집는다 |
| C. 실행기가 Center에 직접 올린다 | 중간 단계가 없다 | 실행기에 **Center 키와 네트워크 일**을 준다 (ADR-0013·0007을 거스른다). 재시도·큐를 실행기가 또 갖는다. 실행기는 오프라인에서도 돌아야 한다 |
| D. 로컬 HTTP·소켓으로 실행기 → Bot UI | 즉시 전달 | ADR-0031이 이미 같은 이유로 접었다 (포트·토큰·수명이 또 는다) |

## 결정

**A — 요청 파일 하나를 더 둔다.** ADR-0031의 「올라오는 길은 실행 기록 하나」에 **값이 필요한 결재 요청만** 예외를 둔다.

1. **어디서 답하나(`where`)는 엔진이 정한다.** `chk:approval.location`과 호스트 설정이 함께 본다 (C14 `APPROVAL_LOCATIONS`).

   | `location` | 결과 |
   | --- | --- |
   | `field` | 현장 (CMN-01) |
   | `center` | Center 결재함 |
   | `follow` (기본) | 호스트가 정한다 — Bot UI는 BUI-03 「원격 결재」(`remote_approval`), 서버 실행기는 늘 `center` |

   엔진은 호스트의 기본값을 `RunEnv`로 받는다 — **엔진이 설정 파일을 읽지 않는다** (바깥에 닿는 길은 `RunEnv` 하나다). 기본은 `field`다: 설정을 안 주면 현장에서 답한다.

   **확인(`manualTask`)은 늘 현장이다** — 화면 앞 사람만 답할 수 있기 때문이다 (C6). `location`에 `center`를 적었으면 **검사가 경고한다** (B12). 조용히 무시하면 「Center 결재함에서 답할 수 있겠지」 하고 그린 사람이 실행할 때까지 모른다 — **적어 둔 것을 말없이 바꾸지 않는다.**

   > 이것을 정하다 **계약 셋이 어긋나 있는 것**이 드러났다. C14는 「수동 작업은 서버 BPM 프로세스에서 Center 결재함으로 간다」고 적었는데, C1 R2는 서버 BPM 프로세스에 확인을 **아예 넣지 못하게** 막고(`human.confirmation=false`) C6은 확인을 **올리지 않는다**고 적었다. 있을 수 없는 경우를 설명하는 문장이라 C14를 고쳤다 (C14 변경 이력 2026-10-07).

2. **`where=center`인 요청만 요청 파일에 쓴다.** `runs/<run_id>.requests.jsonl`, 한 줄에 하나, **C6 `ApprovalCreateRequest` 본문 그대로**. 현장 결재는 쓰지 않는다 (올릴 이유가 없다).

   본문을 그대로 쓰는 것이 요점이다 — **Bot UI는 결재의 내용을 짓지 않는다.** 제목·폼·검토 자료를 아는 것은 엔진뿐이고, Bot UI는 봉투를 나르는 집배원이다 (배포 봉투를 다루는 방식과 같다).

3. **Bot UI가 하트비트 뒤에 올린다** — 실행 기록 보내기(`core.run_shipping`)와 **같은 수법**이다.
   - 보낸 자리는 `.requests.sent`에 남긴다. 멱등이라 같은 것을 다시 보내도 200이다 (C6).
   - **4xx는 다시 보내지 않는다** — 한 줄이 큐를 영원히 막으면 안 된다 (거부는 기록에 남긴다).
   - 닿지 못하면 그대로 두고 다음 주기에 다시 보낸다. **실행은 계속 기다린다** (ADR-0014).

4. **내려가는 길은 제어 파일 그대로**다 (ADR-0031). 하트비트로 받은 답을 Bot UI가 제어 파일에 적고, 실행기가 집어 간다. 받아 갔으면 `approval_acks`로 알린다. 제어 파일에 **지시 하나를 더한다**:

   ```json
   {"kind": "withdraw", "request_id": "apr_…", "reason": "admin_withdraw"}
   ```

   회수는 **답이 아니다** — 실행하는 쪽은 「답 없이 끝남」으로 받는다. 그 노드에 오류 경계 이벤트가 있으면 그쪽으로 가고, 없으면 실행이 실패로 끝난다 (C6). `expired`도 같은 길로 간다.

5. **현장에서 먼저 답하면 Bot UI가 Center에서 거둔다** — `DELETE /approvals/{id}?reason=answered_in_field`. 그래야 결재함에 「답해도 전달될 곳이 없는 결재」가 남지 않는다. 이 경우는 **실행에 영향이 없다**.

6. **끝나면 요청 파일도 지운다** (제어 파일과 같이). 업무 값이 PC에 남지 않는다. 실행 기록만 남아 Center로 간다.

## 결과

- 이 결정으로 쉬워지는 것: **C3가 깨끗하게 남는다** — 실행 기록은 끝까지 값을 나르지 않고, 값이 다니는 길은 결재 하나로 좁아진다 (요청 파일 → C6 → 결재함, 30일 뒤 삭제). 실행기는 네트워크를 모르는 채로 남고, Bot UI는 내용을 모르는 채 나르기만 한다 — 둘 다 시험하기 쉽다. 닿지 못해도 결재가 사라지지 않는다.
- 어려워지거나 포기하는 것: 실행 하나에 파일이 **셋**이 된다 (기록·제어·요청). 결재가 Center에 보이기까지 **하트비트 한 주기**(기본 30초)가 걸리고, 답이 돌아오는 데 또 한 주기가 걸린다 — 사람이 몇 분~며칠 걸리는 일이라 괜찮다고 본다.
- 다시 볼 조건: 결재 말고도 값을 올려야 할 것이 생기면(예: 실행 중 사람에게 보여 줄 중간 산출물) 요청 파일을 일반화할지 본다. 하트비트 주기가 결재에 너무 느리다고 느껴지면 올릴 것이 있을 때만 주기를 당기는 것을 본다 — **연결 방향은 바꾸지 않는다** (ADR-0007).
