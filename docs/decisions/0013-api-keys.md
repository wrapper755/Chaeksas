# ADR-0013. API 키: Center 키는 Bot UI에, 서비스 앱 키는 각 앱의 관리 콘솔에서 발급해 BPM 프로세스 단위로 지정

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-01) — §3 키 지정 위치는 안 C로 확정 (2026-10-01) |
| 날짜 | 2026-10-01 |
| 대체 | ADR-0010 §3(인증)·§4-7(Center 키 목록 동기화), 서비스 앱 화면을 Center 콘솔에 붙인다는 제안 |
| 관련 | ADR-0010, ADR-0012, 계약 C4·C10·C11, 화면 CON-11, BUI-03, BUI-10, STU-04, STU-14, `docs/06-screens/service-app-console.md` |

## 배경

키가 두 종류 있다.
- **Center API 키**: Bot UI·Studio가 Center에 접속할 때 (등록, 하트비트, Bot 다운로드, 실행 기록, 업로드).
- **서비스 앱 API 키**: BPM 프로세스가 서비스 앱(LLM 앱)을 호출할 때.

ADR-0010에서는 서비스 앱 키도 Center가 발급하고 서비스 앱이 Center에서 키 목록을 받아 검증하는 안이었다. 검토 결과, 서비스 앱 키는 **각 서비스 앱(LLM 앱)의 관리 콘솔에서** 발급하는 것이 맞다 (LLM API의 일반적인 방식, 앱마다 권한·사용량 관리가 다름).

## 결정

### 1. Center API 키 — Center 콘솔에서 발급, Bot UI에 등록

- 운영자가 Center 콘솔 「API 키」(CON-11)에서 발급한다. 종류: **Bot UI용**(PC 한 대에 하나), **Studio용**(설계자 한 명에 하나).
- 설치 담당자가 Bot UI 설정(BUI-03)에 Center 주소와 키를 넣으면, 그 키로 Center에 등록·하트비트한다. 키가 곧 그 Bot UI의 신원이다 (다른 Bot UI를 사칭할 수 없다).
- 등록 토큰과 자동 발급은 쓰지 않는다.
- 키 원문은 발급 때 한 번만 보인다. Bot UI·Studio는 OS 비밀 저장소에 둔다.
- 폐기하면 그 Bot UI의 하트비트가 거부된다 (콘솔에 「키 폐기됨」으로 보임).

### 2. 서비스 앱 API 키 — 각 서비스 앱의 관리 콘솔에서 발급

- 서비스 앱마다 **관리 콘솔**(웹)을 가진다. 최소 기능: 상태, API 키 발급·폐기, 사용 기록. UI 자동화 앱은 여기에 셀렉터 인벤토리·모니터링이 더해진다 (`docs/06-screens/service-app-console.md`).
- 키에는 이름, 허용 작업, 허용 수행 모드(자율/결정), 만료가 붙는다.
- 서비스 앱은 자기 키를 스스로 검증한다. Center는 서비스 앱 키를 발급·저장·동기화하지 않는다 (Center는 비밀을 저장하지 않는다는 원칙과 맞음).
- Center 리소스 목록(C7)에는 서비스 앱의 주소·상태·작업 목록·관리 콘솔 주소만 둔다.

### 3. 서비스 앱 키를 어디에 지정하나 — BPM 프로세스 단위, "키 참조"로 (안 C 확정)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. ServiceTask 속성에 키 값 | 태스크마다 다른 키 가능 | 같은 키를 여러 곳에 반복. 키 값이 BPM 파일·패키지에 들어가 서명·배포·Center 저장소로 퍼짐. 바꾸려면 재배포 |
| B. BPM 프로세스 속성에 키 값 | 한 곳에서 관리 | 키 값이 패키지에 들어가는 문제는 A와 같음 |
| **C. BPM 프로세스 속성에 키 참조(이름), 값은 Bot UI·Studio의 비밀 저장소** | 패키지에 비밀이 없음. 키를 바꿔도 재배포 불필요. BPM 프로세스별로 권한·사용량·폐기 관리 가능. 같은 참조가 Studio에서는 개발 키, Bot UI에서는 운영 키로 풀림 | Bot UI마다 키 값을 등록해야 함 |
| D. Bot UI 전역 키 하나 | 가장 간단 | BPM 프로세스별 사용량·권한 구분 불가. 하나가 새면 전부 위험 |

**결정: C** (2026-10-01 확정). 말씀하신 "BPM 프로세스 별로 지정"을 따르되, 값이 아니라 참조를 지정한다.

- BPM 프로세스 속성(STU-04)에 「서비스 앱 키」 표: 서비스 앱 → 키 참조 이름 (예: `ui-automation` → `finance-invoice`).
- ServiceTask(STU-14)·UI 태스크(STU-13)는 기본으로 BPM 프로세스의 키를 **상속**한다. 예외적으로 다른 키가 필요할 때만 태스크에서 참조를 바꾼다.
- 키 값은 실행하는 쪽이 가진다:
  - Bot UI: 「서비스 앱 키」 화면(BUI-10)에서 참조 이름 ↔ 키 값 (운영 키, 결정 수행 허용).
  - Studio: 설정 「서비스 앱 키」에서 같은 참조 이름 ↔ 개발 키 (자율 수행 허용).
- 사전 점검: Bot을 설치·실행하기 전에 Bot UI가 필요한 참조가 모두 등록돼 있는지 확인한다. 없으면 「실행 불가 — 서비스 앱 키 `<참조>`가 이 PC에 없습니다」.
- UI 태스크: Bot이 참조를 풀어 Worker 세션 요청에 키를 실어 보낸다 (127.0.0.1 안에서만). Worker가 그 키로 UI 자동화 앱을 부른다.
- UI 셀렉터 등록(유틸리티): 등록 담당자 개인 키를 Bot UI 설정에 따로 둔다 (레지스트리 쓰기 권한).

> 제안 보완 — 키 값 등록 부담: Bot UI가 많아지면 PC마다 키를 넣는 일이 부담이 된다. 필요해지면 "Center가 암호화된 키 묶음을 Bot UI에 전달"하는 방식을 별도 ADR로 검토한다 (Center가 비밀을 다루게 되므로 지금은 하지 않음).

## 결과

- 쉬워지는 것: 패키지·BPM 파일·Center에 서비스 앱 비밀이 없다. 서비스 앱이 자기 키 정책을 스스로 가진다. BPM 프로세스별로 사용량과 권한을 나눠 볼 수 있다.
- 어려워지는 것: Bot UI 설치 시 Center 키와 서비스 앱 키를 등록하는 절차가 생긴다 (설치 안내 문서 필요). 서비스 앱마다 관리 콘솔을 만들어야 한다 → `service_kit`에 공통 콘솔(상태·API 키·사용 기록)을 넣는다.
- 다시 볼 조건: Bot UI가 수십 대를 넘어 키 배포가 병목이 되면 위 "제안 보완"을 ADR로 연다.
