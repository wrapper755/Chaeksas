# ADR-0023. Bot 실행은 Bot UI의 자식 프로세스(실행기)로 확정, 자식마다 Job Object, 자동 시작은 작업 스케줄러

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-03). Linux 구현은 미확인. **주고받는 길은 [ADR-0031](0031-runner-control-file.md)이 대체함** (stdin → 파일) |
| 날짜 | 2026-10-02 |
| 관련 | 스파이크 `spikes/S4-resident-supervisor/`, ADR-0012·0014(실행기 제안), ADR-0020·0021(Worker), 계약 C10, 화면 BUI-01·BUI-09, `docs/01-architecture.md` §6 |

## 배경

ADR-0012·0014는 Bot 실행을 Bot UI의 **자식 프로세스(실행기) 하나**에서 돌리자고 제안했다(목적은 격리). 단, S4에서 Windows 자식 프로세스 관리가 과하게 복잡하면 Bot UI 안의 스레드 실행으로 되돌린다는 조건을 달았다.
Windows에는 `os.killpg`가 없고, 부모가 죽어도 자식이 따라 죽지 않는다. Bot UI가 상주하려면 자동 시작 방식, 잠금 화면·로그오프 때의 동작도 정해야 한다.

## 선택지

S4에서 가짜 Bot UI·Worker·실행기로 Windows 11 실기 시험을 했다 (자세히: `spikes/S4-resident-supervisor/NOTES.md`).

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 실행기 = 자식 프로세스, 자식마다 Job Object(`KILL_ON_JOB_CLOSE`) | 멈춘 Bot을 손자까지 나무째 끝낼 수 있다. Bot UI가 강제 종료돼도 자식·손자가 남지 않는다 (시험: Job 없으면 6개 고아, Job이면 0개). 헬퍼 약 150줄 | ctypes로 Win32를 직접 부른다. 자식을 일시 정지로 만들어 넣는 순서를 지켜야 한다 |
| B. 실행기 = 자식 프로세스, Job 없이 | 단순 | Bot UI가 죽으면 Worker·실행기·브라우저가 고아로 남는다 |
| C. Bot UI 안의 스레드 | 프로세스 관리가 없다 | 멈춘 Bot을 강제로 끝낼 방법이 없다 (Python 스레드는 죽일 수 없다). Bot의 충돌이 Bot UI를 같이 죽인다 |

자동 시작:

| 선택지 | 결과 |
| --- | --- |
| 작업 스케줄러 「로그온 시」 (현재 사용자) | 관리자 권한 없이 등록. 로그온 4초 뒤 실행, 사용자 화면에 GUI가 뜬다 |
| HKCU `Run` | Windows가 Run 항목을 차례로 실행해서, 시험 PC에서 로그온 2.5~3분 뒤에야 시작 |

## 결정

**A. Bot 실행은 Bot UI의 자식 프로세스(실행기) 하나에서 돌리고, Worker 프로세스와 실행기는 각각 자기 Job Object에 넣는다.** ADR-0012·0014의 실행기 제안을 확정한다.

- **띄우기:** 일시 정지 상태로 만들고 → Job(`KILL_ON_JOB_CLOSE`)에 넣고 → 깨운다. Job 핸들은 Bot UI만 쥔다. 그래서 Bot UI가 어떻게 끝나든 OS가 자식 나무를 정리한다. 이 일은 `01-architecture.md` §5의 「자식 프로세스 관리 공통 헬퍼」가 맡고, Linux 구현은 같은 인터페이스 뒤에 둔다.
- **실행기 끝내기:** 시간 초과·사용자 중지 → `stop` 한 줄(협조 중지 — **제어 파일로**, ADR-0031) → 유예(기본 2초, 설정) → Job 나무째 강제 종료 → 대기열 다음 차례. 실행기의 종료 코드와 방식(`exited`/`stopped`/`killed`)을 실행 기록에 남긴다.
- **Worker 감시:** C10 기동 절차 그대로 (토큰 파일 → 기동 → `/v1/health` 대기 → 죽으면 연속 3회까지 재시작). 연속 횟수는 Worker가 일정 시간 건강하게 살아 있으면 0으로 되돌린다. 재시작 사이는 짧게 늘린다 (0.25·0.5·1초).
  - Worker가 다시 뜨면 토큰이 바뀐다. **실행기·Studio는 토큰 파일을 호출마다(또는 401을 받으면) 다시 읽는다.**
  - 기동 중 종료 코드 2(포트 실패)는 Bot UI가 「포트 <p> 사용 중 — 다른 프로그램이 쓰고 있습니다」로 바꿔 보인다. Windows 오류 문구를 그대로 보이지 않는다.
- **잠금 화면:** Worker는 WTS 세션 잠금(`WTSRegisterSessionNotification` 또는 `WTSSessionInfoEx`)으로 잠금을 안다. 입력 데스크톱 이름이나 UIA 결과로는 알 수 없다 — 잠긴 동안에도 UIA는 요소와 위치를 정상으로 돌려준다. 잠긴 동안에는 화면 조작·캡처를 하지 않는다.
  > 제안: 잠긴 동안 UI 스텝 요청에는 C10에 오류 `session_locked`(재시도 가능)를 더해 돌려주고, 실행기는 해제되거나 스텝 시간 제한에 닿을 때까지 기다린다. 계약은 C10 문서를 먼저 고친 뒤.
- **로그오프·종료:** Bot UI는 최상위 숨은 창으로 `WM_QUERYENDSESSION`(막지 않는다)과 `WM_ENDSESSION`을 받고, `WM_ENDSESSION`에서 실행기·Worker Job을 끝낸다. 메시지 전용 창(`HWND_MESSAGE`)은 이 알림을 받지 못한다.
- **자동 시작:** 설치 파일이 현재 사용자의 작업 스케줄러 「로그온 시」 작업으로 Bot UI를 등록한다 (관리자 권한 불필요). 작업의 실행 시간 제한은 없음, 배터리 조건 없음. 실행 대상은 **설치된 실행 파일**이어야 한다 — 개발용 가상환경 런처가 아니다 (S5).

> 미정: Linux 구현(프로세스 그룹 + `PR_SET_PDEATHSIG`, XDG autostart). 로그오프 중 대기열의 Center 작업을 「거절 — Bot UI 종료」로 알릴 시간이 충분한지 (ADR-0014 §2).

## 결과

- 이 결정으로 쉬워지는 것: 멈추거나 죽은 Bot이 Bot UI·대기열·Center 연결에 영향을 주지 않는다. Bot UI가 강제로 끝나도 고아 프로세스·브라우저가 남지 않는다. 로그온 직후 바로 뜬다.
- 어려워지거나 포기하는 것: Win32 Job API를 ctypes로 감싼 헬퍼를 유지해야 한다 (pywin32를 쓰지 않는 경우). 작업 스케줄러 등록·해제가 설치·제거 절차에 들어간다.
- 다시 볼 조건: Linux에서 같은 보장이 안 되는 경우, 원격 데스크톱·빠른 사용자 전환·절전 복귀에서 다른 결과가 나오는 경우, 사내 보안 정책이 사용자 작업 스케줄러 등록을 막는 경우(그때 HKCU Run을 대안으로).
