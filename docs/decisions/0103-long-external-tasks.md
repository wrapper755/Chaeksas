# ADR-0103. 긴 외부 작업은 서버 실행기가 기다림으로 넘기고 자리를 놓는다 — 짧은 것은 그 자리에서 끝낸다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-29) |
| 날짜 | 2026-10-29 |
| 관련 | [ADR-0102](0102-calling-outside-is-pull.md) §7 조각 6, [ADR-0054](0054-server-run-state-and-concurrency.md)·[0061](0061-waking-runs-whose-timer-is-due.md)·[0062](0062-pc-delegation.md), 계약 C3·C12·C15 |

## 배경

ADR-0102로 바깥 기능은 모두 Center의 외부 작업(C15)으로 부른다. 그런데 서버 실행기는 결과가 올 때까지 **실행 스레드를 쥐고** 롱폴링을 되풀이한다. 몇 분 걸리는 LLM 작업이나 사람이 끝내는 사내 시스템 작업이 몇 개만 겹쳐도 Bot별·실행기 상한이 차고, 그동안 다른 Bot이 돌지 못한다. 결재·메시지·타이머·PC 위임은 이미 「담아 두고 자리를 놓는다」(ADR-0054)로 도는데, 외부 작업만 그 길에 없다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 모든 서버 호출을 기다림으로 | 규칙이 하나 | 1초짜리 호출도 하트비트 주기만큼 늦는다. 스냅샷·기록 줄이 호출마다 생긴다 |
| **B. 한 번 기다려 끝나지 않을 때만 기다림으로** | 짧은 호출은 지금 그대로, 긴 것만 자리를 놓는다 | 갈림길이 하나 는다(「얼마나 기다리면 넘기나」 설정) |
| B-1. 결과를 하트비트 답에 실어 내린다 (PC 위임처럼) | 요청이 늘지 않는다 | C12 답에 칸·ack 칸이 늘고 Center가 실행기의 기다림과 일감을 짝짓는다 |
| **B-2. 실행기가 주기마다 Center에 묻는다** | C15에 이미 있는 길(`GET …/{task_id}`·`ack`·`cancel`)뿐 — Center를 고치지 않는다 | 기다리는 일감 수만큼 주기마다 요청이 생긴다 |

## 결정

**서버 실행기는 외부 작업을 한 번 기다려(기본 20초, `CHK_SERVER_RUNNER__PARK_AFTER_S`) 끝나지 않으면 다섯째 기다림 `external_task`로 넘기고 자리를 놓는다. 결과는 하트비트 주기마다 실행기가 C15로 묻는다.**

1. **넘기는 것은 부르는 쪽이 정한다.** `core.services.CenterServiceCaller(park_after_s=…)`가 그 시간 안에 끝나지 않은 일감을 `ServicePending(task_id)`로 알리고, 엔진은 그 노드에서 `external_task`로 멈춘다(짝 칸 `task_id`, 재시도에 쓸 `attempt`·`call_seq`도 기다림에 담긴다 — 스냅샷과 함께 간다). **서버 실행기만 켠다.** Studio는 시험이라 기다려도 되고, Bot UI 실행기 자식은 어차피 PC의 자리를 쥔다(ADR-0014).
2. **결과는 실행기가 묻는다.** 하트비트 주기마다(타이머 깨우기와 같은 자리, ADR-0061) 기다리는 일감을 `GET /external-tasks/{task_id}`로 보고, 끝난 것을 엔진에 넣는다(`Engine.external_done`). 관문은 결재·메시지·위임과 같다 — **빈자리가 없거나 그 실행을 미는 스레드가 아직 돌면 넣지 않고 다음 주기에 본다.** 넣은 뒤 `ack`한다(C15 셋째 규칙 — Center가 값을 지운다).
3. **이어 가는 규칙은 동기 호출과 하나다.** 끝났으면 `chk:serviceCall.output`대로 변수에 담고, 실패면 `retry`가 받는 것은 `attempt`를 올려 다시 올린다(다시 오래 걸리면 또 넘긴다). 다 실패하면 `TaskFailed`라 오류 경계가 받는다. 기한(`timeout_s`)은 Center가 지킨다 — 지나면 `expired`로 끝나 같은 길을 탄다.
4. **기다림이 걷히면 일감도 거둔다.** 실행 취소·끊는 경계 이벤트로 그 토큰이 걷히면 `POST …/{task_id}/cancel`이다(맡긴 위임을 거두는 것과 같은 결, ADR-0062 §5). 닿지 못하면 기록만 하고 간다 — 일감은 기한에 저절로 끝난다.
5. **받아 간 결과를 잃으면 같은 칸으로 다시 올린다.** 넣고 `ack`한 뒤 스냅샷을 담기 전에 실행기가 죽으면, 되살린 실행은 값이 지워진 일감을 기다린다. 그때는 결과에 출력이 없으므로 **같은 멱등 칸으로 다시 올린다** — Center가 다시 줄에 세우고(C15 §올리기) 일꾼이 멱등 칸으로 저장해 둔 결과를 다시 준다. 업무가 두 번 일어나지 않는다.
6. **기록에 남긴다.** C3 `run_waiting`(`waiting_for: external_task`, `task_id`)·`run_resumed`(`reason: external_task`)이고, C12 `waiting[]`에 같은 갈래와 짝 칸 `task_id`가 올라가 CON-12가 보인다. `service_call` 줄은 결과를 넣을 때 한 번 쓴다 — 동기 호출과 같은 줄이다.

## 결과

- 쉬워지는 것:
  - 몇 분·몇 시간 걸리는 외부 작업이 서버 실행기의 자리를 쥐지 않는다. 재시작도 스냅샷이 넘긴다.
  - Center는 바뀌지 않는다(C15에 있는 셋만 쓴다). 일꾼도 모른다.
- 어려워지거나 포기하는 것:
  - 긴 작업의 결과는 하트비트 주기만큼 늦게 이어 간다(`run_resumed.after_s`에 그대로 보인다).
  - 기다리는 일감마다 주기에 요청 하나다. 많아지면 B-1(하트비트로 묶어 내리기)로 간다.
- 다시 볼 조건: 실행기 하나가 동시에 기다리는 외부 작업이 수백을 넘거나, 주기만큼의 지연이 업무에 문제가 될 때.
