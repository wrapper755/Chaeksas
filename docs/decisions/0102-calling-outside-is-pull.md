# ADR-0102. BPM 프로세스가 바깥 기능을 부르는 길은 모두 Pull이다 — 일감은 Center에, 가져가는 것은 일꾼

| 상태 | 수락 (2026-10-28) — 결정만 들어갔다. 계약은 [C15](../03-contracts/C15-external-tasks.md) **초안**이고 코드는 아직 Push 그대로다 (§7 조각 순서) |
| 날짜 | 2026-10-28 |
| 관련 | 계약 C15(새), C7·C8·C9·C10·C11·C13·C14, [ADR-0007](0007-client-initiated-communication.md)·[0010](0010-service-apps.md)·[0052](0052-service-app-key-notices.md)·[0091](0091-external-apps-without-auth-take-no-key.md)·[0092](0092-keys-are-issued-and-delivered-by-center.md)·[0094](0094-service-app-keys-ride-the-deployment.md)·[0097](0097-external-extension-address-from-center.md), 화면 CON-07·STU-10·STU-14·TOL-02 |

## 배경

지금 BPM 프로세스가 서버의 기능을 부르는 길은 **부르는 쪽이 받는 쪽을 찌르는**(Push) 모양이다.

- 서비스 앱 태스크(`chk:serviceCall`)는 서버 실행기·실행기 자식 프로세스·Studio가 C11 `POST /v1/ops/{operation}`을 부른다. 외부 앱은 같은 자리에서 HTTP 어댑터(C13 §4)가 부른다.
- UI 자동화 Worker는 UI 자동화 앱을 계획·치유·보고(C8)로 부르고, Tool UI의 셀렉터 등록은 C9를 부른다. Center는 그 앱의 공개 카탈로그를 읽는다.

그래서 **Center 콘솔이 바깥 기능의 주소와 키를 쥔다.** 리소스 화면에 서비스 앱 주소를 넣고, 외부 앱마다 운영 키·시험용 키를 넣고(ADR-0094 §7), 외부 확장 주소를 덮어쓴다(ADR-0097). 이것이 세 가지 문제를 낳는다.

1. **설정 화면에 주소·키가 모인다.** 키 참조로 BPMN은 깨끗하지만 그 값은 Center와 현장에 봉해 퍼진다.
2. **인증 방식을 감당하지 못한다.** 어댑터의 `auth`는 `bearer`·`header` 둘뿐이다. OAuth 갱신·mTLS·날마다 바뀌는 세션 토큰은 BPM 쪽에서 할 수 없다.
3. **바깥이 바뀌면 BPM 쪽을 고친다.** 키를 바꾸면 CON-07에서 다시 넣고, 주소·스펙이 바뀌면 정의를 다시 올리고 고정을 다시 누른다.

또 C11은 동기 호출(기본 60초)뿐이라 긴 작업을 정식으로 기다릴 수 없고, 서버 실행기가 닿지 못하는 사내망 시스템은 부를 길이 없다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 지금 그대로 (Push), 어댑터의 인증만 늘린다 | 바꿀 것이 적다 | 키·주소가 계속 Center에 있다. OAuth·mTLS를 BPM 쪽이 다 떠안는다 |
| B. 외부 앱만 Pull | 작은 걸음 | 서비스 앱 주소가 남는다. 부르는 길이 둘이라 부르는 쪽 코드도 둘이다 |
| **C. 네트워크를 건너는 바깥 호출은 모두 Pull** | 부르는 쪽이 주소·키를 모른다. 길이 하나다. 긴 작업·사내망이 된다 | 범위가 크다. Center가 바깥 호출의 길목이 된다(§결과). 일꾼을 상시 띄워야 한다 |

## 결정

**C.** BPM 프로세스(와 그 확장 태스크)가 네트워크를 건너 바깥 기능을 부르는 길은 모두 **Center의 외부 작업**을 거친다. 부르는 쪽은 Center에 일감을 올리고 결과를 기다린다. 기능 쪽의 **일꾼**이 Center에 롱폴링을 걸어 두었다가 가져가(잠금) 수행하고 끝냈다고 알린다. 연결은 늘 **일꾼 → Center**, **부르는 쪽 → Center**다 (ADR-0007의 방향을 서버 사이에도 쓴다).

### 1. 범위

| 길 | 이번 범위 | 까닭 |
| --- | --- | --- |
| 서비스 앱 태스크 → C11 서비스 앱 (서버 실행기·실행기 자식·Studio) | **넣는다** | |
| 서비스 앱 태스크 → 외부 앱 (HTTP 어댑터) | **넣는다** — 어댑터는 **어댑터 일꾼**으로 옮긴다 (§4) | |
| Worker → UI 자동화 앱 (C8 계획·치유·보고) | **넣는다** | Worker가 네트워크를 건넌다 |
| Tool UI·Worker → UI 자동화 앱 (C9 등록 작업) | **넣는다** | |
| Center → UI 자동화 앱 공개 카탈로그 | **넣는다** — 일꾼이 Center에 **올린다** (§3) | 주소를 Center가 몰라야 한다 |
| Center → 서비스 앱 `/manifest`·`/healthz` | **넣는다** — 일꾼이 올리고, 살아 있음은 가져가기가 말한다 | 같은 까닭 |
| 같은 PC 127.0.0.1 (C10 Worker 로컬 API, 로컬 런타임) | 넣지 않는다 | 네트워크를 건너지 않는다 |
| Bot UI·서버 실행기 ↔ Center (C4·C12) | 넣지 않는다 | 이미 현장 → Center다 |
| 모델 호출 (`core.llm`, 서비스 앱의 `ServiceLlm`) | 넣지 않는다 | 리소스로 등록하는 기능이 아니라 실행하는 쪽의 설정이다. > 미정: 따로 정한다 |
| 보내기 (`chk:send` 메일·웹훅) | 넣지 않는다 | 기다릴 결과가 없는 알림이고 허용 호스트는 운영자가 적는다. > 미정: 따로 정한다 |
| 서비스 앱 콘솔 → 앱 관리 API (`/admin/v1/*`) | 넣지 않는다 | BPM 프로세스의 길이 아니라 운영자가 앱 옆에 띄우는 화면이다 |

### 2. BPMN은 그대로다

`chk:serviceCall`의 `app_id`·`operation`·`input`·`output`·`timeout_s`·`retry`는 뜻이 그대로이고 **`app_id`가 토픽**이다. 그림을 다시 그리지 않는다. **`key_ref`와 `chk:process.service_keys`는 쓰는 곳이 없어진다** — 읽고 무시하다가 C14 판을 올릴 때 지운다(그동안 B-검사가 경고 한 줄로 말한다).

### 3. 일꾼

- **서비스 앱은 일꾼이 된다.** `service_kit`이 `POST /v1/ops/{operation}` 대신 **가져가기 루프**를 돌리고 같은 작업 함수를 부른다. 앱 안의 C11 키(해시 보관·`/v1/keys/self`·`/center/v1/keys`)는 없어진다 — 「누가 불러도 되나」는 Center가 가린다 (§5).
- 일꾼은 **Center가 승인해 들인다** — Bot UI·서버 실행기와 같은 요청 코드 승인이다(ADR-0092 §1). 승인하면 토큰을 그 일꾼의 공개키로 봉해 준다. 일꾼은 들일 때 **manifest(작업·스키마·수행 모드)와 기여 자원 카탈로그를 올린다** — Center가 앱을 읽으러 가지 않는다. 판이 바뀌면 다시 올린다.
- 한 토픽에 일꾼이 여럿이어도 된다(늘리기). 한 일감은 한 일꾼에게만 잠긴다.
- **최소 한 번 실행이다.** 잠금이 지나면 일감이 다시 나간다. 일꾼은 C11 멱등 키 여섯 칸으로 **스스로** 한 번만 수행한다 — `service_kit`이 이미 가진 멱등 저장소가 그 일을 한다. 계약은 이것을 맨 앞에 적는다.

### 4. 외부 앱은 어댑터 일꾼이 맡는다

- Chaeksas가 **범용 어댑터 일꾼**(`chk-adapter-consumer`)을 준다. 외부 확장 정의(C13)의 HTTP 어댑터 — 템플릿·제한 JSONPath·`error_when`·관문 — 를 지금 `core.http_adapter` 그대로 돌린다. 외부 시스템 쪽 코드는 필요 없다.
- **외부 앱의 주소·키는 어댑터 일꾼의 설정에만 있다** (환경변수 또는 그 PC의 OS 비밀 저장소, 확장마다 하나). Center는 외부 앱 키(운영·시험용)를 들지 않고 외부 확장 주소도 덮어쓰지 않는다. 인증 방식을 늘리는 일(OAuth 갱신·mTLS)은 **어댑터 일꾼 안에서** 한다 — BPM 쪽과 Center는 모른다.
- 어댑터 일꾼은 외부 앱이 있는 망 안에 띄워도 된다(나가는 연결만 있으면 된다). 그 망은 사설 IP라 **사설망 허용은 어댑터 일꾼 설정의 명시 스위치**로 연다(기본은 닫힘 — ADR-0059 §2와 같은 결).
- 정의는 여전히 Center에 등록한다(E6 서명) — 작업 목록·스키마는 STU-14가 고를 거리이고 C7이 보인다. 어댑터 일꾼은 Center에서 정의를 받고 **봉투를 다시 검증한다**.
- 같은 결로, 외부 시스템이 **제 일꾼을 직접 짜도** 된다(C15를 따르면 된다). 어댑터 일꾼은 그 일꾼의 한 구현일 뿐이다.

### 5. 부르는 쪽과 「불러도 되나」

- 부르는 쪽은 **호출 토큰**으로 Center에 올린다. 서버 실행기와 Studio는 제 Center API 키를 쓰고, 실행기 자식 프로세스·Worker·Tool UI는 Bot UI가 받아 넘긴 호출 토큰을 쓴다(지금 서비스 앱 키를 넘기는 그 자리 — 실행기 자식은 파일, Worker는 C10 세션). 호출 토큰은 **올리기·기다리기만** 열린다.
- 실행기 자식 프로세스는 이 토큰으로 **Center를 직접 부른다.** ADR-0031(자식은 Center를 부르지 않는다)의 예외 하나다 — 하트비트 주기만큼 늦어지면 서비스 태스크 하나가 수십 초가 된다.
- 「불러도 되나」는 **Center가 배포에서** 가린다: 그 실행(C3 소유)의 Bot이 그 토픽을 요구하는가(C1), 그 작업이 그 수행 모드를 받는가(manifest), 등록 작업(`registry_write`)이면 그 PC에 「셀렉터 등록」이 켜졌는가(CON-03). 키마다 허용 작업·모드를 달던 일이 배포 하나로 모인다.
- **자율 수행은 Studio에서만** 올라온다(`run_id`가 `test_…`). 현장에서 온 자율 수행은 Center가 거절한다.

### 6. 시험 실행

Studio 시험 실행의 서비스 앱 태스크도 Center에 올린다. 일감에 `origin: test`가 붙고 일꾼이 **시험 쪽으로 보낼지를 스스로 정한다**(어댑터 일꾼은 확장마다 시험용 주소·키를 따로 둘 수 있다). 그래서 **시험용 키라는 개념이 없어진다.** 케이스가 그 호출의 결과를 적어 두면 올리지 않고 그것을 쓴다(PC 위임 `delegations`와 같은 결 — Center에 닿지 않는 시험, 오류 경계 시험).

### 7. 조각 순서

1. **C15 합의** — 계약 모델, Center의 외부 작업 표(마이그레이션 한 단계)·API·롱폴링, 일꾼 승인.
2. **서비스 앱** — `service_kit` 가져가기 루프, 모의 앱 13개, 부르는 쪽 셋(서버 실행기·실행기 자식·Studio)의 `ServiceCaller` 구현을 Center로. 엔진은 그대로다(부르는 쪽이 결과를 기다린다). M3·M5·M7 묶음이 초록이어야 다음으로 간다.
3. **어댑터 일꾼** — 외부 앱 둘(모의), Center의 외부 앱 키·주소 덮어쓰기 걷기.
4. **UI 자동화** — 계획·치유·보고·등록·카탈로그를 외부 작업으로, Worker·Tool UI가 호출 토큰으로. M4 묶음.
5. **화면** — CON-07(주소·키 칸 → 일꾼 승인·토픽 상태), STU-10(서비스 앱 표·개발 키), TOL-02. 화면 문서를 먼저 고친다.
6. **긴 작업** — 서버 실행기가 외부 작업을 기다리는 동안 스레드를 놓는다(다섯째 기다림). 그때까지는 `timeout_s`가 C11과 같은 상한이다.

한 조각이 끝날 때마다 옛 길(C11 `/v1/ops`, 어댑터 직접 호출, 서비스 앱 키 배달)을 **그 조각에서 걷는다** — 두 길을 나란히 두지 않는다.

## 결과

- 쉬워지는 것:
  - Center 콘솔에서 **바깥 기능의 주소·키를 넣는 칸이 모두 없어진다.** 남는 것은 일꾼 승인과 토픽 상태다.
  - 외부 시스템의 인증이 아무리 복잡해도 일꾼 안의 일이다. 키를 바꿔도 BPM 쪽·Center는 모른다.
  - 서버 실행기가 닿지 못하는 사내망 시스템을 붙일 수 있다. 긴 작업을 정식으로 기다릴 수 있다(조각 6).
  - 「누가 무엇을 불러도 되나」가 배포 한 자리에 모인다.
- 어려워지거나 포기하는 것:
  - **Center가 바깥 호출의 길목이 된다.** Center가 멈추면 서비스 태스크·치유도 멈춘다(지금은 그 앱만 살아 있으면 됐다). 계획 캐시는 그대로 살아 있고, 치유를 못 받으면 지금처럼 **전환**이다.
  - **Center가 업무 값을 잠깐 든다** — 일감의 입력과 결과다. 원칙 6의 예외를 넓히는 일이라 위임 결과(ADR-0062)와 같이 다룬다: 결과를 부른 쪽이 받으면 값을 지우고, 못 받은 것은 7일에 지운다. 누가·언제·성패는 남는다.
  - 호출마다 Center를 한 번 더 거친다. 롱폴링이라 양쪽이 대기 중이면 지연은 짧지만 0은 아니다. 치유처럼 스텝 도중 부르는 것이 가장 민감하다.
  - 일꾼을 상시 띄워야 한다. **아무도 가져가지 않으면 조용히 쌓이므로** 기한이 지나면 `no_consumer`로 업무 실패가 되고(오류 경계가 받는다) 콘솔이 「이 토픽을 가져가는 일꾼이 없다」를 보인다.
  - 롱폴링이 Center의 연결을 오래 붙잡는다. 일꾼 수에 상한을 두는 설정이 필요하다(SQLite인 지금 구성 — ADR-0070).
  - 계약 여럿이 판을 올린다(C11·C13·C14·C10). 조각마다 시험 묶음을 다시 돌린다.
- 대체하는 것: [ADR-0094](0094-service-app-keys-ride-the-deployment.md) 전체(서비스 앱 키를 배포가 데리고 다닌다), [ADR-0097](0097-external-extension-address-from-center.md)(외부 확장 주소를 Center가 덮어쓴다), [ADR-0052](0052-service-app-key-notices.md)(서비스 앱 키 알림), [ADR-0091](0091-external-apps-without-auth-take-no-key.md)(키를 받지 않는 외부 앱 — 키를 다루는 쪽이 어댑터 일꾼이 된다), [ADR-0092](0092-keys-are-issued-and-delivered-by-center.md) §3·§4(서비스 앱 키·외부 앱 키). **옛 ADR이 말하는 것이 지금 코드다** — 조각이 그 자리를 걷을 때까지 코드는 옛 ADR대로 돈다.
- 넓히는 것: [ADR-0007](0007-client-initiated-communication.md) — 「연결은 늘 현장 → 서버」를 **서버 사이에도** 쓴다. 「서비스 앱에는 작업 배분 기능을 두지 않는다」는 그대로다 — 배분은 Center가 한다.
- 다시 볼 조건: 치유 지연이 스텝 시간 제한을 자주 넘기면(Worker → UI 자동화 앱만 직접 길을 되살리는 것을 검토한다). Center 한 대로 롱폴링 연결을 감당하지 못하면.
