## 배경

연동하는 회사 시스템(NowView)은 「누가 어떤 업무를 맡고, 무엇이 그 업무를 시작시키나」를 Center 한 화면에서 보고 싶어 한다. 지금 Center에는 업무 주체가 **가상 직원**(ADR-0085)뿐이다. 가상 직원은 접수 BPM 프로세스 하나와 감독자 이름을 묶은 특별한 자원이라, 사람이 맡는 업무나 자동 업무를 여럿 가진 주체를 그릴 수 없다. 바깥에서 보면 「감독자에 사람 이름, 가상 직원에 접수 묶음 이름」이 섞여 보인다.

사용자가 정한 모양은 이렇다. Center에 업무 주체가 있고, 주체마다 BPM 프로세스(업무)가 등록되며, **사람인지 가상인지 가르지 않는다**. 업무는 시간·바깥 사건(시간 + 서비스 태스크)·**다른 주체의 요청**으로 시작한다. 요청에는 **기다리기**와 **맡기고 끝**이 모두 있다. 같은 회사의 주체끼리는 요청할 수 있고, 받을지 말지는 **받는 쪽 BPM 프로세스가** 거른다(Center·일꾼에 허용 목록을 두지 않는다). 결재 담당은 BPM 프로세스가 회사 규칙으로 정한다. Center와 회사 시스템은 서로 의존하지 않는다.

이름도 정해야 한다. 요청서는 「계정」(`account`)이라 불렀지만 그 말은 이미 **관리자 계정**(ADR-0090, 콘솔에 들어오는 아이디)이 쓰고 있다.

## 선택지

**이름**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 직원 (`staff`)** | 사람과 가상을 가르지 않는 낱말이다. 「가상 직원」이 그대로 「직원」으로 접힌다 | 요청서와 낱말이 다르다 |
| B. 업무 계정 (`work_account`) | 요청서의 말을 살린다 | 화면에 「계정」이 두 종류로 보인다 |
| C. `account`를 이것에 주고 관리자를 `user`로 | 요청서와 같다 | 머지된 ADR-0090·CON-14·코드 이름을 다시 바꾼다 |

**회사**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 직원에 `company` 칸 하나** (글자 id, 회사 자원 없음) | 요청 관문 하나만 본다. 회사 시뮬레이터처럼 한 Center에 회사가 둘인 경우도 된다 | 배포·키·콘솔은 회사로 나누지 않는다 — 멀티테넌트가 아니라는 것을 분명히 적어야 한다 |
| B. Center 한 벌 = 회사 하나 | 칸이 없다 | 회사가 둘이면 Center를 둘 띄운다 |

**요청의 관문**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 서명된 `requires.delegations` + 같은 회사** | 「이 패키지가 무엇을 부를 수 있나」를 승인하는 사람이 본다(C2 「서명이 유일한 관문」 그대로). 목록은 Studio가 그림에서 모아서 사람이 따로 적지 않는다 — Center·일꾼의 허용 목록이 아니다 | 부를 BPM 프로세스는 그림에 적어야 한다 |
| B. 같은 회사면 아무 업무나 | 그림이 더 자유롭다 | 서명된 패키지가 무엇을 부를지 승인하는 사람이 미리 볼 수 없다 — 서명보다 약한 관문이 생긴다 |

**받는 직원을 어떻게 정하나**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 식(선택), 비우면 Center가 고른다** — `bot_ui`와 같은 결 | 배포마다 그림을 고치지 않는다. 담당이 하나면 적을 것이 없다 | 여럿이면 고르지 않은 것이 오류가 된다 |
| B. 그림에 id 글자 | 읽기 쉽다 | 직원 id가 바뀌면 패키지를 다시 낸다 |
| C. 늘 입력으로 | 부르는 쪽이 정한다 | 늘 매핑을 적어야 한다 |

**맡기고 끝(handoff)**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 작업이 만들어지면 끝, 맡긴 실행은 따로 산다** | 기억할 것이 없다. 실패 격리 — 맡긴 쪽이 끝나도 받은 쪽은 제 일을 한다 | 요청한 실행을 취소해도 맡긴 일은 거두지 않는다 |
| B. 취소가 따라간다 | 「요청 취소」가 된다 | 맡긴 작업을 기억할 자리가 필요하고, 요청한 실행이 끝난 뒤에는 어차피 따라갈 수 없다 |

**결재 담당자 값**: A. 지금처럼 글자(ADR-0080) / B. 직원 id. **B16**: A. Studio 경고만 / B. 직원 업무에 Center 관문. **업무 공유**: A. 여러 직원이 같은 업무를 가진다 / B. 업무 하나에 직원 하나.

## 결정

**이름은 직원(`staff`), 회사는 직원의 칸 하나, 요청 관문은 서명 + 같은 회사, 받는 직원은 식(비우면 Center가 고른다), 맡기고 끝은 따로 산다, 담당자는 글자 그대로, B16은 Studio 경고만, 같은 업무를 여러 직원이 가진다.** 모두 A다. 가상 직원 자원은 없앤다.

### 1. 직원 (Center 자원)

| 칸 | 뜻 |
| --- | --- |
| `id` | `^[a-z0-9][a-z0-9._-]{0,63}$`. 주체 이름은 `staff:<id>`이고 예약 앞머리다(ADR-0081의 `on_behalf_invalid`가 막는다 — `vw:`를 대신한다) |
| `name` | 화면 이름. 아무 글이나 된다(사람 이름이어도, 「구매 자동 처리」여도) |
| `company` | 회사 id(`^[a-z0-9][a-z0-9._-]{0,63}$`). **회사 자원은 없다** — 같은 글자면 같은 회사다 |
| `state` | `active` / `stopped`. **멈춘 직원 앞으로는 새 작업이 생기지 않는다** — 일정은 그 직원 몫을 만들지 않고, 요청·작업 지시는 거절한다(409 `staff_stopped`). 이미 도는 실행은 그대로다. 가상 직원의 `stopped`(표시뿐)와 다르다 |
| `work[]` | 그 직원의 업무 — **BPM 프로세스 id**(패키지 id) 목록. 판은 적지 않는다(배포가 정한다). **배포 뒤에 고친다** — 서명된 패키지·봉투는 직원을 모르고, 묶음을 바꿔도 패키지·배포를 다시 내지 않는다 |

- **직원은 로그인하지 않고 결재 권한도 없다.** 콘솔에 들어오는 것은 관리자 계정이고(ADR-0090), 회사 시스템이 사람 대신 답하는 길은 대리 답용 키 + `X-CHK-On-Behalf-Of`(ADR-0081) 그대로다. 결재 담당은 BPM 프로세스가 정한다(§5).
- **업무로 등록할 수 있는 것은 Center에 있는 BPM 프로세스 패키지**(`kind=bpm_process`)다. 승인된 판이 없어도 묶을 수 있다(배포 순서를 막지 않는다). 없는 id는 422 `work_unknown`이다.
- **같은 업무를 여러 직원이 가진다.** 같은 절차를 회사 둘의 직원이 쓰면 직원마다 실행이 갈린다.
- 쓰기(`POST`·`PUT`·`DELETE /staff`)는 **관리자**(콘솔 세션·관리자 토큰)다. 서명은 없다 — 직원은 실행을 허용하지 않는다(그것은 배포 봉투의 일이다). 지우면 등록만 사라지고 실행·작업에 남은 id는 그대로다.
- 읽기는 읽기·관리자 토큰과 **연동용 키**(전부 — ADR-0098 §4와 같은 까닭)다. **대리 답용 키는 읽지 못한다** — 「감독자」가 없어져 거를 기준이 없다.

### 2. 작업은 누구의 일인가 — `staff`

- 작업(`POST /jobs`)·메시지 시작(`POST /messages`)의 선택 칸 **`staff`**(직원 id)가 `virtual_worker`를 대신한다. 그 직원이 이 업무를 가져야 한다(아니면 422 `staff_mismatch` — 없는 id도 같다). 멈춘 직원이면 409 `staff_stopped`다.
- **비우면** 그 업무를 가진 **활성 직원이 정확히 하나**일 때 그 직원이다. 없으면 **직원 없음**이고 지금과 같다(어느 직원에게도 묶이지 않은 업무는 그대로 돈다). 여럿이면 직원 없음 — 조용히 고르지 않는다(ADR-0099 §2와 같은 규칙).
- 고른 id는 작업 행에 남는다(`JobInfo.staff`). 실행이 누구의 일인지는 **Center가 읽을 때** 그 실행의 작업에서 붙인다(`RunInfo.staff` — C3 `run_started`에 칸을 더하지 않는다. `bot_ui_of`와 같은 결). 그래서 CON-01에 「직원」 열이 생긴다.
- **값 출처**(C14 `chk:process.inputs[].source`)는 `staff.id`·`staff.name`·`staff.company`다. `virtual_worker.*`는 없앤다(`supervisors`는 갈 곳이 없다 — 담당은 그림이 정한다). Center가 서버 작업을 내려줄 때 `JobDispatch.staff = {id, name, company}`를 붙이고 저장하지 않는다(ADR-0098 §2 그대로). PC 작업에 싣는 길은 ADR-0099 §3의 「미정」 그대로다.

### 3. 요청 — 위임을 넓힌다

요청은 새 요소가 아니라 **위임(`chk:call.delegate`)에 칸 둘을 더한 것**이다. 대상 패키지의 실행 위치가 PC·서버를 가르는 것(ADR-0082 §1)과 멱등·`requested_by`·결과 보관은 그대로다.

```json
{"delegate": {"bpm_process_id": "buy.request", "staff": "구매담당", "mode": "handoff"},
 "input": {"품목": "품목", "요청자": "내직원ID"}}
```

| 칸 | 뜻 |
| --- | --- |
| `staff` | **받는 직원을 정하는 식**(`bot_ui`와 같은 `chk-expr` 식). 비우면 Center가 고른다(아래) |
| `mode` | `wait`(기본 — 지금 위임 그대로, 결과를 받아 잇는다) / `handoff`(작업이 만들어지면 바로 다음으로 간다) |

**관문 — 서명 + 같은 회사** (Center가 위임 요청을 받을 때 본다)

1. 부를 BPM 프로세스는 **서명된 매니페스트의 `requires.delegations`**에 있어야 한다 — 지금처럼 Studio가 그림에서 모으고 배포 때 승인됐는지 본다(C12). Center·일꾼에 따로 된 허용 목록은 없다.
2. 요청한 실행의 직원을 R(그 실행 작업의 `staff`, 없을 수 있다), 받는 직원을 T라 하면:
   - `staff`를 적었으면 T는 그 직원이고, **그 업무를 가져야** 하며(422 `staff_mismatch`) **활성이어야** 하고(409 `staff_stopped`), **R이 있고 R과 같은 회사**여야 한다(403 `company_mismatch`).
   - 비웠으면 그 업무를 가진 활성 직원 중 **R과 같은 회사인 것**에서 고른다. 하나면 그 직원, 여럿이면 422 `staff_ambiguous`. 하나도 없을 때 — 그 업무를 **아무 직원도 갖지 않았으면** 직원 없이 지금 위임 그대로 가고(T는 R을 이어받는다 — ADR-0099 §3의 「맡긴 일은 맡긴 쪽의 일」), **다른 회사 직원만 가졌으면** 403 `company_mismatch`다(빈칸으로 회사 관문을 비켜 가지 못한다).
3. 그 밖의 거절은 **받는 쪽 BPM 프로세스가** 입력(요청자 등)을 보고 제 그림에서 끝낸다. 거절 결과는 `wait`이면 `outputs`로 돌아온다(ADR-0082 §3의 「업무 결과는 자식이 돌려준다」).
4. 관문에 걸린 요청은 지금 위임 거부와 같이 **업무 실패**(`DELEGATION_FAILED`)로 오류 경계가 받는다.

**맡기고 끝** (`mode: handoff`)

- 엔진은 위임 포트가 작업 id를 돌려주면 **기다리지 않고** 다음으로 간다. 작업을 만들지 못하면(관문·`no_deployment`·닿지 못함) 업무 실패다.
- **결과는 Center를 지나지 않는다** — 원칙 6의 예외(ADR-0062 §4)를 쓸 까닭이 없다. 그래서 그림은 `chk:call.output`을 적을 수 없다(B14 오류). Center는 handoff 작업의 `outputs`를 받아도 담지 않고 `delegations[]`로 내려보내지 않는다.
- **요청한 실행이 취소돼도 거두지 않는다**(ADR-0062 §5의 거두기는 `wait`만이다). 맡긴 실행은 받는 직원의 일로 따로 산다.
- 멱등 키는 지금 위임 그대로다(`dlg_<run_id>_<node_id>_<node_instance>[_<loop_index>]`) — 되살린 실행이 다시 요청해도 같은 작업이다. 반복 안에서도 된다.
- 기록: 받은 쪽 `run_started`의 `source: delegation`·`parent_run_id`, 작업의 `requested_by = server_bot:<run_id>`가 지금처럼 남아 CON-01·CON-13이 오간다. 새 C3 이벤트는 없다.
- 위임이 서버 그림에서만 된다는 것(C1 R10·B14)은 그대로다. PC 실행이 맡기고 끝으로 요청하는 길은 > 미정이다(기다리지 않으므로 ADR-0062가 막은 「서로 기다림」은 없지만, PC 실행 프로세스에 위임 포트가 없다).

### 4. 일정은 직원마다 (ADR-0110 §1을 넓힌다)

- 타이머 시작이 있는 업무를 **활성 직원이 가지면, 차례마다 그 직원마다 작업 하나**를 만든다(`staff`가 찬 작업). 서버는 (BPM 프로세스, 판, 직원)마다, PC는 (배포된 PC, 직원)마다다. 일정을 잡는 기본 키와 멱등 키에 직원 id가 들어간다.
- 그 업무를 **아무 직원도 갖지 않으면** 지금 그대로(직원 없이 한 번). 가진 직원이 **모두 멈췄으면** 만들지 않는다 — 멈춘 직원의 업무는 서 있어야 한다.

### 5. 결재 담당은 그대로 — 글자

`chk:approval.assignees`는 ADR-0080 그대로 이름 글자 목록(또는 그 변수)이다. **무엇을 적을지는 BPM 프로세스가 회사 규칙으로 정한다** — 서비스 태스크가 회사 시스템에서 결재자를 읽어 변수로 두고 `assignees`가 그 변수를 쓴다. Center는 직원·회사로 담당을 바꾸거나 직원 명부와 대조하지 않는다. 회사 시스템이 직원 id를 담당자 글자로 쓰고 싶으면 그렇게 적으면 된다.

### 6. 가상 직원을 접는다

- `virtual_workers` 자원·`/virtual-workers` API·`?virtual_worker=` 거르기·`JobCreateRequest.virtual_worker`·`JobDispatch.virtual_worker`·값 출처 `virtual_worker.*`를 없애고 위의 `staff`로 바꾼다. 저장소는 옮기기 단계 하나로 가상 직원 행을 직원 행으로 옮긴다(`id`·`name` 그대로, `work = [intake]`, `company`는 옮기는 사람이 정하는 기본값 — > 미정: 운영 중인 Center에 가상 직원이 있으면 옮기기 전에 회사 id를 받는 길).
- **Center의 B16 관문(`intake_unknown`·`intake_not_server`·`intake_not_gated`)을 없앤다.** 「결재 없는 일괄 기동」은 Studio 실행 전 검사의 C14 **B16 경고**로만 남는다 — 사람 없이 밤마다 도는 일괄도 올바른 그림이고, 받을지는 BPM 프로세스가 정한다는 원칙과 맞춘다. Center가 BPMN을 읽는 자리는 이것 하나였으므로 Center는 다시 그림을 읽지 않는다.
- 「최근 일괄」은 직원 상세의 「최근 실행」과 「요청」이 대신한다(§7).

### 7. 화면 — CON-13 직원

CON-13 「가상 직원」 자리를 「직원」이 대신한다(메뉴 「업무 › 직원」). 목록(이름·회사·업무 수·상태·최근 실행)과 상세 한 장 — 위에서 아래로 **업무**(BPM 프로세스·판·시작 방법(일정식·요청 받음·메시지)·빼기, 더하기)·**최근 실행**·**요청**(받은 / 보낸)·**열린 결재**(그 직원 실행의 것)다. 모두 Center가 읽을 때 센다(저장하지 않는다). 자세한 배치는 `docs/06-screens/center-console.md` CON-13.

## 요청서와 어긋난 것

| 요청서 | 이 ADR |
| --- | --- |
| R1 이름 `accounts` | `staff` — `account`는 관리자 계정의 것이다 |
| R2 실행이 `account`를 갖는다 (C3 `run_started`) | C3에 칸을 더하지 않고 Center가 읽을 때 작업에서 붙인다 (`RunInfo.staff`) |
| R2 작업의 `requested_by`도 그 계정 | `requested_by`는 **부른 쪽**이 그대로 적힌다(키·사람·`timer:`·`server_bot:`). 「누구의 일인가」는 따로 된 칸 `staff`다 (ADR-0085가 이미 가른 둘) |
| R3 그림의 대상을 「계정 + 업무」로, 허용 검사는 회사 하나 | 대상은 여전히 BPM 프로세스 id이고(서명된 `requires.delegations`), 직원은 식으로 고른다. 회사 검사는 그 위에 더한다 |
| R3 거절 코드 `company_mismatch` | 같다 (403) |
| R5 B16을 계정 업무 전반에 걸지 | 걸지 않는다 — Studio 경고만 |

## 결과

- 이 결정으로 쉬워지는 것: 「누가 어떤 업무를 하고 무엇이 그것을 시작시키나」가 CON-13 한 화면이다. 사람이 맡는 업무와 자동 업무가 같은 모양이다. 같은 회사 직원끼리 기다리며 또는 맡기고 끝으로 업무를 주고받는다. 회사 시스템은 지금처럼 일꾼(C15)과 연동용 키로만 만난다.
- 어려워지거나 포기하는 것: 가상 직원의 감독자 칸이 사라져 「감독자에게 진행을 보인다」(ADR-0085 §3)는 대리 답용 키로는 안 된다 — 연동용 키로 읽어 회사 시스템이 제 규칙으로 보인다. 결재 없는 일괄을 Center가 막지 않는다. 회사는 요청 관문 하나에만 쓰인다 — 배포·키·콘솔은 회사로 나뉘지 않고 관리자는 모든 회사를 본다. 맡기고 끝은 취소가 따라가지 않는다.
- 다시 볼 조건: ① 한 Center를 서로 모르는 회사들이 함께 쓰게 되면 — 배포·키·콘솔을 회사로 나누는 일을 ADR로 연다(ADR-0062 「같은 Center를 여러 조직이」와 같은 조건). ② 직원이 직접 로그인해 제 결재함을 봐야 하면 — 관리자 계정과 직원을 잇는 일을 연다. ③ 「요청을 취소한다」가 업무에서 나오면 맡기고 끝의 거두기를 다시 본다. ④ PC BPM 프로세스가 맡기고 끝으로 요청해야 하면 위임 포트를 PC에도 꽂는다.
