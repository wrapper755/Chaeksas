# ADR-0069. Studio·Bot UI의 판은 사람이 설치 파일로 다시 깔아 올린다 — Center는 판을 보여 줄 뿐 내려 주지 않는다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-10-17) |
| 날짜 | 2026-10-17 |
| 관련 | [ADR-0067](0067-build-stamp.md)(판), [ADR-0068](0068-installer-inno-setup-per-user.md)(설치 파일), [ADR-0014](0014-one-bot-per-pc.md)(PC에 Bot 하나), [ADR-0023](0023-bot-ui-process-supervision.md)(자식 프로세스·자동 시작), 계약 C2·C4 |

## 배경

「판 올리기」는 **프로그램**(Studio·Bot UI — Worker는 Bot UI와 같은 실행 파일이라 함께 간다)의 판을
올리는 일이다. **Bot(BPM 프로세스)의 판은 이 일이 아니다** — 그것은 이미 Center 배포(C2 서명 봉투 → C4
하트비트 → Bot UI 설치)로 오간다.

ADR-0067로 Center는 PC마다 **어느 산출물이 도는지** 안다(C4 `versions.bot_ui`·`build`, CON-03).
ADR-0068로 조용한 설치·같은 `AppId` 덮어쓰기·옛 `_internal` 지우기가 생겼고, 덮어써도 사용자 데이터
(설정·설치한 Bot·실행 기록)는 남는다. 남은 물음은 **새 판을 누가, 언제, 어떻게 현장에 넣는가**다.

조건 둘: 설치 파일은 그 PC 사용자 권한으로 무엇이든 하는 **코드**다. 그리고 코드 서명 인증서가 없다
(ADR-0068 §5). 서버 실행기는 묶지 않으므로(ADR-0067 §3) 이 결정 밖이다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. **사람이 설치 파일로 다시 깐다** — 언제 깔지도, 실패하면 어떻게 할지도 사람이 정한다 | 새 계약·새 관문이 없다. 처음 설치와 같은 파일·같은 길이다. 현장 PC가 코드를 **받을 길 자체가 없다** | PC가 많아지면 판이 흩어지고 사람이 PC마다 가야 한다 |
| B. Center가 설치 파일을 들고 하트비트로 내려 주고, Bot UI가 빈 때 스스로 깐다 | 한 화면에서 모든 PC의 판을 맞춘다 | Center가 현장 PC에 **코드를 밀어 넣는 길**이 생긴다 — Center를 쥔 사람이 모든 PC에서 코드를 돌리지 못하게 **Admin 서명 봉투**(C2에 `kind: installer`)로 막아야 한다. 계약 셋(C2·C4·C5)·저장소 표·화면이 늘고, 스스로 다시 뜨기(Job Object 밖에서 설치 파일 띄우기)·실패 감지를 우리가 짠다 |
| C. 바깥(GitHub Releases·사내 파일 서버)에서 Bot UI가 스스로 받는다 | Center가 큰 파일을 들지 않는다 | B의 위험을 그대로 지고, 현장 PC가 새 바깥 주소에 닿아야 한다 |

## 결정

**A를 쓴다.** Studio·Bot UI 모두 **사람이 설치 파일을 받아 다시 깐다.** 언제 깔지, 실패하면 무엇을 할지는
사람이 정한다. 플랫폼은 **판단할 거리를 보여 주는 것**까지 한다.

### 1. 설치 파일은 하나다 — 처음 설치와 판 올리기가 같다

산출물 워크플로가 만든 설치 파일(ADR-0068)을 그대로 돌린다. 같은 `AppId`라 **덮어쓰기**가 되고, 옛
`_internal`을 지운 뒤 깔며, 사용자 데이터 자리는 건드리지 않는다. 판 올리기용 설치 파일을 따로 만들지 않는다.

### 2. 언제 깔지는 사람이 본다 — 플랫폼은 볼 거리를 준다

설치 파일은 실행 중인 Bot UI를 **닫고** 깐다(Restart Manager). Bot UI가 닫히면 실행기도 함께 끝나
(Job Object, ADR-0023) **도는 Bot과 대기열을 잃는다**(C4 `bot_ui_lost`). 그래서 **도는 Bot도 대기열도 없을
때** 깐다 — 그 판단은 사람이 하고, 볼 자리는 이미 있다:

- **CON-03** — PC마다 판(`versions`)·「실행 중」·「대기열」을 보인다.
- **CON-03 「비활성화...」** — 그 PC에 새 작업·배포를 **보내지 않고**(작업은 Center에서 `pending`으로
  기다린다) 도는 Bot은 끝까지 돈다(C4 `disabled`). **깔기 전에 걸어 두면 비는 때를 만들 수 있다.**
- **Bot UI 트레이·BUI-01** — 현장 사람은 「실행 중인 Bot 없음」을 직접 본다.

순서는 `docs/04-setup.md` §6-3에 적는다. 결재를 기다리는 Bot이 있으면 끝날 때까지 기다릴지, 멈추고 깔지도
사람이 정한다(멈추려면 BUI의 「중지」 — `cancelled`가 기록에 남는다).

### 3. 관문은 사람이다 — 서명 봉투를 두지 않는다

Center가 코드를 내려 주지 않으므로 C2에 `installer` 봉투를 더하지 않는다. 설치 파일을 **어디서 받았는가**가
관문이고, 받는 자리는 **산출물 워크플로가 올린 것**(`installers-windows`) 하나로 정한다. **프로그램이 돌 때의
인증은 그대로다** — Bot UI는 Center API 키로 Center에 닿고(ADR-0013), Bot 패키지는 서명 봉투로만 깔린다(C2).
판 올리기가 이 둘을 바꾸지 않는다.

### 4. 실패하면 사람이 다시 깐다 — 되돌리기는 옛 설치 파일로

깐 뒤 **CON-03에서 그 PC의 판이 바뀌었는지** 본다(새 판이 첫 하트비트에 `versions`를 올린다 — 바뀌었을 때
보내는 칸이다, C4). 뜨지 않거나 문제가 있으면 사람이 **옛 판의 설치 파일로 다시 깐다**(Inno Setup은 낮은
판 덮어쓰기를 막지 않는다).

**옛 설치 파일은 사람이 들고 있다.** 산출물 워크플로는 설치 파일을 **30일** 남긴다(`desktop.yml`의
`retention-days` — GitHub 기본값 90일보다 짧게 적어 두었다). 그 뒤에도 되돌릴 판이 필요하면 받아 둔
설치 파일을 사람이 보관한다 — 플랫폼은 옛 판을 따로 남기지 않는다.

### 5. 판이 섞여 도는 것을 받아들인다

PC마다 사람이 따로 올리므로 **여러 판의 Bot UI가 한 Center에 붙는다**. 계약의 호환 규칙(값 목록은 열린
문자열, 새 칸은 선택 칸 — C4 「호환 규칙」)이 그것을 지금도 지킨다. 계약을 바꿀 때 **옛 Bot UI가 그대로
읽히는가**를 지금처럼 본다 — 판 올리기를 사람에게 맡긴 만큼 이 규칙의 무게가 크다.

## 결과

- 쉬워지는 것: 계약·Center·Bot UI에 새 코드가 없다. 현장 PC가 코드를 받을 길이 없어 Center가 뚫려도
  현장에서 코드를 돌리지 못한다. 처음 설치·Intune 배포·판 올리기가 같은 파일이다.
- 어려워지거나 포기하는 것: 사람이 PC마다 간다. 비는 때를 사람이 만들어야 하고(비활성화), 실패도 사람이
  알아차린다. Studio는 Center와 하트비트를 주고받지 않으므로 **Center가 Studio의 판을 모른다**.
- 다시 볼 조건:
  - **PC가 많아져 사람이 다 갈 수 없으면 B를 다시 본다.** 그때는 Center가 코드를 내려 주는 길이라
    **Admin 서명 봉투가 관문이어야 한다** — 설치 파일 해시를 Admin 키로 서명하고, 받는 쪽이 해시·서명·
    「더 높은 판인가」(되돌리기 금지)를 본 뒤에만 깐다. 배포 봉투(C2)와 같은 결이다.
  - 사람이 설치 파일로 현장 PC에 넣어 보는 일(M6의 둘)에서 SmartScreen·백신 오탐이 판 올리기를 막으면
    인증서(ADR-0068 §5)를 먼저 본다.
  - 판이 섞여 계약 호환이 실제로 깨지면 Center가 **받아 줄 가장 낮은 판**을 정하는 것을 본다.
