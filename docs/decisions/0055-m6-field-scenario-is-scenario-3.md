# ADR-0055. M6의 현장 기준은 시나리오 3 하나다 — 서버 Bot인 1·2·4는 M7 인수 시험이 덮는다

| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-10-13 |
| 관련 | [ADR-0016](0016-server-first.md)(서버 우선), [ADR-0015](0015-run-location.md)(실행 위치), `docs/00-vision.md` §성공 기준, `docs/05-roadmap.md` M6·M7, `docs/09-gaps.md` §6, 계약 C12 |

## 배경

M6의 첫째 기준은 「시나리오 1~4(`00-vision`)가 Windows 현장 PC에서 Center 배포를 거쳐
통과」다. 이 문구는 프로토타입 시절에 적혔고, 그때 네 시나리오는 모두 PC에서 돌았다.

그 뒤 서버 우선(ADR-0016)으로 예제를 옮기면서 **넷 중 셋이 서버 Bot이 되었다** — 시나리오와
예제의 짝은 1 = BX-10, 2 = BX-20, 3 = BX-04, 4 = BX-30이고 실행 위치가 `pc`인 것은 BX-04
하나다. 서버 Bot을 Center로 배포하면 현장 PC가 아니라 **서버 실행기**로 가고, 서버 실행기가
작업을 돌리는 것은 M7이다 (C12). 그래서 문구 그대로는 1·2·4가 M6에서 **성립할 수 없다**
(09-gaps §6-1, Windows 11 PC에서 대 보다 드러났다).

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. M6를 시나리오 3으로 좁히고 1·2·4는 M7 인수 시험이 덮는다 | M6가 M7을 기다리지 않는다. 현장 PC에서만 볼 수 있는 것(UI 태스크·UIA·Bot UI·Center 배포)은 시나리오 3이 다 담는다 | 「네 시나리오를 현장에서」라는 첫 그림은 M7 끝에야 채워진다 |
| B. M6가 M7을 기다린다 | 문구를 바꾸지 않는다 | 첫 릴리스가 서버 실행기 전체에 묶인다. 현장 PC에서 이미 볼 수 있는 것도 미뤄진다 |
| C. 1·2·4의 PC 판을 따로 둔다 | 문구를 지킨다 | 예제를 기준에 맞게 비튼다 (CLAUDE.md §3-6). 서버 우선과 거꾸로 가는 예제가 셋 생긴다 |

## 결정

**A를 고른다.** M6의 현장 기준은 「**시나리오 3(BX-04)**이 Windows 현장 PC에서 Center 배포를
거쳐 끝까지 돈다」이다. 시나리오 1·2·4(BX-10·BX-20·BX-30)는 **M7 인수 시험**(「실행 위치
서버인 업무·기능 예제 전부가 서버 실행기에서 통과」)이 덮고, 로드맵 M7 줄에 셋의 이름을 적는다.

- 시나리오 3이 M6 기준으로 충분한 까닭: `00-vision`이 처음부터 「첫 끝-끝 목표는 시나리오 3을
  Windows 현장 PC에서」라고 적어 두었다 — 웹 UI 태스크·데스크톱 조작(UIA)·BPMN·Center 배포·
  Bot UI를 한 번에 본다. 1·2·4가 보는 능력(포함 게이트웨이·하위 프로세스·호출·결재)은 **현장
  PC가 아니라 엔진**의 일이고, 인수 시험이 Studio 시험 실행으로 이미 본다 (BX-30은 M3 묶음,
  BX-10·BX-20은 M5 묶음).
- 예제는 바꾸지 않는다.

## 결과

- 쉬워지는 것: M6가 서버 실행기(M7)를 기다리지 않는다. 현장에서 막힌 것은 시나리오 3의 공급사
  포털 하나로 줄어든다 (09-gaps §6-1).
- 포기하는 것: 「네 시나리오가 현장에서 돈다」는 첫 릴리스의 약속에서 빠진다 — M7 끝에 채운다.
- 다시 볼 조건: M7이 M6보다 먼저 끝나면, 1·2·4도 현장 PC에서 Center 배포(서버 실행기)를 거쳐
  함께 돌려 M6 기록에 남긴다. PC에서 돌아야 할 시나리오가 새로 생기면 M6 기준에 더한다.
