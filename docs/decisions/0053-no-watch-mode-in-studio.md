# ADR-0053. Studio에 감시 모드를 두지 않는다 — 일정을 읽는 자리는 현장 하나다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 — 「일정을 읽는 자리」는 [ADR-0110](0110-center-keeps-the-schedule.md)이 **Center**로 정했다(현장의 Bot UI·서버 실행기가 아니다). Studio에 감시 모드를 두지 않는다는 결정은 그대로다 |
| 날짜 | 2026-10-13 |
| 관련 | 화면 STU-01(메뉴·도구 모음)·STU-08, 계약 C14 §이벤트(타이머 시작 `timeCycle`)·C1 `triggers`·C3 `source`·C4 `queue[].source`, [ADR-0014](0014-one-bot-per-pc.md), [ADR-0016](0016-server-first.md), `docs/09-gaps.md` §4-5 |

## 배경

화면 문서가 Studio에 감시 모드를 적어 두었다 — 메뉴 「감시 모드 시작」 ↔ 「감시 중지」
(Shift+F5, 「시작 이벤트가 메시지·타이머·조건일 때」 켜짐), STU-08의 수행 모드 라디오
「감시 모드 — 트리거를 기다렸다 되풀이 실행」. **코드는 라디오를 끈 채 「아직 없다」고
말한다.** 09-gaps §4-5가 그것을 마지막 화면 거리로 들고 있었고, 「먼저 정할 것」은
**「시험 실행이 기다려도 되는가」**였다.

코드를 보니 질문이 그것보다 **앞에** 있었다.

1. **일정을 읽는 자리가 아직 어디에도 없다.** C14는 타이머 시작(`timeCycle`, 5필드 cron)을
   **「서버 실행기·Bot UI의 일정이 이것을 읽는다」**고 적어 두었는데, 그 둘에 cron을 읽는
   코드가 **없다**(Bot UI는 Center 작업·수동 실행만 받는다). Studio에 감시 모드를 만들면
   **일정을 읽는 첫 자리가 개발 도구**가 된다.
2. **엔진은 시작 이벤트가 둘 이상이면 거부한다** (`EngineError` — 「메시지·타이머 시작은 아직
   다루지 않는다」). 그리고 시작 이벤트 하나의 타이머·메시지 정의를 **보지 않는다** — 그냥
   시작한다. 감시 모드가 뜻을 가지려면 그 제약부터 풀어야 하고, 그것은 서버 실행기와 메시지
   시작(C12)의 일이다.
3. **시험 실행에는 판정이 있다.** `CaseRun`은 케이스의 기대값과 비교해 통과/실패를 말하고
   끝난다. 「되풀이」는 **판정이 없는 실행**이고, 그 둘을 한 창에 섞으면 STU-09의 요약
   (「전체 N개 끝: 통과 a, 실패 b」)이 무엇을 세는지 알 수 없다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. Studio에 감시 모드를 만든다 (cron + 시험 수신기 메시지로 되풀이) | 적어 둔 화면대로 된다. 설계자가 「트리거가 오면 도는가」를 눌러 본다 | **일정을 읽는 둘째 자리**가 생긴다(현장에 아직 없는데 개발 도구가 먼저 갖는다) → 「Studio에서는 도는데 현장에서 안 된다」의 새 원천. 판정 없는 실행이 시험 실행 창에 섞인다. 엔진의 다중 시작 제약을 먼저 풀어야 한다 |
| B. **두지 않는다** — 화면에서 걷는다 | 일정을 읽는 자리가 **현장 하나**로 남는다. 시험 실행은 **판정이 있는 한 번**으로 남는다. 트리거가 깨우는 것을 보는 길은 **이미 있다**(케이스의 `messages`, 타이머 경계는 `$now_plus`) | 「타이머가 09:00에 정말 깨우나」는 Studio에서 볼 수 없다 — 현장(M7)에서 본다 |
| C. 미룬다 (라디오를 끈 채 둔다) | 결정을 안 한다 | **지금까지 그래 왔다.** 끈 단추와 「아직 없다」 글이 남아 사람이 올 때마다 다시 묻는다 (U3는 「끄고 까닭을 적는다」지만, 영원히 오지 않을 기능이면 까닭이 아니라 **없는 것**이 맞다) |

## 결정

**Studio에 감시 모드를 두지 않는다.** 메뉴 「감시 모드 시작」·STU-08의 라디오·「감시 중지」
글을 화면 문서와 코드에서 걷는다.

- **트리거가 깨우는 그림은 케이스로 본다.** 메시지로 시작·이어 가는 그림은 시험 케이스의
  `messages`(`after_s`·`name`·`correlation`·`payload`)가 넣어 주고, 기다리는 타이머는
  `$now_plus`로 당긴다 (C14 §시험 케이스 형식). **판정이 있는 한 번**이라는 성질이 그대로다.
- **일정(cron)을 읽는 자리는 현장이다** (C14 §이벤트 그대로). 서버 실행기(C12·M7)와 Bot UI가
  그것을 가지면, 그때 **그 코드를 Studio가 빌려 쓸지**를 다시 본다 — 먼저 만들지 않는다.
- **계약은 바뀌지 않는다.** C3 `source`·C4 `queue[].source`의 `watch`·`schedule`은 **그대로
  둔다** — 현장이 쓸 값이고, 지금 쓰는 쪽이 없다는 것은 열린 문자열 계약에서 정상이다
  (Bot UI의 표기 표에도 이미 있다).
- **엔진의 다중 시작 제약도 그대로** 둔다 — 감시 모드를 위해 풀 이유가 없어졌다. 풀 이유는
  메시지 시작(C12)이고 그것은 M7이다.

## 결과

- **쉬워지는 것:** 시험 실행의 뜻이 하나다(판정이 있는 한 번). 일정을 읽는 코드가 **한 곳에만**
  생긴다 — 현장. 끈 단추 하나와 「아직 없다」 글 둘이 사라진다.
- **어려워지거나 포기하는 것:** 「cron이 정말 그 시각에 깨우나」를 **Studio에서 볼 수 없다.**
  현장에 일정이 생기기 전까지는 작업 지시(C5 `/jobs`)나 수동 실행으로 돌려 본다.
- **다시 볼 조건:** ① **현장에 일정이 생기면**(서버 실행기 또는 Bot UI가 `timeCycle`을 읽기
  시작하면) 그 코드를 Studio가 빌려 「지금 쏘기」·「일정 미리 보기」로 보여 줄지 본다.
  ② **메시지 시작을 엔진이 다루게 되면**(C12) 다중 시작 제약이 풀리고, 그때 「트리거를 기다려
  되풀이」가 **현장의 기능**으로 다시 올라올 수 있다 — 그때도 Studio의 일은 아니다.
