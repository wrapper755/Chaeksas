# 프로토타입에서 배운 것

## 잘 된 것 (지킨다)

1. **바로 돌려 보며 만들기.** 시나리오 1~3을 실제 모델로 돌리며 플랫폼 결함 20여 개(프로토타입 Studio·Bot 백로그 C-11~C-33)를 찾아 닫았다. → 새 저장소에서도 `spikes/`와 시나리오 기반 인수 시험으로 유지.
2. **지도/운전사 경계.** 두 묶음이 독립적으로 같은 결론에 도달했다. → [ADR-0008](../decisions/0008-map-driver-hands-boundary.md).
3. **서명 체인.** 키 생성 → 업로드 → 서명 → 배포 → 설치 → 철회가 끝까지 검증되었다 (2026-09-15). 토큰이 새도 배포는 못 한다.
4. **받는 쪽 관대함.** 프로토타입 계약 v1.3에서 모르는 이벤트 종류를 저장하도록 바꾸자, 서버 변경 없이 새 이벤트를 추가할 수 있었다.
5. **값을 기록하지 않는 원칙.** 실행 기록·패키지에 업무 값·비밀·스크린샷을 넣지 않았다.
6. **로케이터 승격.** 치유 결과를 바로 믿지 않고 `unverified` → 3회 연속 성공 → `active`로 올렸다.

## 시나리오에서 나온 실무 교훈 (프로토타입 Studio·Bot `docs/scenarios.md`)

- 데스크톱 접근성 호출은 하나하나가 비싸다. 후보를 늘리기 전에 한 번의 조회(inspect)로 창이 가진 것을 먼저 본다.
- 뒷정리(창 닫기)가 실행 결과를 망치면 안 된다. 시계가 아니라 창 상태가 판정한다.
- 남은 프로세스는 다음 실행을 오염시킨다 (LibreOffice 단일 인스턴스가 남아 셀 접근이 6~7배 느려짐, C-26).
- 취소는 실패가 아니다. 마감이 끊은 태스크를 실패로 세면 다른 케이스 검증이 지워진다.
- 오래 남는 기록(`training.json`, 요약)이 화면보다 늦게 고쳐진다. 화면 문구를 고칠 때 기록 쪽도 본다.
- **웹 화면을 Streamlit으로 만들어 빨리 볼 수 있었지만**, 상호작용마다 전체가 다시 돌고 권한·토큰 숨기기·모양 맞추기가 어려웠다. 앱마다 화면 모양도 달랐다 → 웹은 Next.js, 모든 화면은 토큰 하나와 스타일 가이드 ([ADR-0017](../decisions/0017-web-nextjs-design-system.md)).
