## BX-10. 신규 거래처 등록 심사

| 항목 | 값 |
| --- | --- |
| 분야 | 구매·영업·물류 |
| 출처 | 프로토타입 시나리오 1 (끝남 — 케이스 3/3) → 검토를 서비스 앱으로 바꿔 다시 씀 |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 메시지 `vendor_registration` — 구매 포털의 등록 신청 |
| 서비스 앱·키 참조 | `ext-credit` → `purchase-credit`, `compliance` → `purchase-compliance`, `erp` → `purchase-erp` |
| 확장 | ext-credit, compliance, erp |
| 마일스톤 | **M5** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx10_vendor_onboarding_review.bpmn) · [시험 케이스](cases/bx10_vendor_onboarding_review.cases.json) |

**업무 배경과 목표**

신규 거래처가 등록을 신청하면 서류(사업자등록증, 통장 사본, 신용평가서, 해외 거래처면 수출입 신고서)를 확인한다. **해당하는 점검만** 골라 동시에 돈다: 모든 거래처는 서류 확인, 거래 예상액이 5천만 원 이상이면 신용 점검, 해외 거래처면 제재 목록 점검. 고른 점검이 모두 끝나면 구매팀장이 승인하고 ERP에 거래처를 등록한다.

**왜 서버에서 도는가**

문서 판독·API·결재뿐이다. 신청 서류는 포털이 Center 메시지 본문으로 경로를 넘긴다.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |
| --- | --- | --- | --- | --- |
| `신청번호` | string | ✓ |  |  |
| `거래처명` | string | ✓ |  |  |
| `사업자번호` | string | ✓ |  |  |
| `해외` | bool | ✓ |  |  |
| `예상거래액` | int | ✓ |  | 연간, 원 |
| `서류` | list | ✓ |  | 파일 경로 목록 |
| `회신주소` | string | ✓ |  | 포털 회신 웹훅 |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 등록 신청 | 시작 이벤트 | 메시지 `vendor_registration` | Gw_Checks |
| `Gw_Checks` | 필요한 점검 고르기 | 포함 게이트웨이 | — | Task_Docs (`true`), Task_Credit (`예상거래액 >= 50000000`), Task_Sanction (`해외`) |
| `Task_Docs` | 서류 확인 | AI 태스크 | doc · 결과 `서류결과`:dict · 도구 pdf_text_tool, image_ocr_tool | Gw_Join |
| `Task_Credit` | 신용 점검 | 서비스 앱 태스크 | `ext-credit`.`lookup` · 입력 biz_no → 신용 | Gw_Join |
| `Task_Sanction` | 제재 목록 점검 | 서비스 앱 태스크 | `compliance`.`screen_sanctions` · 입력 name → 제재 | Gw_Join |
| `Gw_Join` | 점검 모으기 | 포함 게이트웨이 | — | Task_Summary |
| `Task_Summary` | 심사 요약 | 스크립트 | `신용 = 신용 if 예상거래액 >= 50000000 else None` … | Approve_Vendor |
| `Approve_Vendor` | 구매팀장 승인 | 결재 | 「신규 거래처 등록」 · 보임 거래처명, 사업자번호, 서류결과, 신용, 제재, 권고 · 칸 `결정`(choice*), `의견`(text) · Center 결재함 | Gw_Decision |
| `Gw_Decision` | 결정 | 배타 게이트웨이 | — | Task_Register (`결정 == '승인'`), Task_Reply (기본) |
| `Task_Register` | ERP 거래처 등록 | 서비스 앱 태스크 | `erp`.`create_vendor` · 입력 name, biz_no → 거래처코드 | Task_Reply |
| `Task_Reply` | 포털에 결과 회신 | 웹훅 보내기 | POST `{회신주소}` | End |
| `End` | 끝 | 끝 이벤트 | — |  |

**주요 변수**

| 이름 | 타입 | 만드는 곳 | 뜻 |
| --- | --- | --- | --- |
| `서류결과` | dict | Task_Docs |  |
| `신용` | dict? | Task_Credit (5천만 이상일 때만) | 돌지 않으면 없음 → `Task_Summary`에서 None |
| `제재` | list? | Task_Sanction (해외일 때만) |  |
| `결정` | string | Approve_Vendor | 승인/반려/보완요청 |

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Docs` 서류 확인**

```markdown
## 상황
`서류`는 거래처가 올린 파일 목록이다.

## 할 일
사업자등록증과 통장 사본이 있는지, 사업자등록증의 번호·상호가 `사업자번호`·`거래처명`과 같은지 확인한다.

## 판단하지 않는 것
신용이나 거래 적합성은 판단하지 않는다.

## 반환
- `서류결과`: {충족(bool), 빠진서류(list), 불일치(list)}
```

</details>

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 국내 소액<br><small>서류 확인만 돈다</small> | {"신청번호": "VR-001", "거래처명": "가나상사", "사업자번호": "123-45-67890", "해외": false, "예상거래액": 10000000, "서류": ["samples/vendor/biz.pdf", "samples/vendor/bank.pdf"], "회신주소": {"$test_receiver": "reply"}} | {"권고": "승인"} | `Approve_Vendor`: {"결정": "승인"} |
| 해외 대액<br><small>세 점검 모두 돈다. 통장 사본 없음</small> | {"신청번호": "VR-002", "거래처명": "Acme Trading", "사업자번호": "999-99-99999", "해외": true, "예상거래액": 300000000, "서류": ["samples/vendor/biz.pdf"], "회신주소": {"$test_receiver": "reply"}} | {"권고": "반려"} | `Approve_Vendor`: {"결정": "보완요청", "의견": "통장 사본 누락"} |

**이 예제로 확인하는 것**

- 포함 게이트웨이(조건에 맞는 가지만 동시에) + 포함 합류
- 돌지 않은 가지의 변수는 없음 → 스크립트에서 None 처리
- 서비스 앱 3개(사내 2·외부 1)와 키 참조 3개
- 선택형 결재 칸(choice)

**주의**

- 세 검토가 각각 만드는 변수 이름을 겹치지 않게 한다 (프로토타입 시나리오 1의 주의).
- 돌지 않은 가지가 만든다고 가정한 변수를 다음 태스크가 읽으면 「없는 변수」 오류 — 합류 뒤 스크립트에서 기본값을 정한다.
- `"true"` 조건으로 「항상」 가지를 명시한다 (포함 게이트웨이는 기본 흐름 외에 아무 가지도 안 맞으면 멈춘다).

## BX-11. 입찰 접수와 마감

| 항목 | 값 |
| --- | --- |
| 분야 | 구매·영업·물류 |
| 출처 | 프로토타입 시나리오 5(입찰 마감, 제안만 됨) → 새로 설계 |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 작업 지시 — 입찰 공고 발행 시 |
| 서비스 앱·키 참조 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx11_bid_collection.bpmn) · [시험 케이스](cases/bx11_bid_collection.cases.json) |

**업무 배경과 목표**

입찰 공고를 낸 뒤 공급사 견적을 마감 시각까지 받는다. 견적이 올 때마다 기록하고, 마감 시각이 되면 접수를 닫는다. 공고가 취소되면(구매 시스템이 이 입찰번호로 「입찰 취소」 메시지를 보냄) 접수를 멈추고 응찰사에 취소를 알린다. 마감 후 AI가 견적을 비교표로 정리하고 구매팀이 낙찰사를 고른다.

**왜 서버에서 도는가**

며칠짜리 대기와 외부 메시지 수신 — 서버.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |
| --- | --- | --- | --- | --- |
| `입찰번호` | string | ✓ |  |  |
| `마감시각` | string | ✓ |  | ISO 8601 시각 (예 `2026-10-15T18:00:00+09:00`) |
| `품목` | list | ✓ |  |  |
| `견적목록` | list |  | [] | 받은 견적 (루프가 쌓는다) |
| `응찰사메일` | list |  | [] | 응찰사 회신 주소 (루프가 쌓는다) |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 공고 발행 | 시작 이벤트 | — | Task_Remaining |
| `Task_Remaining` | 남은 시간 | 스크립트 | `남은시간 = 기간(지금(), 마감시각)` | Recv_Quote |
| `Recv_Quote` | 견적 받기 | 메시지 받기 | 메시지 `bid_quote` · 상관 `입찰번호` · 받는 값 견적 | Task_Record |
| `Task_Record` | 견적 기록 | 스크립트 | `견적목록 = 견적목록 + [견적]` … | Task_Remaining |
| `Task_Close` | 접수 마감 | 스크립트 | `응찰수 = len(견적목록)` | Gw_Any |
| `Gw_Any` | 응찰 있음? | 배타 게이트웨이 | — | Task_Compare (`응찰수 > 0`), End_NoBid (기본) |
| `Task_Compare` | 견적 비교표 | AI 태스크 | llm · 결과 `비교표`:string, `요약`:string | Approve_Award |
| `Approve_Award` | 낙찰사 선택 | 결재 | 「낙찰사 선택」 · 보임 입찰번호, 비교표, 요약 · 칸 `낙찰사`(text*), `사유`(text*) · Center 결재함 | Task_NotifyAward |
| `Task_NotifyAward` | 결과 통보 | 메일 보내기 | 받는 사람 {응찰사메일} · 제목 「[{입찰번호}] 입찰 결과」 | End |
| `End` | 끝 | 끝 이벤트 | — |  |
| `End_NoBid` | 유찰 | 끝 이벤트 | — |  |
| `Task_NotifyCancel` | 취소 통보 | 메일 보내기 | 받는 사람 {응찰사메일} · 제목 「[{입찰번호}] 입찰 취소」 | End_Cancel |
| `End_Cancel` | 취소로 끝 | 끝 이벤트 | 종료(전체) |  |
| `Bnd_Deadline` | 마감 | 경계(타이머) | `Recv_Quote`에 붙음 · `남은시간` | Task_Close |
| `Bnd_Cancel` | 입찰 취소 | 경계(메시지) | `Recv_Quote`에 붙음 · `bid_cancelled` | Task_NotifyCancel |
| `Data_Compare` | 비교표 | 파일 출력 | `입찰/{입찰번호}_비교.md` (md) → `비교표경로` · `Task_Compare`가 끝날 때 | — |

**주요 변수**

| 이름 | 타입 | 만드는 곳 | 뜻 |
| --- | --- | --- | --- |
| `견적` | dict | Recv_Quote (메시지 본문) | {공급사, 단가, 납기, 조건, 회신메일} |
| `남은시간` | string | Task_Remaining | ISO 기간 — 받기를 다시 기다릴 때마다 새로 계산 |
| `견적목록` | list | Task_Record | 누적 |
| `응찰사메일` | list | Task_Record | 견적의 회신 주소 모음 |

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Compare` 견적 비교표**

```markdown
## 상황
`견적목록`은 공급사별 견적이다 (단가, 납기, 조건). `품목`은 공고 품목이다.

## 할 일
품목별로 견적을 비교하는 표를 만들고, 가격·납기·조건의 장단점을 한 줄씩 적는다.

## 판단하지 않는 것
낙찰사를 정하지 않는다. 견적에 없는 값을 추정하지 않는다.

## 반환
- `비교표`: markdown 표 문자열
- `요약`: string
```

</details>

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |

**이 예제로 확인하는 것**

- 받기 태스크 루프 + 경계 타이머(마감) + 경계 메시지(취소, 상관 키 `입찰번호`)
- 루프백 흐름
- 타이머 기간을 매번 계산 (마감 시각 고정)
- 종료(terminate) 끝 이벤트

**주의**

- 처음에는 「견적 접수」를 하위 프로세스로 묶고 마감 경계를 붙였다. 그런데 **중단 경계가 끊은 하위 프로세스는 안에서 만든 변수를 내보내지 않는다**(BPMN 표준, 프로토타입 시나리오 2에서 확인) — 마감 순간 견적목록이 사라진다. 그래서 받기 태스크에 직접 경계를 붙이고, 누적 변수는 바깥에 둔다.
- 받기를 다시 기다릴 때마다 경계 타이머가 새로 시작된다 — 기간을 상수(`P5D`)로 두면 마감이 계속 밀린다. 고정된 마감 시각에서 남은 시간을 매번 계산한다.
- 취소를 신호로 그리기 쉽지만, 신호는 **한 실행 안의 가지 사이**에서만 쓴다 (C14). 바깥에서 특정 입찰을 멈추려면 메시지 + 상관 키(`chk:receive`를 경계에)로 보낸다.
- 견적이 0건이면 AI 비교가 빈 표를 지어낼 수 있다 — 「유찰」 가지를 먼저 둔다.

**왜 서버에서 도는가**

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |

| `사유` | string | ✓ |  | 고객이 쓴 글 |

**흐름 (노드)**

| `Task_Classify` | 사유 분류 | AI 태스크 | llm · 결과 `분류`:string, `근거`:string | Recv_Arrived |

- 받기 태스크의 중단 타이머(자동 취소)
- AI 분류 → 스크립트 계산 → 서비스 앱 작업
- 부작용 있는 작업(환불)의 멱등 — C11 키

**주의**

- AI는 분류만, 금액 계산은 스크립트 — 금액이 AI 출력에 직접 기대지 않게 한다.
- 환불은 같은 요청이 두 번 가면 안 된다 — 사내 확장 `shop`은 C11 서비스 앱이라 멱등 키(실행·노드·시도 단위)로 막는다.
- 프로토타입 시나리오 7은 「폴더에 신청서가 떨어지면」 조건 시작으로 기획됐다. 조건 시작은 쓰지 않으므로(C14) 쇼핑몰이 메시지를 보내게 한다.
- 입고 메시지가 받기 태스크보다 먼저 오면(분류 AI가 도는 중) C12가 `no_receiver`로 거부한다 — 메시지 보관은 README 「아직 정하지 않은 것」.

- 재실행 멱등 (주문번호로 건너뛰기)

**주의**

- 로그인 정보를 목표·파라미터·UI 스텝 값에 쓰면 패키지에 비밀이 들어간다 — 로그인은 사람이 프로필에 해 두고, 끊기면 확인 트리거로 (CLAUDE.md 보안 규칙).
- 포털 화면이 바뀌면 셀렉터 사다리 + 자가 치유(C8)가 먼저 버틴다. 치유가 한도를 넘으면 전환(escalated) — PC Bot은 확인 창으로 넘긴다 (C10).
- 매일 돌리되 「어제」만 읽으면 실행이 하루 빠졌을 때 구멍이 난다 — 재실행 멱등(주문번호로 건너뛰기) 덕분에 조회일을 입력으로 넣어 다시 돌리면 된다.
- 「같은 날 다시 실행」 케이스를 처음부터 둔다 — 재시도·재실행이 중복을 만들지 않는지.

## BX-16. 재고 발주 제안 (서버) → ERP 입력 (PC)

| 항목 | 값 |
| --- | --- |
| 분야 | 구매·영업·물류 |
| 출처 | 새로 설계 — 서버와 PC를 나누는 대표 예 |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 타이머 — 매일 07:00 |
| 서비스 앱·키 참조 | `wms` → `scm-wms`, `center-jobs` → `scm-center-jobs` |
| 확장 | wms, center-jobs |
| 마일스톤 | **M5** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx16_reorder_proposal.bpmn) · [시험 케이스](cases/bx16_reorder_proposal.cases.json) |

**업무 배경과 목표**

재고 데이터를 API로 읽어 안전재고 아래로 떨어진 품목의 발주 수량을 계산하고 구매 담당이 확인한다. 확인된 발주는 **ERP 화면 입력이 필요한데 ERP에 API가 없다.** 그래서 서버 BPM 프로세스는 「발주 입력」 PC BPM 프로세스(BX-17)의 작업 지시를 만든다. **현재 계약에는 서버 BPM 프로세스가 PC 작업을 만드는 요소가 없다** (「PC 위임」은 [ADR-0016](../decisions/0016-server-first.md) §3에 제안만 — 서버 BPM 프로세스의 Call Activity가 PC BPM 프로세스를 부르는 모양이며, schema 1에서는 C1 R3가 거부한다). 이 예제는 그 자리를 사내 확장 `center-jobs`(Center 작업 지시 API를 감싼 서비스 앱 — Center 연동용 키는 그 앱이 가진다)로 메운다.

**왜 서버에서 도는가**

계산·결재는 서버, 화면 입력만 PC — **업무를 두 BPM 프로세스로 쪼갠다.** PC 쪽은 짧게 끝나 실행 자리를 오래 잡지 않는다.

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 매일 07:00 | 시작 이벤트 | 타이머 `0 7 * * 1-5` | Task_Stock |
| `Task_Stock` | 재고 읽기 | 서비스 앱 태스크 | `wms`.`list_stock` · 입력  → 재고 | Task_Calc |
| `Task_Calc` | 발주량 계산 | 스크립트 | `제안 = [dict(품목=x.code, 수량=x.safety * 2 - x.qty) for x in 재고 if x.qty < ` … | Gw_Any |
| `Gw_Any` | 제안 있음? | 배타 게이트웨이 | — | Approve_Order (`제안수 > 0`), End (기본) |
| `Approve_Order` | 발주 확인 | 결재 | 「발주 제안 확인」 · 보임 제안 · 칸 `승인`(bool*), `메모`(text) · Center 결재함 | Gw_Order |
| `Gw_Order` | 발주? | 배타 게이트웨이 | — | Task_Confirm (`승인`), End (기본) |
| `Task_Confirm` | 확정 | 스크립트 | `확정 = 제안` | Task_Dispatch |
| `Task_Dispatch` | ERP 입력 작업 지시 | 서비스 앱 태스크 | `center-jobs`.`create_job` · 입력 bpm_process, target, inputs → 작업번호 | End |
| `End` | 끝 | 끝 이벤트 | — |  |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 부족 2품목<br><small>모의 WMS가 2품목을 안전재고 아래로 돌려준다</small> | {} | {"제안수": 2, "작업번호": "*"} | `Approve_Order`: {"승인": true} |

**이 예제로 확인하는 것**

- 서버 + PC 두 BPM 프로세스로 쪼개기
- 작업 지시를 사내 확장 서비스 앱으로 (PC 위임의 공백 표시)
- 결재 반려 시 발주 안 함

**주의**

- 한 BPM 프로세스 안에 서버 일과 PC 일을 섞지 않는다 — 실행 위치는 BPM 프로세스 단위다 (ADR-0015).
- 웹훅 태스크로 Center API를 직접 부르면 키를 붙일 방법이 없다 (웹훅은 인증 헤더를 갖지 않음, 비밀을 BPMN에 둘 수 없음) — 그래서 서비스 앱으로 감쌌다.
- PC 위임이 확정되면(ADR-0016 §3, M7) 이 서비스 앱 태스크를 BX-17을 부르는 Call Activity로 바꾼다. 결과·실패는 Call Activity 출력과 오류 경계로 돌아온다.
