## BX-20. 입사자 온보딩

| 항목 | 값 |
| --- | --- |
| 분야 | 인사·총무 |
| 출처 | 프로토타입 시나리오 2 (끝남 — 케이스 3/3, 재생 3/3) |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 메시지 `new_hire` — 인사 시스템의 입사 확정 |
| 서비스 앱·키 참조 | `directory` → `hr-directory` |
| 확장 | directory |
| 마일스톤 | **M5** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx20_employee_onboarding.bpmn) · [시험 케이스](cases/bx20_employee_onboarding.cases.json) |

**업무 배경과 목표**

입사 확정이 오면 계정 준비(메일·메신저·그룹웨어)를 하위 프로세스로 묶어 진행한다. 계정 준비가 이틀 안에 끝나지 않으면 IT팀에 에스컬레이션한다. 계정이 준비되면 AI가 입사자에게 보낼 환영 안내를 쓰고, 장비 지급을 총무팀이 확인한 뒤 입사자와 팀장에게 메일을 보낸다.

**왜 서버에서 도는가**

프로토타입 시나리오 2는 장비 수령을 PC의 수동 작업으로 확인했다. 실제 업무에서 총무팀 확인은 입사일까지 며칠 걸릴 수 있고, PC Bot이면 그동안 실행 자리를 쥔다 (ADR-0014). 그래서 **Center 결재함의 확인**으로 바꿔 서버에서 기다린다.

## 상황

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 정상 입사 | {"사번": "E2610-01", "이름": "박지민", "부서": "재무팀", "입사일": "2026-10-12", "팀장메일": "lead@example.com", "개인메일": "jimin@example.net"} | {"회사메일": "*"} | `Approve_Equipment`: {"노트북": "NB-2210", "출입카드": true} |
| 정상 입사 (사람이 확인) (수동) | {"사번": "E2610-02", "이름": "이도윤", "부서": "영업팀", "입사일": "2026-10-12", "팀장메일": "lead@example.com", "개인메일": "doyun@example.net"} | {} | — (사람이 직접 답함) |

**이 예제로 확인하는 것**

- 하위 프로세스 + 안의 병렬
- 하위 프로세스의 비중단 타이머 경계(에스컬레이션)
- PC 수동 작업 → Center 결재함 확인으로 옮긴 사례
- AI 문장 + 업무 파라미터

**주의**

- 하위 프로세스 안에서 만든 변수(`회사메일`)는 정상으로 끝나면 밖에서도 보인다 (호출과 다름). 그러나 **중단 경계가 끊은 하위 프로세스는 안에서 만든 변수를 하나도 내보내지 않는다** (프로토타입 시나리오 2에서 확인). 그래서 이 예제의 2일 경계는 비중단 — 에스컬레이션만 하고 계정 준비는 계속한다.
- 하위 프로세스 안에는 시작 이벤트만 저절로 생긴다. 끝 이벤트를 직접 넣지 않으면 마지막 안쪽 태스크에 나가는 흐름이 없어 실행 전 검사(B9)가 막는다 (프로토타입 시나리오 2).
- 마감·경계로 끊긴 태스크를 실패로 세면 마감을 시험하는 케이스가 다른 케이스의 판정을 지운다 — 취소는 판정이 아니다 (프로토타입 결함 C-21).

## BX-21. 휴가 신청

| 항목 | 값 |
| --- | --- |
| 분야 | 인사·총무 |
| 출처 | 새로 설계 |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 메시지 `leave_request` — 그룹웨어 휴가 신청 |
| 서비스 앱·키 참조 | `hris` → `hr-hris` |
| 확장 | hris |
| 마일스톤 | **M5** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx21_leave_request.bpmn) · [시험 케이스](cases/bx21_leave_request.cases.json) |

**업무 배경과 목표**

직원이 휴가를 신청하면 잔여 휴가를 확인한다 (공유 BPM 프로세스 BX-24 호출). 잔여가 모자라면 바로 반려, 3일 이하면 팀장 결재, 3일 초과면 팀장 → 부서장 순서로 결재한다. 승인되면 근태 시스템에 등록한다.

**왜 서버에서 도는가**

결재 대기 — 서버.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |
| --- | --- | --- | --- | --- |
| `신청번호` | string | ✓ |  |  |
| `사번` | string | ✓ |  |  |
| `시작일` | date | ✓ |  |  |
| `일수` | number | ✓ |  | 반차 0.5 |
| `회신주소` | string | ✓ |  | 그룹웨어 회신 웹훅 |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 휴가 신청 | 시작 이벤트 | 메시지 `leave_request` | Call_Balance |
| `Call_Balance` | 잔여 휴가 (BX-24) | BPM 프로세스 호출 | `Proc_bx24_leave_balance` · 입력 사번 · 출력 잔여 | Gw_Enough |
| `Gw_Enough` | 잔여 충분? | 배타 게이트웨이 | — | Approve_Lead (`잔여 >= 일수`), Task_Reject (기본) |
| `Approve_Lead` | 팀장 결재 | 결재 | 「휴가 결재 (팀장)」 · 보임 사번, 시작일, 일수, 잔여 · 칸 `승인`(bool*), `의견`(text) · Center 결재함 | Gw_Long |
| `Gw_Long` | 3일 초과? | 배타 게이트웨이 | — | Approve_Head (`승인 and 일수 > 3`), Gw_Result (기본) |
| `Approve_Head` | 부서장 결재 | 결재 | 「휴가 결재 (부서장)」 · 보임 사번, 시작일, 일수, 잔여, 의견 · 칸 `승인`(bool*) · Center 결재함 | Gw_Result |
| `Gw_Result` | 승인? | 배타 게이트웨이 | — | Task_Register (`승인`), Task_Reject (기본) |
| `Task_Register` | 근태 등록 | 서비스 앱 태스크 | `hris`.`register_leave` · 입력 emp_id, start, days → 등록 | Task_Approved |
| `Task_Approved` | 승인 정리 | 스크립트 | `결과 = '승인'` | Task_Reply |
| `Task_Reject` | 반려 정리 | 스크립트 | `결과 = '반려'` | Task_Reply |
| `Task_Reply` | 그룹웨어 회신 | 웹훅 보내기 | POST `{회신주소}` | End |
| `End` | 끝 | 끝 이벤트 | — |  |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 2일 승인 | {"신청번호": "LV-1", "사번": "E001", "시작일": "2026-10-20", "일수": 2, "회신주소": {"$test_receiver": "reply"}} | {"승인": true} | `Approve_Lead`: {"승인": true} |
| 5일 부서장 반려 | {"신청번호": "LV-2", "사번": "E001", "시작일": "2026-11-02", "일수": 5, "회신주소": {"$test_receiver": "reply"}} | {"결과": "반려"} | `Approve_Lead`: {"승인": true}; `Approve_Head`: {"승인": false} |
| 잔여 부족 | {"신청번호": "LV-3", "사번": "E002", "시작일": "2026-10-20", "일수": 20, "회신주소": {"$test_receiver": "reply"}} | {"결과": "반려"} | — |

**이 예제로 확인하는 것**

- 순차 결재 2단계 (조건부)
- 같은 변수(`승인`)를 두 결재가 덮어쓰는 패턴
- 공유 BPM 프로세스 호출
- 여러 길이 한 태스크로 합류

**주의**

- 두 결재가 같은 칸 이름(`승인`)을 쓰면 뒤 결재가 앞 값을 덮는다 — 의도한 것이면 괜찮지만, 둘 다 남기려면 칸 이름을 다르게 한다.
- 결재자 지정(누가 결재하나)은 Center 결재함의 배정 규칙(C6)이 정한다. BPMN에 사람 이름을 쓰지 않는다.

## BX-22. 퇴사자 계정 회수

| 항목 | 값 |

| 시작 | 메시지 `employee_left` — 인사 시스템이 퇴사 처리 때 한 사람씩 보냄 |
| 서비스 앱·키 참조 | `directory` → `sec-directory`, `erp` → `sec-erp` |

**업무 배경과 목표**

퇴사 처리된 직원 한 사람의 계정을 세 시스템(메일, VPN, ERP)에서 동시에 회수한다. 한 시스템에서 실패해도 다른 시스템 회수는 계속되고, 실패한 것만 모아 보안팀에 알려 수동으로 처리하게 한다.

**왜 서버에서 도는가**

API만 쓴다 — 서버. 세 시스템을 동시에.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |
| --- | --- | --- | --- | --- |
| `사번` | string | ✓ |  |  |
| `이름` | string | ✓ |  |  |
| `퇴사일` | date | ✓ |  |  |
| `보안팀메일` | string |  | "security@example.com" |  |

| --- | --- | --- | --- | --- |

| `Sub_Revoke` | 계정 회수 | 하위 프로세스 | 안에 14개 노드 | Task_Count |

| `↳ Rv_ErpFail` | ERP 실패 기록 | 스크립트 | `ERP실패 = dict(시스템='ERP', 오류=error_message)` | Rv_ErpDone |
| `↳ Rv_MailDone` | 메일 끝 | 배타 게이트웨이 | — | Rv_Join |
| `↳ Rv_VpnDone` | VPN 끝 | 배타 게이트웨이 | — | Rv_Join |
| `↳ Rv_ErpDone` | ERP 끝 | 배타 게이트웨이 | — | Rv_Join |
| `↳ Rv_Join` | 모두 끝 | 병렬 게이트웨이 | — | Rv_End |
| `↳ Rv_End` | 끝 | 끝 이벤트 | — |  |
| `↳ Bnd_MailFail` | 실패 | 경계(오류) | `Rv_Mail`에 붙음 · `TASK_FAILED` | Rv_MailFail |
| `↳ Bnd_VpnFail` | 실패 | 경계(오류) | `Rv_Vpn`에 붙음 · `TASK_FAILED` | Rv_VpnFail |
| `↳ Bnd_ErpFail` | 실패 | 경계(오류) | `Rv_Erp`에 붙음 · `TASK_FAILED` | Rv_ErpFail |
| `Task_Count` | 실패 모으기 | 스크립트 | `실패 = [x for x in [메일실패, VPN실패, ERP실패] if x is not None]` … | Gw_Fail |
| `Gw_Fail` | 실패 있음? | 배타 게이트웨이 | — | Task_Security (`실패수 > 0`), End (기본) |
| `Task_Security` | 보안팀 알림 | 메일 보내기 | 받는 사람 {보안팀메일} · 제목 「[계정 회수] {이름}({사번}) 수동 처리 {실패수}건」 | End |
| `End` | 끝 | 끝 이벤트 | — |  |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 정상 | {"사번": "E008", "이름": "최서연", "퇴사일": "2026-10-31"} | {"실패수": 0} | — |
| ERP 실패<br><small>모의 ERP가 E009에 503을 계속 돌려준다 — 재시도 2번 뒤 실패</small> | {"사번": "E009", "이름": "정하준", "퇴사일": "2026-10-31"} | {"실패수": 1, "실패": [{"시스템": "ERP"}]} | — |

**이 예제로 확인하는 것**

- 병렬 가지마다 오류 경계 → 배타 합류 → 병렬 합류 (가지 수 맞추기)
- 하위 프로세스
- `TASK_FAILED` + 재시도 정책
- 가지별 변수 → 합류 뒤 모으기
- 건마다 실행 하나 (메시지 시작)

**주의**

- 오류 경계의 대체 흐름을 병렬 합류에 바로 이으면 합류가 5개를 기다리는데 3개만 온다 — 영원히 멈춘다. 각 가지를 배타 게이트웨이로 먼저 모아 **가지 수와 합류 수를 맞춘다** (build.py가 검사).
- 여러 가지가 같은 목록 변수에 덧붙이면 동시 쓰기가 된다 — 가지마다 자기 변수에 쓰고, 합류 뒤 모은다. 그 변수는 분기 전에 비워 둔다 (B11).
- 여러 사람을 한 실행에서 돌리지 않고 **사람마다 실행 하나** — 실패·재시도·감사가 사람 단위로 깔끔하다. 서버는 동시에 여러 실행을 돌린다.
- 오류 경계가 없는 병렬 가지가 실패하면 실행 전체가 실패한다 — 「계속해야 하는」 가지에는 오류 경계를 붙인다.

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Write` 안내 메일 쓰기**

```markdown
## 상황
`대상`은 미이수자 한 명(이름, 메일, 팀장메일, 교육명, 마감일, 남은일수, 링크, 단계)이다. 교육 시스템이 돌려준 값에 `단계`를 붙였다.

## 할 일
단계에 맞는 안내 메일 제목과 본문을 쓴다. 받는 사람은 `대상.메일`, 「팀장참조」·「인사팀보고」면 참조에 `대상.팀장메일`(인사팀보고는 업무 파라미터 `인사팀메일`도). 이수 링크는 `대상.링크`를 그대로 쓴다.

## 판단하지 않는 것
불이익을 과장하지 않는다.

## 반환
- `메일`: {받는사람, 참조, 제목, 본문}
```
