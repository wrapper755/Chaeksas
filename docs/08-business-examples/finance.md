## BX-01. 월별 청구서 대사

| 항목 | 값 |
| --- | --- |
| 분야 | 재무·회계 |
| 출처 | 프로토타입 업무 A (실제로 만들어 돌림) |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 타이머 — 매월 1일 09:00 (`0 9 1 * *`), 또는 작업 지시(대상월 지정) |
| 서비스 앱·키 참조 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx01_invoice_reconciliation.bpmn) · [시험 케이스](cases/bx01_invoice_reconciliation.cases.json) |

**업무 배경과 목표**

공급사가 보낸 청구서 PDF(양식 3가지, 7건)를 발주 대장(xlsx)과 맞춰 본다. 문제없는 건은 지급 대상으로, 문제 있는 건은 보류로 나누고 대사표를 만든다. 보류가 있으면 담당자가 확인한 뒤 결과를 재무팀에 메일로 보낸다.

보류 규칙(6가지): 미등록 발주, 중복 청구, 금액 불일치, 부가세 ≠ 공급가의 10%, 미입고, 그리고 참고용으로 미청구 발주를 따로 적는다.

**왜 서버에서 도는가**

화면 조작이 없다 (문서 읽기 + 판단 + 메일). 결재가 며칠 늦어도 서버가 상태를 저장하고 기다리므로 PC를 붙잡지 않는다 (ADR-0016).

| `재무팀메일` | string |  | "finance@example.com" | 받는 사람 |

**이 예제로 확인하는 것**

- 순차 반복 AI 태스크(`collect_into`)
- AI 문서 읽기(doc) + 규칙은 스크립트로
- 조건부 결재(Center 결재함)
- 파일 출력 → 메일 첨부(`store_as`)
- 오류 경계 `SEND_FAILED`
- 타이머 시작(월 1회)

**주의**

- 목표를 템플릿 문구 그대로 두면 모델이 대장을 지어냈다 — 목표에 데이터가 어디 있는지 적는다.
- 비어 있는 업무 파라미터가 실제 변수를 덮어썼다 — 경로처럼 실행마다 바뀌는 값은 파라미터가 아니라 입력으로.
- `발주번호`를 int로 두면 `PO-2608-001`이 `2608001`이 된다 — 번호는 string (C14 B8).
- 판독 태스크가 중복을 먼저 판단해 버렸다 — 목표에 「판단하지 않는 것」을 적는다.
- 결재 `show`를 문자열 하나로 쓰면 아무것도 안 보였다 — 배열로 (C14 B2).
- 케이스가 하나뿐이었다 — 「문제 없는 달」·「청구서 없음」을 처음부터 둔다.

**샘플 데이터**

프로토타입 `samples/invoice_reconciliation/2026-08/` — 청구서 PDF 7장(양식 3종), `ledger_2026-08.xlsx` 7줄. 심어 둔 문제: 금액 +90,000(유니스오피스), 미입고(삼정), 미등록 PO-2608-011(네오소재), 중복(대성테크 재발행), 부가세 180,000(코리아플러스), 미청구 발주 005·007. 새 저장소로 옮길 때 `samples/`에 복사한다.

**업무 배경과 목표**

평일 아침마다 외부 환율 API에서 USD 기준 KRW·EUR·JPY 환율을 받아 통화별 상한·하한과 비교한다. 경고가 있을 때만 담당자에게 확인을 받고, 보고서를 만들어 메일로 보낸다. 메일이 실패해도 실행 전체가 실패하지 않게 오류 경계로 기록만 남긴다.

**왜 서버에서 도는가**

외부 API와 메일뿐이다. 결재를 기다리는 동안 서버는 상태를 저장한다.

| 상한 돌파 | {"상한": {"KRW": 1000, "EUR": 1.2, "JPY": 200}, "하한": {"KRW": 500, "EUR": 0.5, "JPY": 100}} | {"경고수": 1} | `Approve_Warn`: {"조치필요": true, "메모": "환율 급등 — 결제 일정 확인 필요"} |
| 상한 돌파 (사람이 확인) (수동) | {"상한": {"KRW": 1000}} | {"경고수": 1} | — (사람이 직접 답함) |

**이 예제로 확인하는 것**

- API AI 태스크 + 업무 파라미터(재생 때 `$param`)
- 조건부 결재
- 파일 출력 → 메일 첨부
- 오류 경계로 메일 실패를 흡수
- 평일 타이머

**주의**

- 임계값은 처음에 숫자 하나였다가 통화별 dict로 바뀌었다 — 처음부터 dict로.
- 운영 임계값은 스크립트 기본값에, 케이스는 입력으로만 덮어쓴다 (업무 파라미터는 케이스가 못 바꾼다).
- 받는 사람 주소는 「설정에서 읽어 오기」가 아니라 **기본값 있는 입력**이다 (ADR-0025 — 식은 순수 함수만).
- 보고서 모양은 스크립트가 글자를 이어 붙이지 않고 **파일 출력 템플릿**에 둔다 (같은 ADR).
- 주소를 목표 문장에 쓰면 재생이 그 문장에 묶인다 — 업무 파라미터로.
- 「성공했지만 결과가 틀린」 실수 4가지: 경로에 `outputs/` 두 번, 빈 템플릿, `store_as` 없음, 받는 사람 변수 없음 (C14 §파일 출력).
- 작은 태스크는 재생해도 시간이 줄지 않았다 (LLM 7회→1회, 시간 같음) — 재생의 이득은 큰 태스크에서.

**샘플 데이터**

외부 API `api.frankfurter.dev` (키 없음). 서버망에서 닿는지 먼저 확인한다.

**업무 배경과 목표**

경비 시스템에서 지출 신청이 오면 정책으로 먼저 거른다: 영수증이 없으면 바로 반려, 10만 원 이하면 자동 승인, 그 밖에는 결재자에게 보낸다. 결재는 며칠 걸릴 수 있다. 3일이 지나면 리마인드(결재는 계속 기다림), 7일이 지나면 기한 초과로 반려한다. 어떤 길로 끝나든 신청자에게 회신하고 처리 기록을 남긴다.

- 네 갈래가 한 곳으로 합류

- 웹훅 회신 + 오류 경계

- 상태 저장·재개(며칠 대기)가 이 업무의 핵심이었다 — 서버 실행기가 맡는다 (C12 `run_waiting`/`run_resumed`).
- 리마인드 Send Task가 결재가 끝날 때까지 늦게 실행된 결함이 있었다 (A-11) — 비중단 경계의 가지는 즉시 돌아야 한다.
- 경계 타이머는 반복(`timeCycle`)을 지원하지 않아 리마인드는 한 번뿐이다 (C14).
- 마감에 진 결재가 빨간색(실패)으로 보였다 — 정상 경로다. 「취소됨」(neutral)으로 표시한다.
- 기한 값은 기본값 있는 입력으로 — 업무 파라미터면 케이스가 짧은 기한으로 바꿀 수 없다.
- 결과 정리 스크립트는 네 갈래 어디서 와도 같은 변수를 읽는다. 결재 칸(`승인여부`·`결재의견`)과 `기한초과`는 결재를 거치지 않는 길에서는 생기지 않으므로 사전 점검에서 먼저 정해 둔다 (B11).

- 셀 읽기가 수식을 돌려줬다 — `read`는 계산된 값을 읽도록 요소를 등록한다.
- 남은 프로세스가 다음 실행을 가로챘다 — UI 태스크 「실행 후 닫기」를 켠다.
- 시작 주소를 케이스마다 바꿀 수 없었다 — 시작 주소는 화면 등록(C9)의 기본 주소, 케이스는 필터 값만 바꾼다.

**샘플 데이터**

프로토타입은 the-internet.herokuapp.com/tables(4줄, 합계 251)와 `taxbook.ods`를 썼다. 새 구조에서는 사내 시험 포털 화면을 BUI-06으로 등록해 쓴다.

- AI 분류 반복 + 규칙 점검 분리 (판단은 규칙, 분류는 AI)
- 규칙 태스크 반복 + DMN `COLLECT` (한 건에 위반 여러 개, 없으면 빈 목록)

- DMN이 읽는 칸(요일·시)은 앞 태스크의 반환에 있어야 한다 — 판독 목표의 반환 칸을 DMN 입력에 맞춰 정한다.

**업무 배경과 목표**

ERP에서 만기가 지난 매출채권을 가져와 거래처마다 연체 단계(1차 안내 / 2차 독촉 / 법무 이관 검토)를 규칙으로 정한다. 1·2차는 AI가 거래처별 독촉 메일 초안을 쓰고 보낸다. 법무 이관 검토 대상(연체 90일 이상 또는 1억 원 이상)은 재무팀장 결재를 받는다.

**왜 서버에서 도는가**

ERP 연동은 사내 확장(서비스 앱)의 API로, 메일·결재만 있다 → 서버.
