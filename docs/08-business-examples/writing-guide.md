## 1. 프로토타입에서 왜 어려웠나

프로토타입에서 시나리오 하나를 끝까지 돌릴 때마다 플랫폼 결함이 열 개 넘게 나왔다 (시나리오 2에서 11개, 시나리오 3에서 12개). 결함 자체보다 더 큰 문제는 **시나리오를 쓰는 방법이 정해져 있지 않았다**는 것이다.

| 증상 | 원인 | 이 문서의 규칙 |
| --- | --- | --- |
| 모델이 대장을 지어냈다 | 목표 문구를 템플릿 그대로 둠 — 데이터가 어디 있는지 안 적음 | §4 목표 4단 |
| 판독 태스크가 대사까지 해 버림 | 「하지 말 것」이 없음 | §4 「판단하지 않는 것」 |
| 빈 업무 파라미터가 실제 변수를 덮음 | 파라미터·입력·변수의 구분이 없음 | §5 값의 네 자리 |
| `PO-2608-001`이 `2608001`로 | 번호를 int로 | §5 번호는 string |
| 결재 창에 아무것도 안 보임 | `show`를 문자열 하나로 | §6 |
| 파일은 생겼는데 첨부가 안 됨 | `store_as` 없음, 경로에 `outputs/` 두 번 | §7 |
| 마감을 시험하는 케이스가 실패로 집계 | 취소를 실패로 셈 | §8 |
| 마감이 끊은 하위 프로세스의 결과가 사라짐 | BPMN 표준 동작을 몰랐음 | §8 |
| 결재를 며칠 기다리는 동안 PC가 묶임 | 실행 위치 개념이 없었음 | §3 |
| 케이스 결재 응답을 읽을 수 없음 | 노드 id가 `Activity_0ngrasb` | §2 |
| 케이스가 하나뿐 — 통과해도 증명하는 게 없음 | 최소 케이스 세트가 없음 | §10 |
| 카드·BPMN·케이스가 서로 어긋남 | 손으로 따로 고침 | §11 원본 하나 |

## 2. 카드 한 장의 순서

예제 하나는 다음 순서로 쓴다. 앞 칸이 비면 뒤 칸을 쓰지 않는다.

1. **업무 배경과 목표** — 누가, 언제, 무엇을 받아서, 무엇을 남기면 끝인가. **판정할 수 있는 산출물**(파일·변수·보낸 메시지)이 없으면 그 업무는 검증할 수 없으니 만들지 않는다.
2. **사람이 하던 순서(as-is)와 판단 기준** — 판단 기준은 표로. 이것이 규칙(DMN)·스크립트·AI 목표 중 어디로 갈지 정한다.
3. **실행 위치와 이유** (§3).
4. **노드** — 읽을 수 있는 id(`Task_ReadLedger`, `Gw_HasHold`, `Approve_Hold`). 종류 접두어: `Task_`, `Gw_`, `Approve_`/`Manual_`, `Recv_`, `Call_`, `Sub_`, `Bnd_`, `Data_`, `Ms_`(이정표).
5. **변수·입력** (§5), **결재 폼** (§6), **출력** (§7).
6. **케이스** (§10).
7. **주의** — 만들며 막힌 것. 다음 사람이 같은 데서 막히지 않게.

## 3. 실행 위치 — 서버가 기본

[ADR-0016](../decisions/0016-server-first.md): 업무 대부분은 서버 Bot이 돌고, PC Bot은 「그 PC가 아니면 안 되는 일」만 한다.

| 질문 | 예면 |
| --- | --- |
| API 없는 웹·데스크톱 화면을 조작하나? (UI 태스크, `web`/`desktop` AI 태스크) | PC |
| 그 PC 앞의 사람이 화면을 보며 바로 확인해야 하나? (`location: field`) | PC |
| 사내 인증서·브라우저 프로필 로그인이 그 PC에만 있나? | PC |
| 결재·메시지를 **몇 시간 이상** 기다리나? | **서버** — PC는 끝날 때까지 실행 자리를 쥔다 (ADR-0014). BX-03 |
| 여러 건을 동시에 돌려야 하나? (병렬 반복) | 서버 — PC에서는 차례로 돈다 |

한 업무에 둘 다 있으면 **BPM 프로세스를 둘로 쪼갠다** (BX-16 서버 + BX-17 PC). 실행 위치는 BPM 프로세스 단위다.

## 4. BPMN에 그릴 것과 목표에 쓸 것

**업무 규칙으로 고정된 순서·분기는 BPMN에, 「상황 보고 알아서」는 AI 태스크 목표에.** 순서를 목표에 적으면 재생이 안 되고, 화면 셀렉터를 BPMN에 적으면 화면이 바뀔 때마다 그림을 고쳐야 한다.

| 판단 | 둘 곳 |
| --- | --- |
| 표로 쓸 수 있는 규칙 (금액 구간, 등급, 지역) | 규칙 태스크 (DMN) — 현업이 표를 고친다 (BX-12). DMN은 **한 건**을 판정한다 — 목록은 규칙 태스크를 반복한다 (BX-06·07·08·23). DMN 입력은 앞 태스크의 반환 칸과 이름을 맞춘다 |
| 계산·집계·필터 | 스크립트 |
| 읽기·분류·요약·문장 쓰기 | AI 태스크 |
| 사람만 할 수 있는 판단 | 결재 |

**AI는 분류·판독·문장만, 판단은 규칙·스크립트·사람이** (BX-07, BX-13, BX-15). 금액이 AI 출력에 직접 기대지 않게 한다.

**AI 태스크 크기:** 화면 한두 개, 또는 문서 한 장에서 끝나고 **반환 필드로 검증할 수 있는** 단위. 분기는 목표가 아니라 게이트웨이로.

**목표 4단** (C14 권장, 이 폴더의 모든 AI 태스크가 이 모양이다):

```markdown
## 상황
`대장파일`은 이번 달 발주 대장(xlsx)이다. 한 줄이 발주 한 건이다.      ← 데이터가 어디 있는지, 변수 이름으로

## 할 일
모든 줄을 읽어 발주번호·공급사·공급가액·입고여부를 목록으로 돌려준다.    ← 하나의 동작

## 판단하지 않는 것
대사·지급 판단은 하지 않는다. 값이 비어 있으면 비운 채로 둔다.          ← 뒤 단계의 일, 지어내지 말 것

## 반환
- `발주목록`: list of {발주번호(string), 공급사(string), 공급가액(int), 입고(bool)}
```

- 주소·시트 이름처럼 **실행마다 같은 운영 값**은 목표 문장이 아니라 업무 파라미터에 둔다. 재생 때 `$param`으로 저장되어 값만 바꿔 다시 쓸 수 있다 (BX-02, BX-37).
- 고객에게 나가는 글은 AI 초안 → 사람 확인 (BX-32).
- 대량 처리는 건마다 반복하지 말고 묶음으로 (BX-35: 50건씩 병렬).

## 5. 값의 네 자리

| 자리 | 누가 채우나 | 예 | 케이스가 바꿀 수 있나 |
| --- | --- | --- | --- |
| **입력** (`chk:process.inputs`) | 작업 지시, 메시지 본문, 호출하는 쪽, 케이스 | `대상월`, `신청번호`, `회신주소` | 예 |
| 입력의 **기본값** (`inputs[].default`) | 정의 | 받는 사람 메일(`finance@example.com`) | 예 (덮어씀) |
| **업무 파라미터** (`chk:aiTask.params`) | 정의 | 환율 API 주소, 계정과목표 | **아니오** — 운영 값만 |
| **변수** | 앞 태스크의 결과·결재 칸·스크립트 | `보류`, `승인`, `발송결과` | 아니오 (기대값으로 확인만) |

규칙:

- **메시지 본문으로 들어오는 값은 입력으로 선언한다.** 메시지 시작이면 `inputs`, 받기 태스크면 `chk:receive.payload`. 선언하지 않으면 실행 전 검사 B11이 「출처 없음」으로 잡는다. 이 예제들을 처음 쓸 때도 받는 사람·회신 주소를 선언하지 않은 실수가 여러 번 나왔다.
- **타이머로 시작하는 BPM 프로세스에는 기본값 없는 필수 입력을 두지 않는다** — 채울 사람이 없다 (BX-05, BX-07: 선택 입력 + 첫 스크립트에서 정함).
- 선언한 입력을 주지 않으면 `None`이다 (`x or 기본값`은 입력에만). 그 밖의 변수는 **읽기 전에 반드시 만들어져 있어야** 한다 — 갈래가 합쳐지는 곳에서 읽을 변수는 갈래가 나뉘기 전에 정해 둔다 (BX-03, BX-22).
- **경로·기한·임계값처럼 시험에서 바꿔야 하는 값은 입력**으로 (BX-02 상한·하한, BX-03 기한). 파라미터로 두면 케이스가 못 바꾼다.
- **번호는 string.** 발주번호·사업자번호·사번 (C14 B8).
- 변수 이름은 한글 가능, 공백·하이픈·숫자 시작 불가. 문자열 상수는 식에서 따옴표로 (`결정 == '승인'`).
- **한 가지에서만 생기는 변수를 합류 뒤에 읽지 않는다.** 합류 직후 스크립트에서 기본값을 정한다 (BX-10 `신용`·`제재`, BX-33 `기간`은 일부러 남긴 반례).
- 병렬 가지 둘이 같은 목록 변수에 덧붙이지 않는다 — 가지별 변수로 나눴다가 합류 뒤 합친다 (BX-22 주의).
- 결재 두 개가 같은 칸 이름을 쓰면 뒤가 앞을 덮는다. 둘 다 남기려면 이름을 나눈다 (BX-21).
- 호출은 **적은 변수만** 오간다. 같은 대상을 여러 번 부르면 출력 이름을 나눈다 (BX-30 `손해배상결과`·`지재권결과`·`해지결과`). 호출 대상은 `outputs`를 선언한다.
- 공유 BPM 프로세스는 부르는 쪽 패키지에 **복사되어** 들어간다 (용어집). 원본을 고치면 부르는 쪽을 다시 패키징해야 반영된다 (BX-12).

## 6. 결재 폼

- `show`는 **변수 이름 배열**. 결재자가 판단에 필요한 것만 (C14 B2).
- 칸 타입은 C6의 `bool`·`number`·`text`·`choice`(+`choices`) (C14 B12). 긴 글도 `text`. 목록을 결재 칸으로 받지 않는다 — 「제안대로 진행?」 bool로 묻고 목록은 스크립트가 정한다 (BX-16).
- **반려 길을 그린다.** 승인 칸이 있으면 뒤에 게이트웨이가 있어야 한다 — 반려를 무시하고 승인처럼 흘러가는 실수가 흔하다 (BX-05, BX-08, BX-16).
- 칸 `key`가 그대로 변수가 된다 — 뒤 게이트웨이 조건에서 쓰는 이름으로 짓는다.
- 위치: 서버 BPM 프로세스는 언제나 Center 결재함. PC에서 `field`는 **몇 분 안에 끝나는 현장 확인**만 (FX-16). 며칠 걸릴 수 있으면 서버로 옮긴다.
- 누가 결재하나는 BPMN에 쓰지 않는다 — Center 결재 배정 규칙(C6)이 정한다.
- 사람이 실물 작업을 하고 「확인」만 누르면 수동 확인(manualTask), 칸 없음 (FX-19).

## 7. 파일 출력

- `path`는 출력 폴더 기준 상대 경로, `outputs/`를 붙이지 않는다. 날짜·번호를 넣어 덮어쓰지 않게 (`대사표/대사표_{대상월}.md`).
- `template`이나 `variables` 중 하나는 반드시 (C14 B5). 둘 다 없으면 프로토타입에서는 모든 변수가 쏟아졌다.
- **`store_as` 필수.** 메일 첨부·후속 태스크가 경로를 받는 유일한 길이다.
- 쓰는 시점은 연결된 태스크가 끝날 때다. 보고서 본문은 스크립트·AI가 변수로 만들고, 파일 출력은 그 변수를 담기만 한다.

## 8. 시간과 기다림

| 하고 싶은 것 | 쓰는 것 | 주의 |
| --- | --- | --- |
| 매일·매월 시작 | 타이머 시작 (5필드 cron) | Studio 시험 실행은 일정을 기다리지 않고 **지금** 시작한다 |
| 기다리는 동안 한 번 알림 | 비중단 타이머 경계 | 경계는 반복 안 됨 — 리마인드는 한 번 (BX-03) |
| 기한이 지나면 다른 길로 | 중단 타이머 경계 | 끊긴 태스크는 **취소됨**(실패 아님). 그 길로 끝난 케이스는 통과다 |
| 고정된 마감 시각까지 반복해서 받기 | 받기 + 경계, 기간을 매번 계산 | 다시 기다릴 때마다 경계가 새로 시작된다 (BX-11) |
| 바깥 시스템의 응답 기다리기 | 받기 태스크 + 상관 키 | 상관 키가 없으면 메시지 시작만 깨운다 |
| 한 실행 안 가지끼리 알리기 | 신호 | 다른 실행·바깥에는 신호가 아니라 메시지 (FX-13). 경계는 태스크에만 붙는다 |
| 파일이 생기면 시작 | **조건 시작은 쓰지 않는다** | 타이머 + 목록 확인, 또는 바깥 시스템이 메시지를 보내게 (FX-04) |

- **기한·기간은 기본값 있는 입력으로** 두면 케이스가 짧게 바꿀 수 있다 (BX-03 `리마인드기한`, BX-34 `확인기한`). BPMN에 상수(`PT10M`)로 박으면 시험용 사본이 필요하다.
- **메시지가 받기보다 먼저 오면 잃는다** (C12 `no_receiver`). 바깥 시스템이 언제 보내는지 따져 보고, 받기 태스크를 일찍 세우거나 결재 칸으로도 받는다 (BX-34). 메시지 보관은 아직 없다.
- 받는 쪽이 아직 기다리지 않을 때 던진 **신호도 사라진다** (FX-13).
- **중단 경계가 끊은 하위 프로세스는 안에서 만든 변수를 내보내지 않는다** (BPMN 표준). 마감 뒤에도 필요한 값은 하위 프로세스 밖에서 누적한다 (BX-11 처음 판의 실수).
- 오래 기다리는 업무는 서버에서 (§3).

## 9. 확장·서비스 앱·화면

- 서비스 앱을 부르면 BPM 프로세스에 키 참조가 있어야 한다 (`service_keys` 또는 태스크 `key_ref`). **키 값은 어디에도 쓰지 않는다** — 이름만. 같은 앱이라도 BPM 프로세스마다 다른 키(읽기 전용 키 등)를 쓸 수 있다 (BX-35).
- 외부 앱은 C13 HTTP 어댑터 정의로 붙이고 Admin 서명을 받는다. 서버에 배포하려면 쓰는 작업이 결정 수행을 지원해야 한다 (C1 R8) — 외부 정의의 `modes`에 적는다.
- 그 작업이 멱등이 아니면 정의에 `idempotent:false`. 결과를 모르는 실패는 PC에서는 확인 창, 서버에서는 실행 실패나 오류 경계로 간다 (C13). 서버 BPM 프로세스는 오류 경계를 붙여 **사람에게 확인시킨다** — 기록만 남기면 아무도 모른다 (BX-32).
- 웹훅 태스크로 Center API처럼 인증이 필요한 곳을 부르지 않는다 (인증 헤더를 붙일 길이 없다). 서비스 앱으로 감싼다 (BX-16).
- 웹훅 본문은 `fields:[…]`로 고른다. `all`은 비밀이 섞일 수 있다 (B13).
- 등록된 화면이면 UI 태스크(셀렉터 사다리, LLM 없음), 등록 전 탐색이나 예외 화면만 `web`/`desktop` AI 태스크 (BX-36). UI 동작은 C10 목록(`fill`·`click`·`press`·`select`·`read`·`read_table`·`read_options`·`read_selection`) 안에서.
- 로그인은 Bot이 하지 않는다. 사람이 그 PC의 브라우저 프로필에 로그인해 두고, 끊기면 확인 트리거(「로그인 화면」)로 사람에게 넘긴다 (BX-14). 비밀번호를 스텝 값·파라미터에 쓰지 않는다.
- 데스크톱 앱의 경고 창은 확인 트리거로 등록한다. 단일 인스턴스 앱은 남은 프로세스가 다음 실행을 가로챈다 — 「실행 후 닫기」.
- 재실행해도 중복이 생기지 않게: 덧붙이기는 번호로 건너뛰기(BX-14), 넣기는 upsert(BX-36), 부작용 있는 서비스 앱 작업은 C11 멱등 키.

## 10. 케이스 — 최소 세트

케이스가 없으면 그 실행은 아무것도 증명하지 않는다. 예제마다 다음 중 해당하는 것을 모두 둔다.

| 케이스 | 무엇을 보나 | 예 |
| --- | --- | --- |
| 정상 | 기본 경로, 대표 숫자 | BX-01 「8월 정상」 |
| 문제 없음 / 대상 없음 | 조건부 가지가 **안** 도는지 | BX-01 「문제 없는 달」, BX-04 「발행 대상 없음」 |
| 비어 있음 | 반복 0번 | BX-01 「청구서 없음」, FX-09 「빈 목록」 |
| 경계값 | 규칙의 경계 (`>`와 `>=`) | BX-12 「무게 경계값」, FX-03b |
| 시간 초과·취소 | 경계 이벤트 가지 — 결재 자동 응답을 비워 두면 기다린다 | BX-03 「기한 초과」, BX-11 「공고 취소」 |
| 반려 | 승인 칸 뒤의 다른 길 | BX-05 「팀장 보류」, BX-21 「5일 부서장 반려」 |
| 바깥 실패 | 오류 경계 | BX-02 「메일 서버 없음」, FX-08 |
| 다시 실행 | 중복이 안 생기는지 | BX-14 「같은 날 다시 실행」 |
| 수동 (`manual: true`) | 결재 폼을 사람이 실제로 보는지 | BX-01, BX-20 |

- 결재 자동 응답(`approvals`)은 노드 id가 키다 — 그래서 id를 읽을 수 있게 짓는다.
- AI 결과는 정확히 같지 않다. 기대값에 `"*"`(있음), `{"$gte": 4}`(비교), 객체 부분 일치를 쓴다 (C14 비교 규칙).
- 시각을 받는 입력은 `{"$now_plus": "PT20S"}`로 (BX-11). 웹훅 회신 주소는 `{"$test_receiver": "reply"}` — Studio 시험 수신기 (C14).
- 받기 태스크를 시험하는 케이스는 `messages`로 메시지를 보낸다 (BX-05, BX-13).
- 경합에 기대는 케이스를 만들지 않는다. 순서가 필요하면 타이머·메시지로 순서를 잡는다 (FX-13).

## 11. 예제 더하기

1. 해당 분야의 `_source/spec_*.py`에 `Example(...)`를 더한다. 도우미(`start`, `ai`, `appr`, `goal` …)는 `_source/exdsl.py`.
2. `python _source/build.py` — 검사가 실패하면 고친다. 생성물을 직접 고치지 않는다.
3. 새 요소를 처음 쓰면 bpmn-js로 열어 그림을 본다 (라이트·다크 둘 다).
4. README의 커버리지 표가 저절로 갱신된다. 「없음」이 줄었는지 본다.
5. 예제가 계약의 공백을 드러내면 README 「아직 정하지 않은 것」과 해당 계약·ADR에 적는다. **예제를 계약에 맞추려고 업무를 비틀지 않는다** — 공백을 기록한다.
