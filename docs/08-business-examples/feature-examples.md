## FX-01. API AI 태스크

| 항목 | 값 |
| --- | --- |
| 분야 | 기능 예제 |
| 출처 | 프로토타입 example_api |
| 실행 위치 | **서버 (서버 BPM 프로세스)** |
| 시작 | 수동 실행 |
| 서비스 앱 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/fx01_api_call.bpmn) · [시험 케이스](cases/fx01_api_call.cases.json) |

**업무 배경과 목표**

공개 API 한 번 호출해 값을 꺼낸다. 업무 파라미터로 주소를 두면 재생 때 그대로 쓰인다.

**왜 서버에서 도는가**

서버 기본 (ADR-0016).

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 시작 | 시작 이벤트 | — | Task_Api |
| `Task_Api` | API 호출 | AI 태스크 | api · 결과 `원화`:number · 도구 http_request_tool · 파라미터 주소 | End |
| `End` | 끝 | 끝 이벤트 | — |  |

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Api` API 호출**

```markdown
## 상황
업무 파라미터 `주소`가 JSON API다.

## 할 일
GET으로 한 번 불러 `rates.KRW`를 꺼낸다.

## 판단하지 않는 것
값을 지어내지 않는다. 응답에 없으면 실패한다.

## 반환
- `원화`: number
```

</details>

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 기본 | {} | {"원화": {"$gt": 0}} | — |

**이 예제로 확인하는 것**

- `domain: api`
- 업무 파라미터
- 결정 수행 재생

**주의**

- 결과 타입을 적지 않으면 문자열 `"1380.5"`가 와서 뒤 비교가 틀렸다 — 결과에 타입을 적는다.

| 시작 | 수동 실행 |

| 파일 | [BPMN](bpmn/fx02_business_rule.bpmn) · [시험 케이스](cases/fx02_business_rule.cases.json) · [DMN](bpmn/discount_policy.dmn) |

**업무 배경과 목표**

금액·등급으로 할인율과 사유를 정한다.

**왜 서버에서 도는가**

서버 기본 (ADR-0016).

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다. 값 출처가 있으면 Center가 넣는다)

| 이름 | 타입 | 필수 | 기본값 | 값 출처 | 뜻 |
| --- | --- | --- | --- | --- | --- |
| `금액` | int | ✓ |  | 부르는 쪽 |  |
| `등급` | string | ✓ |  | 부르는 쪽 |  |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 시작 | 시작 이벤트 | — | Task_Rule |
| `Task_Rule` | 할인 정하기 | 규칙(DMN) | DMN `discount_policy` → 할인율, 사유 | Task_Price |
| `Task_Price` | 최종가 | 스크립트 | `최종가 = round(금액 * (1 - 할인율))` | End |
| `End` | 끝 | 끝 이벤트 | — |  |

**규칙 `discount_policy` (할인 정책, 적중 정책 FIRST)**

| 금액 | 등급 | → discount | discount_reason | 설명 |
| --- | --- | --- | --- | --- |
| >= 1000000 | "VIP" | 0.2 | "VIP 대량 주문" |  |
| >= 1000000 | - | 0.1 | "대량 주문" |  |
| - | "VIP" | 0.05 | "VIP" |  |
| - | - | 0 | "할인 없음" |  |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| VIP 대량 | {"금액": 1500000, "등급": "VIP"} | {"할인율": 0.2, "최종가": 1200000} | — |
| 일반 소량 | {"금액": 50000, "등급": "일반"} | {"할인율": 0} | — |

**이 예제로 확인하는 것**

- `businessRuleTask` + `chk:rule` 입력·출력 매핑
- 다중 출력 DMN

**주의**

- 프로토타입은 DMN 입력 이름(amount)과 변수 이름(금액)이 같아야 했다 — 새 형식은 `input` 매핑으로 잇는다.

## FX-04. 폴더 감시 (조건 시작 대체)

| 항목 | 값 |
| --- | --- |
| 분야 | 기능 예제 |
| 출처 | 프로토타입 example_conditional_start |
| 실행 위치 | **서버 (서버 BPM 프로세스)** |
| 시작 | 타이머 — 5분마다 |
| 서비스 앱 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/fx04_folder_poll.bpmn) · [시험 케이스](cases/fx04_folder_poll.cases.json) |

**업무 배경과 목표**

받은 폴더에 파일이 있으면 처리한다. 프로토타입은 조건 시작 이벤트를 썼지만 엔진이 조건을 계속 평가하지 못했다 → **타이머 + 게이트웨이**로 바꾼다.

**왜 서버에서 도는가**

서버 기본 (ADR-0016).

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다. 값 출처가 있으면 Center가 넣는다)

| 이름 | 타입 | 필수 | 기본값 | 값 출처 | 뜻 |
| --- | --- | --- | --- | --- | --- |
| `감시폴더` | string |  |  | 부르는 쪽 |  |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 5분마다 | 시작 이벤트 | 타이머 `*/5 * * * *` | Task_List |
| `Task_List` | 파일 목록 | 파일 목록 | `{감시폴더}` · 무늬 `*` → `파일` · 개수 `건수` | Gw_Any |
| `Gw_Any` | 있음? | 배타 게이트웨이 | — | Approve_Confirm (`건수 > 0`), End_None (기본) |
| `Approve_Confirm` | 처리 확인 | 결재 | 「받은 파일 처리」 · 보임 파일 · 칸 `처리`(bool*) · Center 결재함 | End |
| `End_None` | 없음 | 끝 이벤트 | — |  |
| `End` | 끝 | 끝 이벤트 | — |  |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 빈 폴더 | {"감시폴더": "samples/inbox-empty"} | {"건수": 0} | — |
| 2건 | {"감시폴더": "samples/inbox"} | {"건수": 2} | `Approve_Confirm`: {"처리": true} |

**이 예제로 확인하는 것**

- 조건 시작 이벤트는 지원하지 않음 (C14) → 타이머 폴링
- 끝 이벤트 둘
- 파일 목록 태스크 (`chk:fileList`)

**주의**

- 조건 시작은 「무엇이 바뀌면 다시 평가하나」가 정의되지 않아 프로토타입에서 한 번만 돌았다.
- 폴링은 실행이 자주 생긴다 — 「없음」 실행은 이력에서 접어 보이게(CON-04 필터).

| 항목 | 값 |
| --- | --- |
| 분야 | 기능 예제 |
| 출처 | 프로토타입 example_signal |
| 실행 위치 | **서버 (서버 BPM 프로세스)** |
| 시작 | 수동 실행 |
| 서비스 앱 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |

**업무 배경과 목표**

가지 A가 준비되면 `ready` 신호를, 검사에서 문제가 나오면 `abort` 신호를 던진다. 가지 B는 `ready`를 기다렸다가 일하고, 일하는 중 `abort`가 오면 정리한다.

**왜 서버에서 도는가**

서버 기본 (ADR-0016).

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다. 값 출처가 있으면 Center가 넣는다)

| 이름 | 타입 | 필수 | 기본값 | 값 출처 | 뜻 |
| --- | --- | --- | --- | --- | --- |
| `검사결과` | string |  | "ok" | 부르는 쪽 |  |
| `작업번호` | string |  | "W-1" | 부르는 쪽 |  |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 시작 | 시작 이벤트 | — | Gw_Fork |
| `Gw_Fork` |  | 병렬 게이트웨이 | — | Wait_A, Wait_Ready |
| `Wait_A` | 1초 뒤 | 중간 받기 | 타이머 `PT1S` | Task_Prepare |
| `Task_Prepare` | 준비 (A) | 스크립트 | `준비 = True` | Thr_Ready |
| `Thr_Ready` | ready | 중간 던지기 | 신호 `ready` | Task_Inspect |
| `Task_Inspect` | 검사 (A) | 스크립트 | `result = 검사결과` | Gw_Problem |
| `Gw_Problem` | 문제? | 배타 게이트웨이 | — | Thr_Abort (`result != 'ok'`), End_A (기본) |
| `Thr_Abort` | abort | 중간 던지기 | 신호 `abort` | End_A |
| `End_A` | A 끝 | 끝 이벤트 | — |  |
| `Wait_Ready` | ready 대기 | 중간 받기 | 신호 `ready` | Recv_Work |
| `Recv_Work` | 본 작업 완료 받기 | 메시지 받기 | 메시지 `work_done` · 상관 `작업번호` | Task_Work |
| `Task_Work` | 본 작업 기록 (B) | 스크립트 | `작업 = '완료'` | End_B |
| `Task_Cleanup` | 정리 (B) | 스크립트 | `작업 = '중단'` | End_B |
| `End_B` | B 끝 | 끝 이벤트 | — |  |
| `Bnd_Abort` | abort | 경계(신호) | `Recv_Work`에 붙음 · `abort` | Task_Cleanup |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 정상 | {} | {"작업": "완료"} | —<br>4초 뒤 `work_done` {} |
| 문제<br><small>abort가 1초쯤 오므로 4초 뒤 완료 메시지는 받을 곳이 없다</small> | {"검사결과": "bad"} | {"작업": "중단"} | —<br>4초 뒤 `work_done` {} |

**이 예제로 확인하는 것**

- 중간 던지기 신호 / 중간 받기 신호 / 경계 신호
- 한 실행 안의 가지 사이 신호 (C14 범위)
- 중간 받기 타이머로 순서 잡기
- 받기 태스크의 신호 경계

**주의**

- 신호는 **한 실행 안의 가지 사이**에서만 오간다 (C14). 다른 실행·외부 시스템에 알리려면 메시지를 쓴다 (BX-11).
- 받는 쪽이 아직 기다리지 않을 때 던진 신호는 사라진다. 가지 A 앞에 1초 대기를 두어 B가 먼저 `ready 대기`에 서게 한다 — 시험용 순서 잡기이며, 실제 업무에서는 신호에 순서를 기대지 않는다.
- `abort` 경계는 바깥 작업 완료를 기다리는 받기 태스크에 붙였다. 경계는 태스크에만 붙는다(이벤트에는 못 붙임). 순간에 끝나는 스크립트에 붙이면 신호가 닿기 전에 끝나 버린다.

- **칸이 없어도 답은 비어 있지 않다** — 폼이 없는 결재의 답은 `decision`(`approve`/`reject`)이다 (C6). 케이스에 `{}`를 적었더니 Studio 시험 실행이 답을 거절하고 같은 자리를 되풀이했다 (조각 3e-3).
- PC에서 `field`로 둘 때는 몇 분 안에 끝나는 일만. 며칠 걸릴 수 있으면 서버 BPM 프로세스 + Center 결재함 (BX-20).

| `Task_Say` | 정리 | 스크립트 | `요약 = f'{등급}/{담당}'` | End |
| `Task_None` | 해당 없음 | 스크립트 | `요약 = '해당 없음'` | End |
| `End` | 끝 | 끝 이벤트 | — |  |

**규칙 `risk_grade` (위험 등급, 적중 정책 UNIQUE)**

| 점수 | → grade | 설명 |
| --- | --- | --- |
| [80..100] | "상" | 80 이상 |
| [50..79] | "중" |  |
| [1..49] | "하" | 1 이상 |

**규칙 `owner_any` (담당 배정, 적중 정책 ANY)**

| 점수 | 지역 | → owner | 설명 |
| --- | --- | --- | --- |
| [80..100] | - | "본사" | 고위험은 본사 |
| - | "서울","본사" | "본사" | 서울·본사 지역도 본사 |
| [1..79] | "부산","대구","광주" | "지점" | 그 밖은 지점 |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 고위험 서울 — 두 줄이 겹친다<br><small>`ANY`의 두 줄이 함께 맞고 **결과가 같다** — `UNIQUE` 쪽은 한 줄만 맞는다</small> | {"점수": 90, "지역": "서울"} | {"등급": "상", "담당": "본사", "요약": "상/본사"} | — |
| 중위험 부산 | {"점수": 60, "지역": "부산"} | {"등급": "중", "담당": "지점", "요약": "중/지점"} | — |
| 해당 없음 (0점)<br><small>맞는 줄이 없으면 **모든 출력이 `None`**이다 — 실패가 아니다</small> | {"점수": 0, "지역": "부산"} | {"등급": null, "요약": "해당 없음"} | — |

**이 예제로 확인하는 것**

- DMN 적중 정책 `UNIQUE`
- DMN 적중 정책 `ANY` (겹치는 줄, 같은 결과)
- 맞는 줄 없음 = 모든 출력 `None`

**주의**

- 적중 정책 넷 중 예제가 밟던 것은 `FIRST`·`COLLECT` 둘뿐이었다 — 코드는 넷을 받는다 (`contracts.dmn.HIT_POLICIES`). 「받는다」와 「돌려 봤다」는 다르다.
- `UNIQUE`는 **구간을 겹치지 않게** 적어야 한다. 겹치면 판정이 `DmnError`이고 **오류 경계로 받을 수 없다** — 그림의 흠이라 고쳐야 한다 (단위 시험이 그 자리를 본다).
- `ANY`는 「겹쳐도 된다」가 아니라 **「겹치면 결과가 같아야 한다」**다. 결과가 갈라지면 실행 오류다 — `FIRST`로 두면 그것을 아무도 보지 않는다.
- 그래서 `ANY` 표에는 **모든 것에 맞는 마지막 줄을 둘 수 없다** — 처음에 `-, - → 지점`을 적었더니 고위험 서울에서 세 줄이 맞고 결과가 갈라져 판정이 멈췄다. 「그 밖」은 **값을 적어** 겹치지 않게 한다.
- 맞는 줄이 없을 때를 **게이트웨이로 가른다** — `None`을 그대로 뒤에 쓰면 식이 멈춘다.

| 문의 한 건<br><small>세 모드가 **같은 답을 낸다** — 다른 것은 「모델을 몇 번 부르나」다 (시험이 그것을 센다)</small> | {"문의": "지난주에 받은 물건이 깨져 있습니다"} | {"문의갈래": "*", "기록결과": "*", "말투": "*"} | — |

**이 예제로 확인하는 것**

- 재생 모드 `plan`(기본)·`full`·`none`을 한 그림에서
- `full`은 도구가 있어야 한다 (B12)
- `none`은 되밟지 않는다

**주의**

- 재생 모드 셋 중 예제가 밟던 것은 **기본 `plan` 하나**뿐이었다 (AI 태스크 31개가 모두 기본값) — `full`·`none`은 계약과 코드에만 있었다. FX-21·FX-22와 같은 꼴이다.
- **`full`에는 도구가 있어야 한다** (B12 검사 오류) — 아무것도 확인하지 않고 답만 복사하는 태스크를 만들지 않으려는 규칙이다. 그래서 `full`은 「도구가 일을 하는」 자리(입력·발행·쓰기)에 쓴다.
- **명세가 없으면 `plan`·`full`도 그냥 돈다** (C14) — 처음 배포한 BPM 프로세스가 멈추면 안 된다. 그래서 자율 수행을 한 번도 하지 않은 BPM 프로세스에서는 세 모드가 똑같이 보인다.
- **재생이 맞지 않으면 몰래 자율로 넘어가지 않는다** (ADR-0028) — 기억에 적힌 도구가 없거나 도구가 실패하면 `TASK_FAILED`로 올려 오류 경계가 받는다.

## FX-24. 일괄 기동 — 접수 BPM 프로세스

| 항목 | 값 |
| --- | --- |
| 분야 | 기능 예제 |
| 출처 | 새로 — 가상 직원·일괄 기동 (ADR-0079·0082) |
| 실행 위치 | **서버 (서버 BPM 프로세스)** |
| 시작 | 작업 지시 — 인입 목록을 받는다 |
| 서비스 앱 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/fx24_batch_intake.bpmn) · [시험 케이스](cases/fx24_batch_intake.cases.json) |

**업무 배경과 목표**

가상 직원의 **접수 BPM 프로세스**이다. 인입 N건을 감독자에게 **한 번에** 보이고(결재 하나, 담당자 = 감독자), 승인되면 **건마다 서버 BPM 프로세스(FX-25) 작업을 하나씩** 낸다 — Call Activity 반복 + 위임이다. 반려하면 아무것도 기동하지 않는다. 일괄은 이 실행 한 번이고 일괄 id는 그 `run_id`다 (ADR-0079).

**왜 서버에서 도는가**

서버 기본 (ADR-0016). 기동할 것도 서버 BPM 프로세스라 실행 위치를 그림에 적지 않는다 — 대상 패키지가 정한다 (ADR-0082).

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다. 값 출처가 있으면 Center가 넣는다)

| 이름 | 타입 | 필수 | 기본값 | 값 출처 | 뜻 |
| --- | --- | --- | --- | --- | --- |
| `인입` | list | ✓ |  | 부르는 쪽 | {번호, 금액} 목록 |
| `감독자` | list | ✓ |  | `virtual_worker.supervisors` | 이 일괄을 승인할 사람들 — Center가 가상 직원 등록에서 넣는다 |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 시작 | 시작 이벤트 | — | Task_Count |
| `Task_Count` | 건수 세기 | 스크립트 | `건수 = len(인입)` | Approve_Batch |
| `Approve_Batch` | 일괄 승인 | 결재 | 「인입 {건수}건 일괄 기동」 · 보임 인입, 건수 · 칸 `승인`(bool*), `메모`(text) · Center 결재함 | Gw_Ok |
| `Gw_Ok` | 승인? | 배타 게이트웨이 | — | Call_Batch (`승인`), End (기본) |
| `Call_Batch` | 건마다 기동 (위임 반복) | BPM 프로세스 호출 | `Proc_fx25_batch_item` · 입력 번호, 금액 · 출력 처리결과 · 반복(차례) `인입`→`결과목록` | Task_Tally |
| `Task_Tally` | 결과 세기 | 스크립트 | `등록수 = len([x for x in 결과목록 if x == '등록'])` … | End |
| `Task_Failed` | 기동 실패 | 스크립트 | `실패사유 = error_message` | End |
| `End` | 끝 | 끝 이벤트 | — |  |
| `Bnd_Batch` | 기동 실패 | 경계(오류) | `Call_Batch`에 붙음 · `DELEGATION_FAILED` | Task_Failed |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 세 건 승인<br><small>Studio에서는 케이스가 **건마다 같은 값**을 돌려준다. 진짜 서버 실행기에서는 FX-25가 건마다 판정한다(둘째 건은 보류)</small> | {"인입": [{"번호": 1, "금액": 500000}, {"번호": 2, "금액": 2000000}, {"번호": 3, "금액": 300000}], "감독자": ["김감독"]} | {"건수": 3, "결과목록": ["등록", "등록", "등록"], "등록수": 3, "감독자": ["김감독"]} | `Approve_Batch`: {"승인": true} |
| 반려 — 기동 없음<br><small>반려하면 위임이 하나도 나가지 않는다</small> | {"인입": [{"번호": 1, "금액": 500000}], "감독자": ["김감독"]} | {"건수": 1} | `Approve_Batch`: {"승인": false} |
| 기동 실패<br><small>위임 결과를 **적어 두지 않으면** 그 자리에서 실패다 — 반복 노드의 오류 경계가 **한 번** 받고 나머지 건은 거둔다</small> | {"인입": [{"번호": 1, "금액": 500000}], "감독자": ["김감독"]} | {"실패사유": "*"} | `Approve_Batch`: {"승인": true} |

**이 예제로 확인하는 것**

- **일괄 기동** — Call Activity 반복 + 위임 (`chk:loop` + `chk:call.delegate`)
- 서버 BPM 프로세스에 위임
- **병렬 반복** — 건을 한 번에 맡기고 함께 기다린다 (`isSequential=false`, ADR-0087)
- 결재 담당자 = **가상 직원의 감독자** (`assignees: "감독자"` ← 입력의 값 출처 `virtual_worker.supervisors`, ADR-0099)
- 결재 반려 시 기동 없음

**주의**

- 일괄은 **자원이 아니라 실행 하나**다 — 승인은 보통 결재이고 순서는 그림에 있다 (ADR-0079). 그래서 B16이 그림에서 「결재를 지나지 않는 반복 위임」을 알린다.
- 결재가 **보여 준 목록 그대로** 반복한다 — 결재와 반복 사이에서 `인입`을 다시 만들면 B16 경고다 (보여 준 것과 다른 것을 기동할 수 있다).
- 건별 업무 결과(등록·보류)는 **자식 BPM 프로세스가 제 그림에서 정해 `outputs`로 돌려준다** — 위임 실패로 남는 것은 거절·만료 같은 바깥 일뿐이다. 바깥 일 한 건이 실패하면 **맡겨 둔 나머지를 거둔다** (ADR-0087 §4 — 시작 안 된 것·시작된 서버 자식은 취소된다).
- 반복 안의 위임은 **차례마다 작업 하나**이고 멱등 키에 차례가 들어간다 — 그것이 없으면 2건째부터 1건째 작업이 돌아왔다 (엔진은 반복 중에 `node_instance`를 올리지 않는다).
- **감독자를 그림에 다시 적지 않는다** — 입력 `감독자`의 **값 출처**가 `virtual_worker.supervisors`라 Center가 등록된 가상 직원의 감독자를 넣고, 결재가 그 입력을 담당자로 쓴다. 감독자를 CON-13에서 바꾸면 다음 일괄부터 따라간다. 받는 정보는 다른 입력과 **한 목록**이다 (ADR-0099). 필수로 두었으니 가상 직원 없이 돌리면 **시작조차 하지 않는다**. 부르는 쪽은 이 입력을 줄 수 없고(422) Studio에서는 케이스 입력에 같이 적는다.
- **자식은 가상 직원을 이어받는다** — FX-25는 입력 `처리자`의 값 출처를 `virtual_worker.name`으로 **선언**했을 뿐이고 FX-24가 넘기지 않는다. 일괄이 맡긴 작업은 그 가상 직원의 작업이라 Center가 값을 넣는다. FX-25를 혼자 기동하면 `처리자`는 비어 있다.
- **병렬로 그린다** — 차례로 그리면 한 건이 끝나야 다음 건을 맡겨 N건이 한 건씩 끝까지 돈다. 서버 그림의 병렬 반복은 N건을 한 번에 맡기고, 결과 목록은 끝난 순서와 상관없이 **입력 순서**다 (ADR-0087).

| 실행 위치 | **서버 (서버 BPM 프로세스)** |
| 시작 | 작업 지시 — FX-24가 **위임**으로 만든다 |
| 서비스 앱 | 없음 |

**업무 배경과 목표**

일괄의 한 건을 처리한다. 금액이 크면 **보류**로 판정하고 그것을 **결과로 돌려준다** — 실패가 아니라 업무 결과다. `처리결과`를 `outputs`로 선언해 맡긴 쪽(FX-24)에게 돌려준다 (C1 — 선언한 것만 올라간다).

**왜 서버에서 도는가**

서버 기본 (ADR-0016).

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다. 값 출처가 있으면 Center가 넣는다)

| 이름 | 타입 | 필수 | 기본값 | 값 출처 | 뜻 |
| --- | --- | --- | --- | --- | --- |
| `번호` | int | ✓ |  | 부르는 쪽 |  |
| `금액` | int | ✓ |  | 부르는 쪽 |  |
| `처리자` | string |  |  | `virtual_worker.name` | 일괄을 낸 가상 직원의 이름 — Center가 넣는다(맡긴 일괄의 가상 직원). 혼자 기동하면 비어 있다 |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 시작 | 시작 이벤트 | — | Gw_Amount |

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 작은 금액 | {"번호": 1, "금액": 500000} | {"처리결과": "등록"} | — |

- 위임으로 시작하는 서버 BPM 프로세스
- `outputs` 선언 — 맡긴 쪽이 받을 것

**주의**

- 건별 업무 결과는 **자식의 그림**에 있다 — 맡긴 쪽이 「실패」로 받으면 한 건 때문에 일괄 전체가 멈춘다 (ADR-0082 §3).
