## BX-30. 계약서 검토

| 항목 | 값 |
| --- | --- |
| 분야 | 운영·법무·IT·고객 |
| 출처 | 프로토타입 시나리오 4 (진행 중이던 것 — 호출 3개, 사전 점검까지) |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 메시지 `contract_review` — 전자계약 시스템의 검토 요청 |
| 서비스 앱·키 참조 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx30_contract_review.bpmn) · [시험 케이스](cases/bx30_contract_review.cases.json) |

**업무 배경과 목표**

계약서 초안이 오면 조항을 뽑고, 위험도가 높은 세 가지 조항(손해배상·지식재산·해지)을 공유 BPM 프로세스 「조항 검토」(BX-37)로 각각 검토한다. 셋의 결과를 모아 위험 등급을 정하고, 높으면 법무팀 결재를 받는다. 검토 의견서를 만들어 요청 시스템에 돌려준다.

**왜 서버에서 도는가**

문서·AI·결재 — 서버.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| --- | --- | --- | --- | --- |
| `요청번호` | string | ✓ |  |  |
| `계약서` | string | ✓ |  | PDF 경로 |
| `상대방` | string | ✓ |  |  |
| `회신주소` | string | ✓ |  |  |

**흐름 (노드)**

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Extract` 조항 뽑기**

```markdown
## 상황
`계약서`는 계약서 PDF다.

## 할 일
손해배상, 지식재산, 해지 조항의 원문을 찾아 그대로 옮긴다. 조항 번호도 적는다.

## 판단하지 않는 것
조항이 유리한지 불리한지 판단하지 않는다. 없으면 빈 문자열.

## 반환
- `손해배상조항`: string
- `지재권조항`: string
- `해지조항`: string
```

**`Task_Opinion` 의견서 쓰기**

```markdown
## 상황
세 조항의 검토 결과(`손해배상결과`, `지재권결과`, `해지결과`)와 `등급`, 법무 의견(있으면 `의견`)이 있다.

## 할 일
요청자가 읽을 검토 의견서를 쓴다: 요약 → 조항별 위험과 수정 제안 → 결론.

## 판단하지 않는 것
검토 결과에 없는 새 위험을 만들지 않는다.

## 반환
- `의견서`: string (markdown)
```

</details>

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 표준 계약 | {"요청번호": "CR-01", "계약서": "samples/contracts/standard.pdf", "상대방": "가나상사", "회신주소": {"$test_receiver": "reply"}} | {"등급": "낮음"} | — |
| 무제한 배상 | {"요청번호": "CR-02", "계약서": "samples/contracts/unlimited_liability.pdf", "상대방": "다라물산", "회신주소": {"$test_receiver": "reply"}} | {"등급": "높음"} | `Approve_Legal`: {"의견": "배상 한도 조항 추가 필요", "서명가능": false} |

**이 예제로 확인하는 것**

- 같은 공유 BPM 프로세스를 다른 매핑으로 3번 호출
- 호출을 병렬로
- 리터럴 입력 매핑(`'손해배상'`)
- AI 두 번 — 추출과 작성 사이에 판단(스크립트·결재)

**주의**

- 호출 셋이 모두 `결과`를 돌려준다. 출력 매핑으로 이름을 나눠야(`손해배상결과` 등) 셋이 따로 남는다 — 프로토타입 사전 점검에서 호출마다 자기 매핑만 들어가고 결과 셋이 다른 이름으로 남는 것을 확인했다. 출력에 적지 않은 변수는 돌아오지 않는다.
- 같은 AI 태스크(BX-37 `Task_Review`)가 한 실행 안에서 세 번, 서로 다른 입력으로 돈다. 재생 명세는 태스크마다 하나라서, 종류에 따라 달라지는 값은 목표 문장이 아니라 입력으로 받아야 세 조항에 맞게 재생된다 (프로토타입 시나리오 4의 주의).
- 추출 목표에 「판단하지 않는 것」을 적어 위험 평가는 검토 BPM 프로세스에만 맡긴다.

## BX-37. 조항 검토 (공유)

| 항목 | 값 |
| --- | --- |
| 분야 | 운영·법무·IT·고객 |
| 출처 | 프로토타입 시나리오 4의 호출 대상 |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | BPM 프로세스 호출 — BX-30 |
| 서비스 앱·키 참조 | 없음 |
| 확장 | 없음 (플랫폼 기본 태스크만) |
| 마일스톤 | **M3** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx37_clause_review.bpmn) · [시험 케이스](cases/bx37_clause_review.cases.json) |

**업무 배경과 목표**

조항 원문과 종류를 받아 사내 표준 조항(업무 파라미터)과 비교하고 위험 점수(0~5)와 수정 제안을 돌려준다.

**왜 서버에서 도는가**

AI만 — 서버.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |
| --- | --- | --- | --- | --- |
| `조항` | string | ✓ |  | 원문 |
| `종류` | string | ✓ |  | 손해배상/지식재산/해지 |
| `표준조항` | dict |  | {"손해배상": "직접 손해에 한하며 계약금액을 한도로 한다", "지식재산": "산출물의 권리는 발주자에게 귀속", "해지": "30일 전 서면 통지"} | 종류별 사내 표준 |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 시작 | 시작 이벤트 | — | Gw_Empty |
| `Gw_Empty` | 조항 있음? | 배타 게이트웨이 | — | Task_Review (`조항 != ''`), Task_Missing (기본) |
| `Task_Review` | 조항 검토 | AI 태스크 | llm · 결과 `결과`:dict | End |
| `Task_Missing` | 조항 없음 | 스크립트 | `결과 = dict(점수=3, 이유='조항이 없음', 제안=표준조항[종류])` | End |
| `End` | 끝 | 끝 이벤트 | — |  |

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Review` 조항 검토**

```markdown
## 상황
`조항`은 계약서의 `종류` 조항 원문이다. `표준조항[종류]`가 사내 표준이다.

## 할 일
표준과 비교해 위험 점수(0 없음 ~ 5 매우 높음), 이유, 수정 제안 문구를 낸다.

## 판단하지 않는 것
다른 종류의 조항을 평가하지 않는다.

## 반환
- `결과`: {점수(int), 이유(string), 제안(string)}
```

</details>

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 무제한 배상 | {"조항": "을은 갑에게 발생한 모든 손해를 배상한다.", "종류": "손해배상"} | {"결과": {"점수": {"$gte": 4}}} | — |
| 빈 조항 | {"조항": "", "종류": "해지"} | {"결과": {"점수": 3}} | — |

**이 예제로 확인하는 것**

- 호출 대상 공유 BPM 프로세스
- 빈 입력 가드(게이트웨이)

**주의**

- AI 결과는 값이 매번 조금씩 다르다 — 기대 결과에 비교 연산(`{"$gte": 4}`)과 부분 일치를 쓴다 (C14 시험 케이스 비교 규칙).

## BX-31. 업무 요청 접수·분배

| 항목 | 값 |
| --- | --- |
| 분야 | 운영·법무·IT·고객 |
| 출처 | 프로토타입 example_operator(운영 비서) 확장 → 새로 설계 |
| 실행 위치 | **서버 (서버 Bot)** |
| 시작 | 메시지 `ops_request` — 사내 요청 메일함·메신저 봇이 보냄 |
| 서비스 앱·키 참조 | `ticketing` → `ops-ticket` |
| 확장 | ticketing |
| 마일스톤 | **M5** Studio 시험 실행에서 처음 통과 → M5 Center 배포 → M7 서버 실행기 |
| 파일 | [BPMN](bpmn/bx31_request_triage.bpmn) · [시험 케이스](cases/bx31_request_triage.cases.json) |

**업무 배경과 목표**

사내 공용 요청 창구(「운영지원」)로 들어오는 자유 형식 요청을 AI가 읽고 종류(장비/권한/시설/기타)와 긴급도를 정해 담당 팀 큐로 보낸다. 판단이 애매하면(AI 확신도 낮음) 사람이 분류한다. 접수 확인을 요청자에게 보낸다.

**왜 서버에서 도는가**

AI·메시지 — 서버.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| 이름 | 타입 | 필수 | 기본값 | 뜻 |
| --- | --- | --- | --- | --- |
| `요청번호` | string | ✓ |  |  |
| `요청자` | string | ✓ |  |  |
| `본문` | string | ✓ |  |  |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |
| --- | --- | --- | --- | --- |
| `Start` | 요청 도착 | 시작 이벤트 | 메시지 `ops_request` | Task_Classify |
| `Task_Classify` | 요청 분류 | AI 태스크 | llm · 결과 `종류`:string, `긴급도`:string, `요약`:string, `확신도`:number | Gw_Confident |
| `Gw_Confident` | 확신? | 배타 게이트웨이 | — | Task_Ticket (`확신도 >= 0.8`), Approve_Manual (기본) |
| `Approve_Manual` | 사람이 분류 | 결재 | 「요청 분류」 · 보임 본문, 종류, 긴급도, 요약, 확신도 · 칸 `종류`(choice*), `긴급도`(choice*) · Center 결재함 | Task_Ticket |
| `Task_Ticket` | 티켓 만들기 | 서비스 앱 태스크 | `ticketing`.`create_ticket` · 입력 queue, priority, title, body → 티켓번호 | Task_Ack |
| `Task_Ack` | 접수 확인 | 메일 보내기 | 받는 사람 {요청자} · 제목 「[접수] {요약}」 | End |
| `End` | 끝 | 끝 이벤트 | — |  |

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Classify` 요청 분류**

```markdown
## 상황

## 할 일
종류(장비|권한|시설|기타), 긴급도(높음|보통|낮음), 한 줄 요약, 확신도(0~1)를 낸다.

## 반환

- `긴급도`: string
- `요약`: string
- `확신도`: number
```

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 노트북 고장 | {"요청번호": "R-1", "요청자": "a@example.com", "본문": "노트북 화면이 안 켜져요. 오늘 오후 고객 미팅이 있어요."} | {"종류": "장비", "긴급도": "높음"} | — |
| 애매한 요청 | {"요청번호": "R-2", "요청자": "a@example.com", "본문": "그거 좀 봐주세요"} | {"종류": "기타"} | `Approve_Manual`: {"종류": "기타", "긴급도": "낮음"} |

**이 예제로 확인하는 것**

- AI 확신도로 사람 개입 여부 결정 (human-in-the-loop)
- 결재 칸이 AI 결과 변수를 덮어씀
- 티켓 시스템 서비스 앱

**주의**

- 확신도는 모델의 자기 평가라 믿을 만하지 않다 — 기준값(0.8)은 케이스로 보정하고, 사람 분류 결과를 모아 나중에 기준을 다시 잡는다.

| 출처 | 새로 설계 — 외부 확장(멱등 아님) 예 |

**왜 서버에서 도는가**

외부 API·AI·결재 — 서버.

**입력** (`chk:process.inputs` — 작업 지시·메시지 본문·케이스가 채운다)

| `본문` | string | ✓ |  |  |

**흐름 (노드)**

| id | 이름 | 종류 | 핵심 속성 | 다음 |

| `Approve_Agent` | 상담원 확인 | 결재 | 「답변 확인」 · 보임 제목, 본문, 초안, 근거부족 · 칸 `최종답변`(text*), `보내기`(bool*) · Center 결재함 | Gw_Send |

<details><summary>AI 태스크 목표 전문</summary>

**`Task_Draft` 답변 초안**

```markdown
## 상황
`본문`은 고객 문의, `근거`는 사내 FAQ 검색 결과(최대 5개)다.

## 할 일
근거만 사용해 정중한 답변 초안을 쓴다. 근거가 부족하면 `근거부족`을 true로.

## 판단하지 않는 것
근거에 없는 정책·보상을 약속하지 않는다.

## 반환
- `초안`: string
- `근거부족`: bool
```

</details>

**시험 케이스**

| 케이스 | 입력 | 기대 결과 | 결재 자동 응답 · 보내는 메시지 |
| --- | --- | --- | --- |
| 배송 문의 | {"문의번호": "T-1001", "제목": "배송 언제 와요?", "본문": "주문한 지 5일 지났어요"} | {"근거부족": false} | `Approve_Agent`: {"최종답변": "안녕하세요 고객님, ...", "보내기": true} |

**이 예제로 확인하는 것**

- 외부 확장 `idempotent:false` 작업 — 자동 재시도 없음
- 실패·결과 모름을 오류 경계로 받아 사람 확인 결재로
- RAG형 근거 검색 + 초안
- 결재에서 긴 글 수정(text 칸)

**주의**

- 멱등이 아닌 외부 작업은 C13 정의에 `idempotent:false`로 적는다. 결과를 모르는 실패는 서버에서 실행 실패 또는 오류 경계로 간다 (C13 §4-1) — 이 예제는 오류 경계로 받아 사람이 외부 화면을 확인한다. 기록만 남기고 끝내면 아무도 모른다.
- 오류 경계는 확실한 실패(4xx)와 결과 모름을 같이 받는다 — 결재 창에 `error_message`를 보여 구분하게 한다.
- 서버 배포에는 `post_reply`가 결정 수행을 지원해야 한다 (C1 R8). 외부 정의의 `modes`에 명시한다.
- AI 초안을 그대로 보내지 않는다 — 고객에게 나가는 글은 사람이 확인.

- 확인 기한을 BPMN에 상수(`PT10M`)로 박으면 케이스가 짧게 바꿀 수 없다 — 기본값 있는 입력으로 둔다.
- 당직 확인 전에 복구 메시지가 오면 받기 태스크가 아직 없어 C12가 `no_receiver`로 거부하고, 실행은 복구를 영원히 기다린다. 메시지 보관(TTL)이 정해지기 전에는 복구 확인을 받기 대신 확인 결재의 칸(「이미 복구됨」)으로도 받는 편이 안전하다 — README 「아직 정하지 않은 것」.
- 팀장 호출 뒤에도 복구 메시지를 기다리게 하려면 `Task_Lead` → `Recv_Recovered`로 이어도 된다. 끝 이벤트가 둘인 것은 의도.

**이 예제로 확인하는 것**

- UI 태스크(등록 화면)와 AI 데스크톱 자율 태스크를 한 BPM 프로세스에
- PC BPM 프로세스에서 서비스 앱 호출
- upsert로 재실행 안전

**주의**

- 프로토타입 시나리오 3에서 데스크톱을 AI가 직접 몰면 자율 388초, 재생 56초였다 — 등록된 화면은 UI 태스크로(LLM 없음), 예외만 AI 태스크로.
- 운영 Bot은 결정 수행(재생)이다. 모양이 제각각인 예외 카드는 재생 명세가 맞지 않을 수 있다 — 그때 운영에서 몰래 자율 수행으로 넘어가지 않는다(ADR-0010). 오류 경계로 받아 `수작업` 목록으로 사람에게 넘기고, 정상 카드는 그대로 넣는다.
- `read_table`은 표의 머리글·줄을 돌려준다 (C10). 카드처럼 「항목 | 값」 격자는 표로 읽고 스크립트에서 사전으로 바꾼다.
